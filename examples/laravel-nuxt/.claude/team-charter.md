## Назначение

Интернет-магазин shop: API бэкенда на Laravel и витрина на Nuxt. Раскладка `multi`: корень
workspace — отдельный репозиторий конфигурации команды и памяти (`.claude/`, `memory/`), код —
в независимых репозиториях внутри `projects/`, у каждого свой `origin` на GitLab:

```
projects/
├── shop-backend/    Laravel 12 · PHP 8.4 · PostgreSQL — API, модули app/Modules/*
└── shop-frontend/   Nuxt 4 · @nuxt/ui · Pinia — витрина, клиент API генерирует orval в app/api/
```

## Intake-режим

**План вместе, дальше сами.** Задача крупнее мелкой правки начинается с плана: `architect` готовит design brief (понимание задачи, 2–3 варианта с трейд-оффами, риски, вопросы), пользователь правит и утверждает. После утверждения реализация, тесты и ревью идут без остановок до готового MR; прерывание — только на необратимом, всплывшем после плана.

<!-- beerpowers:engine intake -->
Вопрос пользователю поднимается только на **необратимых развилках** — список один,
в `memory/project/safety-rules.md`, раздел «Только после подтверждения пользователя».
Всё остальное команда решает сама и докладывает результатом.

**Язык постановки сверяется с `memory/project/glossary.md`.** Термин из постановки или речи
пользователя, который расходится со словарём или в нём не определён, поднимается вопросом
в design brief, а не толкуется молча. Уточнённый термин вносится в глоссарий в том же заходе.
Правила ведения — последний раздел глоссария.

**Расхождение макета, кода и постановки команда молча не разрешает** — каждое выносится
пользователю, даже когда «взять свежий источник» выглядит очевидным: источники принадлежат
разным людям, и какой из них устарел, знает только человек.

## Порядок гейтов

<!-- beerpowers:engine gates -->
```
исполнитель → reviewer (ранний) ⇄ фиксы → tester → reviewer (финальный) → push + MR
                      ↑______________|
               петля, пока есть блокеры
```

**Исполнитель на срезе гоняет тесты затронутого, а не весь набор.** Тесты модулей и файлов,
которых коснулся срез, — формой фильтра по пути или имени теста из `memory/commands/<скоуп>.md`,
раздел «Тесты по фильтру»; полный прогон — один раз, перед сдачей раннему `reviewer`'у. Полный
набор после каждого среза перепроверяет то, чего срез не трогал, и на большом наборе съедает
до половины захода. Раздела нет — фильтр строится по раннеру из таблицы «Стек», а рабочая форма
уходит в отчёт: раздел ведёт team-lead.

1. **Ранний `reviewer`** — по прод-коду: границы модулей, инварианты, объём, структура;
   замечания без вердикта. Блокеры закрываются петлёй до `tester`'а: исполнитель правит,
   ранний проход повторяется по инкременту `git diff HEAD~1`. Рекомендации `tester`'а
   не задерживают — их разбирает финальный проход.
2. **`tester`** — тесты, прогон UI в реальном браузере, скриншоты, мутационные пробы и их таблица
   в `test-cases.md`. Фаза — свой заход: состояние между заходами — только в `test-cases.md`
   и `bug-log.md`, а не в пересказе брифа и не в новом файле папки задачи.
3. **Финальный `reviewer`** — весь дифф **вместе с тестами**, screenshots-gate и закрытие замечаний
   раннего прохода. Только здесь появляется `APPROVED`; push и MR — после него.

Ревью дважды, потому что **тесты — тоже код и требуют ревью**; второй проход дешёвый — тестовые
файлы и скриншоты, база `HEAD~1`.

**`NOT APPROVED` — маршрут по тому, что правит фикс.** Назначает `reviewer` строкой в отчёте:

| Что правит фикс | Маршрут |
|---|---|
| тесты, комментарии, документация | исполнитель → повторный финальный проход по `git diff HEAD~1` |
| прод-код | исполнитель → `tester` (только затронутые сценарии, объём называет `reviewer`) → финальный проход |
| прод-код, задевший UI | то же плюс **новые скриншоты**: снятые до фикса относятся к другому коду |

Прод-фикс не возвращается к `reviewer`'у напрямую: `APPROVED` утверждает, что `tester` проверил
**этот** код.

**Финальная точка — последней.** Финальный проход начинается, когда правки, тесты и мутационные
пробы закончены, и выносит вердикт по результатам на коммите, который уйдёт в MR. Готовые
результаты `reviewer` читает, недостающие быстрые гейты (`memory/commands/`) гоняет сам в фоне;
мутационных проб не гоняет — нехватка пробы — находка с маршрутом на `tester`. Полный прогон
набора `tester`'а засчитывается без перезапуска, если лог снят **на том же коммите** — коммит
в логе совпадает с `git rev-parse HEAD` репозитория, дерево при прогоне было чистым — и в логе
есть итоговая строка прогона. Коммит другой, дерево было грязным, коммита или итоговой строки
в логе нет — полный прогон гоняет `reviewer`. Параллельно
с финальным проходом не идёт ничего, что влияет на вердикт.
<!-- /beerpowers:engine -->

<!-- beerpowers:engine adversary -->
**Независимый оппонент на money-critical.** Дифф задел деньги, арифметику сумм или миграцию,
трансформирующую данные, — роль, которая это увидела, запрашивает у team-lead'а через
`SendMessage` независимого оппонента со свежим контекстом по тому же диффу и **завершает ход**
промежуточным отчётом «жду оппонента», не дописывая вывод в том же сообщении: иначе эскалация
выродится в формальность. Team-lead ответил — роль продолжает по ответу: поднял оппонента —
его находки идут в вывод с пометкой источника, отказал — в выходе строка
`adversary: declined (money-critical)` с его причиной. Ответа нет и ход возобновили без него —
работа не блокируется, но в выходе стоит строка `adversary: none (money-critical)`: осознанный
риск принимает человек.
<!-- /beerpowers:engine -->

## Правила работы

<!-- beerpowers:engine communication -->
**Коммуникация.** Между ролями — `SendMessage`. Задачи — через `Task*`, если рантайм их выдал:
в списке инструментов или отложенными, через `ToolSearch`. Не выдал —
роль передаёт состав задачи team-lead'у через `SendMessage`, список ведёт он.

**Язык и стиль.** Отчёт роли team-lead'у — по-английски: пользователь его не читает,
а кириллица стоит примерно вдвое дороже в токенах. Всё, что попадает в файл или git, —
по-русски. Стиль отчёта — caveman (full): без артиклей и филлеров, фрагменты допустимы,
короткие синонимы. Технические термины, код, имена API и строки ошибок — точно, без изменений
и без «упрощения».

**Отчёт роли — короткий по умолчанию:** что сделано, чем проверено, что не проверено,
открытые вопросы. Без пересказа диффа и таблиц замеров, если не просили; подробный разбор —
когда роль нашла дефект или расхождение.
<!-- /beerpowers:engine -->

<!-- beerpowers:engine ui-findings-report if=ui:true -->
**Находка в интерфейсе — адресом и скриншотом.** В отчёте к каждому месту — URL страницы
(`http://localhost:<порт>/…`, а не «в каталоге»), ширина и путь скриншота, где место выделено;
мест несколько — скриншот на каждое. Имя класса, токена или компонента — после адреса,
не вместо него: team-lead передаёт находку человеку как есть, а человек не обязан знать,
как элемент называется в разметке.
<!-- /beerpowers:engine -->

<!-- beerpowers:engine git-roles -->
**Git — роли не пишут.** Ветки, коммиты, push и MR делает team-lead; `reviewer` остаётся
read-only. Имя ветки — код задачи (`<КОД>`). Запреты — `memory/project/safety-rules.md`.

**База для диффа — ответ `node .claude/bin/git-base.mjs <репо> <КОД>`.** Скрипт сам знает
профиль репозитория, ветку по умолчанию на сервере и базу из `memory/tasks/<КОД>/git-flow.md`
и печатает готовую команду: дифф от точки ответвления до рабочего дерева, вместе
с незакоммиченным. У одной задачи база бывает разной в разных репозиториях — скрипт зовётся
по каждому. Инкремент после прошлого коммита — `git -C <репо> diff HEAD~1`.
<!-- /beerpowers:engine -->

<!-- beerpowers:engine processes -->
**Процессы гасятся только по своему PID.** Роль поднимает dev-сервер и headless-браузер сама
и обязана убрать их за собой — но целью служит PID, полученный при запуске, а не имя образа.
Рабочая форма — `taskkill //F //PID <свой pid> //T`, на POSIX — `kill <свой pid>`; свой
headless Chrome — иначе, по скиллу `beerpowers:page-screenshot`: его дерево процессов `taskkill`
переживает. Барьер —
`guard-kill` плагина, если он включён в `.claude/workspace.json`; что он ловит и почему
не маска — `.claude/reference/hooks.md`.

**Порт dev-сервера не назначается — адрес берётся из вывода сервера.** Сервер запускается
в фоне формой из `memory/commands/<скоуп>.md`, без своего порта, с выводом в файл в scratchpad;
адрес — из его строки вида `Local: http://localhost:3002/`, и он же идёт в скриншоты и отчёт.
Занятый порт dev-серверы обходят сами (Nuxt, Vite, `artisan serve` берут следующий свободный),
поэтому соседние деревья и вторая роль не мешают друг другу, а угаданный «свой обычный» порт
ведёт на чужой сервер. Порт задаётся явно, только если проект требует этого
в `memory/commands/<скоуп>.md`.
<!-- /beerpowers:engine -->

<!-- beerpowers:engine evidence -->
**Тестом называется только тест.** Формулировки «покрыто тестом», «проверено под
`Queue::fake()`» допустимы, если тестовый файл лежит в том же диффе. Разовый прогон в консоли
или браузере называется прогоном: «прогнано вручную», «проверено в браузере». `tester`
оставляет тест на изменённое поведение либо пишет, почему теста нет, — эта строка попадает
в описание MR, и молчание о тестах читается как нарушение.

**Шкала находок — только из charter.** Находка размечается как **блокер** (нарушение
доменного инварианта, решения менеджера или молчаливая порча данных — мерж без починки
запрещён) либо **рекомендация** (улучшение без нарушения, разбирается на финальном ревью),
с основанием: какой инвариант или решение задето. **Security-находка в коде, который дифф
добавил или изменил, — всегда блокер**: инъекция, обход прав или доступ к чужому объекту,
секрет в коде или логах, файл без проверки, вывод ввода без экранирования, ослабленная
проверка. Та же находка в коде, который дифф не трогал, и укрепление сверх нынешнего
уровня — рекомендация плюс пункт `tech-debt/`: задача не держит чужой долг. Уровни BLOCKER/HIGH/MEDIUM/LOW
не используются: определений у них в проекте нет. Пришла чужая шкала — пересчитать в шкалу
charter до отчёта.

**Метки находок — латиницей, и только из таблицы.** Таблица держит и идентификаторы,
которые находками не являются, но живут в тех же файлах и коммитах. У каждого вида своя
буква — первая буква его английского названия, и буква одного вида у другого запрещена:
«B1 закрыт» в коммите читается одним способом, а греп по метке приносит только её.

| Префикс | Что обозначает | Кто ставит | Где живёт | Как закрывается |
|---|---|---|---|---|
| `B<N>` | blocker — блокер или баг по шкале выше | `reviewer`, `tester`; находки оппонента — `reviewer` в своём отчёте | отчёт роли, `review-report.md`, `bug-log.md` | фиксом и перепроверкой: назван тест или прогон, проба — строкой таблицы мутаций |
| `R<N>` | recommendation — рекомендация | `reviewer`, `tester`, `auditor`, `product` | отчёт роли, `review-report.md` | на финальном ревью: сделано в задаче, пункт `tech-debt/` или отказ с причиной |
| `N<N>` | note — наблюдение без дефекта | любая роль | отчёт роли, `review-report.md`, `test-cases.md` | решением team-lead'а: снято строкой с причиной или стало находкой `B`/`R` со своим номером |
| `C<N>` | case — сценарий тест-плана | `architect` в тест-плане брифа, `tester` дописывает | `design-brief.md`, `test-cases.md` | прогоном `tester`'а со статусом pass / fail / skip |
| `M<N>` | mutation — проба таблицы «критерий → тест → мутация» | `tester`; план проб — `architect` в брифе | `test-cases.md`, `design-brief.md` | прогоном: на ветке тест зелёный, на мутанте красный |
| `S<N>` | slice — срез плана брифа, `S0` — подготовительный | `architect` | `design-brief.md` | гейты среза зелёные (тесты — затронутого, по фильтру), срез закоммичен |
| `Q<N>` | question — развилка или вопрос пользователю | team-lead, `architect` в open questions брифа | `design-brief.md`, `preflight.md` | ответом человека, записанным в `preflight.md` дословно |

Нумерация сквозная внутри задачи, у каждой буквы своя. Находки — одна последовательность
на все роли: `B1` у `tester`'а и `B2` у `reviewer`'а. Номер не переиспользуется: закрытый `B3`
остаётся `B3`, следующий блокер — `B4`. Метка вне таблицы не вводится — ни буква раздела
у сценария, ни своя нумерация шагов: нужен новый вид идентификатора — это правка таблицы
движка, а не обычай проекта. `P0`–`P3` у `product` и Workflow-скриптов — приоритет очерёдности
работ, а не метка: он стоит рядом с меткой, а не вместо неё. Форма одна в отчёте роли, в файлах
`memory/tasks/**`, в коммитах и в чате: метка, переписанная кириллицей, выглядит как другая
и рвёт поиск грепом. Чужая шкала пересчитывается до отчёта — абзац «Шкала находок».

**Правило находки — на весь дифф.** Находка ревью формулируется правилом, а не списком мест:
«ни одного объекта, собранного руками при существующей фабрике, в новых и изменённых тестах»,
«после переноса кода найти осиротевшие методы, связи и импорты». Список мест закрывает
только названные строки, и следующий проход находит то же нарушение в соседнем файле.

<!-- beerpowers:engine shell -->
**Shell-вызовы.** Форма команды выбирается так, чтобы она прошла без запроса разрешения:

- Никакого `cd … &&` — рабочая директория уже корень workspace, а `cd` и промптит,
  и оставляет залипший cwd для следующих вызовов. В другой репозиторий заходим флагами
  самих инструментов: `git -C <путь>`, `npm --prefix <путь>`, `make -C <путь>`.
- Аллоулищенные скрипты вызываем **литеральным путём**: без переменной в имени команды
  (`"$DIR/script"` не матчится), без `$(…)`-подстановки. Динамику (`git rev-parse`) считаем
  отдельным простым вызовом и подставляем literal в следующий.
- **Независимые чтения и поиски — одним ходом.** Несколько `Read`, `Grep`, `Glob` или
  читающих Bash-команд, результат которых не влияет на выбор следующей, отправляются
  в одном вызове, а не по одному: каждый лишний ход перечитывает весь контекст
  (пересчитать — `/beerpowers:token-audit`). Зависимое чтение — когда путь или шаблон второго
  вызова берётся из результата первого — идёт отдельным ходом.
- Файлы пишем инструментами `Write`/`Edit`, не `echo >>` и не heredoc.
- Безопасной непромптящей формы нет — сказать об этом и предложить правило в
  `.claude/settings.json`, а не запускать вслепую.

**Правила по путям.** В `.claude/rules/` лежат требования, привязанные к каталогам. Рантайм
подмешивает их роли автоматически — но **только при открытии файла через `Read`**. `cat`,
`git diff` и любое другое чтение через `Bash` уходят мимо них молча.

**Инструменты поиска.** Чтение и поиск — через `Read`/`Grep`/`Glob`, не через `cat`/`rg`/`find`:
`Grep`/`Glob` заявлены в `tools:` ролей и фактически выдаются. `rg`, `grep -rn`, `ls`, `cat`
через `Bash` — только после того, как вызов инструмента в этом заходе реально вернул отказ;
предполагать недоступность заранее нельзя.

Чтение истории — исключение: `git status`, `diff`, `log`, `show`, `blame` инструментом
не читаются вовсе, здесь `Bash` и есть правильная форма. Файл, который git показал изменённым,
затем открывается через `Read`.

<!-- beerpowers:engine code-hygiene -->
**Комментарии в коде.** Не писать то, что и так видно из кода или из имени вызова.
Комментировать только неочевидное «почему»: скрытое ограничение, обходной путь, неожиданное
поведение стороннего кода. Перед сдачей — перечитать добавленные строки комментариев в диффе
и удалить те, что читатель восстановил бы из строки под ними. Барьер — `guard-comments`
плагина, если он включён: печатает добавленные комментарии и блокирует коммит один раз,
содержание не оценивает (`.claude/reference/hooks.md`).

**Линт в конце задачи.** Менял код — прогони линтер с автофиксом **только по изменённым
файлам**, не по всему репозиторию. Формы по скоупу — `memory/commands/<скоуп>.md`.

<!-- beerpowers:engine evidence-discipline -->
**Артефакты — файлами.** Design brief, ADR, отчёты ревью и планы пишутся файлами
(`memory/tasks/<КОД>/`, `memory/adr/`), а не выдаются простыней в чат.

**Записи о красных базах — с датой и командой, иначе не заводятся.** Утверждение вида
«гейт красный», «в ветке по умолчанию N ошибок», «команда не работает» выключает гейт: роль
перестаёт читать вывод и начинает искать в нём подтверждение, что красное — чужое. Поэтому
такая запись обязана нести **дату** и **точную команду со всеми флагами**, которой получена.
Без команды перепроверить нельзя, и запись живёт вечно.

Читающий такую запись **перепроверяет её прогоном**, прежде чем на неё опереться, и правит
на месте, если не воспроизвелась. Критерий приёмки по гейту — зелёный вывод целиком; ссылка
на красную базу допустима только после того, как она подтверждена своим прогоном.

**Усечённый идентификатор не достраивается по памяти.** Хеш коммита, номер MR, id треда,
ключ, код задачи, увиденный в сокращённом виде, берётся из сохранённого вывода или
запрашивается заново. Правдоподобный id хуже явной ошибки: он совпадает с чужой сущностью,
и действие уходит не туда молча. Печатаешь сокращённо ради читаемости — полный вывод тем же
вызовом в файл, значение дальше — из файла. Сущность опознаётся по идентификатору, а не
по подстроке текста: появится второй объект с той же подстрокой — действие уйдёт в него.

**Вывод о поведении делается прогоном, а не чтением кода.** Механизм, найденный в исходнике
библиотеки, может не проявляться на реальных входных данных. Заявление вида «библиотека
теряет события», «флаг залипает», «запрос не уходит» подтверждается замером, который
эту величину меряет.

**Диагностику начинать с грепа `memory/` по буквальной строке ошибки.** Красный гейт, странный
вывод инструмента, расхождение двух окружений — первым делом `Grep` по `memory/` с точным
текстом исключения или именем символа из него, а не по теме и не по своей догадке о причине:
готовый разбор часто уже написан. Нашёл запись — перепроверь её прогоном, но раскопки с нуля
не начинай. Не нашёл — диагностируй и запиши результат так, чтобы следующий нашёл его грепом
по тому же симптому: строка ошибки стоит в тексте записи, а не только в пересказе.

**Инструмент замера — часть утверждения.** Прежде чем объявить дефект по красной пробе,
проверь, что проба вообще способна дать зелёный результат на заведомо исправном объекте.
Не способна — она измеряет себя, а не код.

**Два прогона подряд — не независимое подтверждение.** Повтор в той же сессии на том же
состоянии окружения воспроизводит и настоящий дефект, и общий для обоих прогонов артефакт.
Для гейта, зависящего от генерируемого кеша — `.nuxt`, `vendor`, `node_modules`, — считается
только прогон на чистом кеше либо в другой момент времени.

Случаи, на которых написаны эти четыре правила, — `memory/tests/probes.md`. Читать перед
тем, как объявить гейт красным.

**Число в отчёте — из итоговой строки инструмента или счётом по полному файлу, с единицей
счёта.** Касается каждого, кто запускает команды.

- Полный вывод прогона пишется в файл целиком; усечение (`head`, `tail`, `grep`) делается
  при чтении, не при записи: обрезанный вывод выглядит как полный.
- Число ошибок, тестов, файлов берётся из summary-строки самого инструмента (раннеры тестов,
  статанализ, typecheck печатают итог в конце) либо считается командой (`grep -c`) по полному
  файлу. Число из хвоста вывода — артефакт обрезки, в отчёт и в вердикт не идёт.
- У числа есть единица счёта: файлы, вхождения, места кода или элементы на экране. Число
  без единицы не воспроизводится.
- Код выхода фоновой составной команды читается из маркера в логе (`cmd > log 2>&1;
  echo CODE=$? >> log`, затем греп по `CODE=`), а не из статуса задачи: статус цепочки
  принадлежит последнему `echo` и равен нулю всегда. Код выхода вообще — не гейт сам по себе:
  два прогона сборки на одном состоянии могут дать разные коды при одинаковых ошибках;
  критерий гейта — счёт строк ошибок в логе, форма — `memory/commands/<скоуп>.md`.
- Фоновый прогон дольше десяти минут без нового вывода проверяется по процессу — PID жив,
  хвост лога растёт, — и либо докладывается строкой «прогон жив: <факт>», либо гасится
  по своему PID и перезапускается. Ожидание без проверки работой не считается.
- Конца фонового прогона дожидаются отрезками по четыре с половиной минуты — блокирующим
  вызовом `Bash` в foreground, а не перечитыванием лога:
  `i=0; until grep -q '^CODE=' <лог> || [ $i -ge 27 ]; do sleep 10; i=$((i+1)); done; tail -20 <лог>`
  с `timeout: 300000`. Каждый `Read` или `tail` лога — отдельный запрос к модели, который
  заново читает весь контекст захода, у роли это сотни тысяч токенов за одну проверку;
  опрос раз в несколько секунд обходится дороже самого прогона. Вызов длиннее пяти минут
  обходится ещё дороже: кеш промпта роли живёт пять минут, и запрос после такого вызова
  заново пишет в кеш весь контекст по ставке записи — в 12–25 раз дороже чтения, смотря
  по модели. Отрезок кончился без `CODE=` — следующий такой же вызов; десять минут без нового
  вывода — проверка по PID из пункта выше. Сразу в foreground запускается только прогон,
  который заведомо укладывается в четыре минуты, с тем же таймаутом; длиннее — в фон
  и ожидание отрезками.
- Полный прогон тестов репозитория — через `parallel-tests.mjs`, если у репозитория есть
  запись `tests.repos.<репо>` в `.claude/workspace.json`:
  `node .claude/bin/parallel-tests.mjs --repos <репо> > <лог> 2>&1`, в рабочем дереве —
  с `--task <КОД>`, несколько репозиториев — через запятую. Инструмент делит тесты на процессы
  с отдельной базой и временным каталогом у каждого, держит общий на машину лимит процессов
  для всех сессий и сам пишет в конец лога строки `REPO`, `TOTAL` и `CODE=` — число в отчёт
  берётся из них, ожидание — по `CODE=`, как в пункте выше. Форма вызова — `--help` инструмента
  и эти настройки, а не пересказ в памяти; своих параллельных обвязок (цикл по процессам,
  база на процесс руками) не пишешь. Записи нет — форма из `memory/commands/<скоуп>.md`.
  Лог полного прогона несёт коммит, на котором он снят: инструмент пишет его в строку `START`
  сам (`head=<sha> tree=clean|dirty`), форма из памяти начинает лог строкой
  `HEAD=<sha> tree=clean|dirty` по `git -C <репо> rev-parse HEAD` и `git -C <репо> status --porcelain`.
  По этой строке финальный проход решает, перезапускать ли набор («Финальная точка — последней»).
- Мутационные пробы — через `mutants.mjs`, если у репозитория есть запись
  `tests.repos.<репо>.mutate` в `.claude/workspace.json`:
  `node .claude/bin/mutants.mjs <файл мутантов> > <лог> 2>&1`, в рабочем дереве — с `--task <КОД>`.
  Файл мутантов — во временном каталоге роли, а не в `memory/tasks/<КОД>/`; формат — `--help`
  инструмента. Каждый мутант идёт в своей копии дерева со своим фильтром теста, нулевой мутант
  без замены проверяет, что фильтр зелёный на исправном коде, проверка копии с опустошённым
  файлом — что тест читает файл из копии, неизменившиеся берутся из кеша.
  Таблицу мутаций в `test-cases.md` даёт вывод инструмента, итог — его строка `TOTAL`;
  самодельных скриптов замены и прогона мутантов не пишешь. Записи нет — пробы руками
  в рабочем дереве задачи, по одной, с откатом и `git status` после каждой.
