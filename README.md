# 🍺 beerpowers

Плагин для Claude Code, который превращает обычную сессию в тимлида небольшой команды
разработки. Под рукой у него архитектор, бэкенд-разработчик, специалист по базе данных,
фронтендер, тестировщик и ревьюер; для зрелых продуктов — ещё devops и аудитор безопасности
и производительности, для продуктовой работы — продакт, для быстрых поисков по коду —
разведчик. Каждый работает в своём контексте, отвечает за свой участок и сдаёт работу через
проверки, которые нельзя пройти на словах.

Задача проходит путь от постановки в трекере до merge request по одному и тому же процессу:
разбор, план, реализация по слоям, тесты, ревью в два прохода, коммит и MR с честным
описанием. А то, что нельзя доверить тексту инструкции, держат хуки.

## 🤔 Зачем это нужно

Если одна сессия Claude и пишет код, и сама же его проверяет, рано или поздно она начинает
верить себе на слово. Тесты «зелёные», потому что их никто не запускал. Ревью «пройдено»,
потому что ревьюер — тот же контекст, который только что этот код написал. Правило из
`CLAUDE.md` честно прочитано в начале и тихо забыто к середине длинной задачи. beerpowers
отвечает на это разделением труда и проверками, которые смотрят на факты, а не на отчёты:

- **У каждой роли свой контекст.** Исполнитель не ревьюит сам себя. Ревьюер читает дифф,
  а не пересказ того, что исполнитель якобы сделал.
- **Гейты вместо обещаний.** Сборка, тесты и линт запускаются, и их вывод читается целиком.
  Ревью идёт в два прохода: ранний — по архитектуре, пока менять ещё дёшево, финальный — по
  всему диффу перед MR.
- **Каждому заходу — свой уровень мышления.** Тимлид сам решает, на какой модели и с каким
  `effort` поднять роль, и решает по цене ошибки, а не по объёму работы: проектирование
  и ревью — всегда в полную силу, механическая правка, которую проверит сборка, — дешевле.
  Выбор он называет тебе перед каждым вызовом.
- **Барьеры, а не просьбы.** Push в защищённую ветку, убийство чужих процессов, комментарии,
  пересказывающие код, отклоняются хуками — механически, без надежды на то, что модель
  вспомнит запрет.
- **Память, в которой всё на своём месте.** Формы команд, доменные инварианты, грабли, техдолг
  и конвенции тестов лежат каждый в своём файле. Роль знает, где искать и куда записать
  найденное, а знание не расползается копиями по десятку мест.
- **Постановка из первоисточника.** Задача читается из трекера в момент работы, а не из файла,
  который скопировали неделю назад и который с тех пор молча устарел.

## 🎯 Для какого проекта

beerpowers рассчитан на веб-продукт: бэкенд и фронтенд одним или несколькими
git-репозиториями. Чем ближе ваш проект к этому описанию, тем больше плагин сделает сам.

| | Что поддержано |
|---|---|
| Стек | Для Laravel, Nuxt 3/4, PostgreSQL, Supabase, Elasticsearch и GitLab CI у ролей есть готовые стековые чеклисты. Другой стек — NestJS, Next, Django и так далее — работает на общих шаблонах ролей, а команды сборки и тестов setup берёт из самого проекта; стековые скиллы он предложит, если они у тебя установлены |
| Git-хостинг | GitLab — MR заводится прямо первым push'ем, полное описание ставится через API. GitHub — через `gh pr create` |
| Флоу веток | `main-default` — задача ответвляется от ветки по умолчанию, мерж MR и есть выкатка. `dev-default` — задачи копятся в `dev`, в `master` или `main` уходят плановым merge или срочным cherry-pick. `custom` — свой флоу, описанный словами |
| Трекер задач | Яндекс Трекер — команда сама выгружает постановку вместе с комментариями и вложениями. С другим трекером постановку даёшь текстом |
| Макеты | Figma — фронтендер сам выгружает фрейм по ссылке из постановки |
| ОС | Windows (через Git Bash) и Linux |

### ⚠️ Ограничения

- **macOS пока не проверялся.** Хуки и скрипты написаны под POSIX `sh`, но с BSD-версиями
  утилит не прогонялись.
- **Agent Teams — экспериментальный режим Claude Code.** Поведение рантайма меняется от версии
  к версии. Что замерено и на какой версии, ведётся в
  [журнале замеров](plugins/beerpowers/reference/runtime-compat.md); что ещё не проверено
  в живой работе — там же, в разделе «Не замерено».
- **Команда живёт в отдельном каталоге над репозиториями кода**, а не внутри репозитория
  продукта. Как его устроить — ниже.

## 📁 Перед установкой: структура каталогов

Код лежит не в корне, а в `projects/`. Сам корень — отдельный git-репозиторий, в котором
хранятся настройки команды и память проекта. Так рабочие деревья задач, их артефакты и заметки
команды не попадают в историю продукта, а несколько репозиториев одного проекта команда видит
вместе — как ты, когда открываешь их рядом.

```
shop/                    ← корень workspace, свой git-репозиторий; здесь запускается Claude Code
└── projects/
    ├── shop-backend/    ← клон репозитория бэкенда
    └── shop-frontend/   ← клон репозитория фронтенда
```

Собрать такую структуру с нуля (команды одинаково работают в bash и PowerShell):

```
mkdir shop
cd shop
git init
git clone <адрес репозитория бэкенда> projects/shop-backend
git clone <адрес репозитория фронтенда> projects/shop-frontend
```

Даже если репозиторий один, он всё равно кладётся в `projects/<имя>/`. После setup рядом
появятся `.claude/`, `memory/`, `CLAUDE.md` и `.gitignore`, а когда команда начнёт работать
над задачами — ещё и `worktrees/` с отдельными рабочими деревьями. И `projects/`,
и `worktrees/` стоят в `.gitignore` корня.

## 📦 Установка

Понадобятся:

- **Claude Code с включённым Agent Teams** — флаг `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`
  в `env` файла `settings.json`. Для проекта setup пропишет его в `.claude/settings.json` сам;
- **`node` 22 или новее, `git`, `bash` и `sh`** — на Windows всё это даёт Git for Windows;
- **Chrome** — если у проекта есть интерфейс. Скриншоты страниц роли снимают в собственном
  headless Chrome: ему нужен только установленный браузер.
- **Расширение Claude in Chrome** — если хочешь, чтобы роли
  прокликивали интерфейс в твоём браузере, с твоими входами в аккаунты. Работают они там только
  в своей вкладке и чужие не трогают. Без расширения для этого есть встроенный браузер
  десктопного приложения Claude.

```
/plugin marketplace add AKosogorov/beerpowers
/plugin install beerpowers@akosogorov
```

## 🚀 Первый запуск

Открой Claude Code в корне workspace и запусти:

```
/beerpowers:setup
```

Сначала setup молча изучает репозитории: стек, команды сборки и тестов, брейкпоинты вёрстки,
флоу веток на сервере, следы трекера и макетов. Потом задаёт вопросы — по одной теме за раз:
кто будет работать с командой, какой нужен состав, где команде останавливаться и ждать тебя,
какие интеграции подключить, какие барьеры включить, какие скиллы раздать ролям, на каких
ширинах проверять вёрстку и как устроен git. В конце показывает план и ничего не пишет, пока
ты его не подтвердишь. Твои существующие файлы он не перезаписывает: всё, что затрагивает их,
сначала показывается диффом.

После setup в проекте появляются:

| Что | Зачем |
|---|---|
| `.claude/team-charter.md` | правила, общие для всех ролей; подключён к `CLAUDE.md` импортом |
| `.claude/team-lead.md` | как главная сессия ведёт задачу: класс, состав, модель и effort, гейты, закрытие |
| `.claude/agents/` | роли, настроенные под стек проекта |
| `.claude/workspace.json`, `.claude/git-settings.json` | ширины экранов, барьеры, профили репозиториев |
| `.claude/settings.json` | разрешения под команды проекта и запреты разрушающих |
| `.claude/bin/`, `.claude/hooks/`, `.claude/reference/` | скрипты, хуки и справочники из плагина |
| `memory/` | память проекта: карта, команды, инварианты, грабли, техдолг, тесты, задачи |

Как это выглядит целиком, видно на вымышленном проекте Laravel + Nuxt в [`examples/`](examples/).

Сразу после setup стоит запустить `/beerpowers:doctor`: он проверит машину и всё собранное
и на каждую проблему скажет, как её починить. А если хочется, чтобы команда с первого дня
знала проект глубже, `/beerpowers:onboard` прочитает код по подсистемам и наполнит память.

## 🔄 Как идёт работа над задачей

1. **`/beerpowers:task-start <код-задачи>`.** Тимлид выгружает постановку из трекера вместе
   с комментариями и вложениями, разбирает её, определяет класс задачи — тривиальная, lean
   или фича, — заводит папку `memory/tasks/<код-задачи>/` и ветку от правильной базы. Если задача
   незнакомая и хочется сначала понять, во что ввязываешься, добавь `--preview`: будут разбор
   и вопросы, но ни одной записи и ни одной поднятой роли.
2. **План.** По умолчанию команда приходит с планом: как она поняла задачу, два-три варианта
   решения с плюсами и минусами, риски и вопросы. Дальше ты правишь и говоришь «делай». Если
   нужен контроль плотнее, в setup можно выбрать остановку после каждого этапа; если хочется
   отдать задачу целиком — режим без остановок. Необратимое — миграцию с данными, удаление,
   деньги, смену публичного API — команда согласует всегда, в любом режиме.
3. **Работа ролей.** Тимлид поднимает только тех, кто нужен задаче: архитектора — когда есть
   что проектировать, исполнителей — по задетым слоям, тестировщика — писать тесты и прогонять
   экраны на всех ширинах проекта со скриншотами, ревьюера — на ранний и финальный проход.
   Каждому он выставляет модель и `effort` по цене ошибки этого захода и называет выбор тебе.
   Фронтендер сам выгружает фрейм Figma по ссылке из постановки. Найденное на ревью уходит
   обратно исполнителю — ревьюер код не правит.
4. **Коммиты и MR.** Коммитит тимлид, по коммиту на каждый заход, а перед MR схлопывает
   историю в один коммит на задачу. Первый push заводит MR с описанием: что сделано, чем это
   проверено и что осталось непроверенным. Кнопку мержа жмёшь ты. Хочешь сначала посмотреть
   на стенде — скажи «залей в dev».
5. **Возвращение к задаче.** Тот же `/beerpowers:task-start <код-задачи>` на уже начатой задаче
   перевыгружает постановку и показывает, что в ней поменялось с прошлого раза.
6. **После мержа — `/beerpowers:retro`.** Уроки задачи переезжают в память проекта, а папки
   влитых задач и их рабочие деревья убираются.

Несколько задач параллельно — не проблема: каждая получает своё рабочее дерево
`worktrees/<код-задачи>/`. Флаг `--worktree` просит об этом явно, а если репозиторий уже занят
другой задачей, отдельное дерево заводится само.

## 🔌 Интеграции и доступы

| Интеграция | Что даёт | Что нужно |
|---|---|---|
| Яндекс Трекер | постановка с комментариями и вложениями | OAuth-токен с правом `tracker:read` и идентификатор организации — в `~/.claude/yandex-tracker-settings.json` (один файл на все проекты) или в переменных `YANDEX_TRACKER_*`. Где выпустить токен и что куда вписать, объясняет шаблон `.claude/yandex-tracker-settings.json.example` |
| Figma | фреймы макета файлами в папке задачи | personal access token на чтение — в `~/.claude/figma-settings.json` или в `FIGMA_TOKEN`; шаблон — `.claude/figma-settings.json.example` |
| GitLab | MR с полным описанием | при HTTPS токен отдаёт git credential helper, настраивать ничего не нужно; при SSH setup спросит, где лежит токен |
| GitHub | PR | авторизованный `gh` |
| Chrome | скриншоты страниц, прокликивание интерфейса | установленный Chrome; для работы в твоём браузере — расширение Claude in Chrome |

## 🛡️ Барьеры

Барьеры — хуки плагина. По умолчанию включены все, а setup спрашивает, какие оставить.

| Барьер | Что он не пропустит |
|---|---|
| `guard-push` | push в `master`, `main` и ветку по умолчанию, голый force-push, удаление веток на сервере; push с силой, после которого из ветки на сервере пропадут коммиты, — один раз со списком; на GitLab — первый push ветки задачи без создания MR |
| `guard-kill` | остановку процессов по имени вроде `pkill node` или `taskkill /IM` — только по своему PID, иначе вместе с процессом роли упадут твой dev-сервер и IDE |
| `guard-comments` | коммит с комментариями, которые просто пересказывают код |
| `guard-commit-split` | коммит файлов задачи вперемешку с остальной памятью и настройками |
| `guard-agent-memory` | запись в личную память роли чего-либо, кроме твоей обратной связи; не выключается |
| `guard-user-files` | перезапись и удаление твоих файлов, пока идут setup и onboard |

К ним можно добавить два напоминания. `quality-reminder` после каждой правки подсказывает роли,
какие проверки нужны для этого типа файла. `screenshots-reminder` один раз возвращает
тестировщика, который закончил работу над экраном, не сняв скриншотов.

## ⌨️ Команды

| Команда | Когда звать |
|---|---|
| `/beerpowers:task-start <код-задачи>` | начать задачу или вернуться к ней; `--preview` — только разбор |
| `/beerpowers:team-lazy` | задача на несколько ролей, которых не нужно поднимать заранее |
| `/beerpowers:team-up` | эпик с петлями «сделал → проверили → доработал» — вся команда сразу |
| `/beerpowers:team-down` | свернуть команду; незавершённое остаётся в `handover.md` задачи |
| `/beerpowers:retro [<код-задачи> …]` | после мержа: уроки и уборка влитых задач с их рабочими деревьями |
| `/beerpowers:worktrees-clear` | убрать рабочие деревья отдельно |
| `/beerpowers:decision-brief` | собрать материал для решения, которое принимает человек вне команды |
| `/beerpowers:token-audit` | разобраться, куда ушли токены сессии и ролей |
| `/beerpowers:setup` | собрать команду; в уже собранном проекте — дописать недостающее |
| `/beerpowers:doctor` | диагностика машины и собранного, с фиксом на каждую строку |
| `/beerpowers:update` | перенести новую версию плагина в собранный проект |
| `/beerpowers:onboard` | глубоко наполнить память по существующему коду |
| `/beerpowers:feature`, `/beerpowers:product-onboard` | продуктовая дорожка: от хотелки через PRD и декомпозицию к плану; включается в setup |

У плагина есть и скиллы — `brainstorm`, `grill`, `minimal-diff`, `debug-loop`, `prototype`,
`page-screenshot`, `economy`, `summarizing-mr-links`. В меню `/` их нет: их зовут тимлид
и роли, когда наступает нужный момент.

## ⬆️ Обновление

То, что setup сгенерировал в проекте, вместе с плагином не обновляется. После обновления
плагина запусти `/beerpowers:update`: он перенесёт новые блоки движка и свежие копии скриптов,
не трогая проектный текст. Что изменилось от версии к версии и нужен ли `update`, написано
в [`CHANGELOG.md`](CHANGELOG.md). Проект, собранный предшественником — qtim, `update` тоже
переводит.
