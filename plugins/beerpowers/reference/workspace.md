# Контракт движка с проектом: `workspace.json`, маркеры, копии

> Generic reference плагина. Читает team-lead при `/beerpowers:setup`, `/beerpowers:update`,
> `/beerpowers:doctor`; на этот контракт опираются хуки плагина и скрипты `templates/bin/`.
> Ролям не нужен: им хватает charter.

Здесь — всё, что движок знает о проекте помимо charter: раскладка каталогов, параметры, git-настройки, включённые
барьеры, границы engine-блоков в сгенерированном тексте и правило копий. Формат меняется только
синхронно с потребителями: `setup` (пишет), `update` (сливает), `doctor` (сверяет), хуки
`hooks/*.sh` и скрипты `templates/bin/*` (читают).

## `.claude/workspace.json`

Под версией, общий для всех машин: в нём нет абсолютных путей и ничего личного. Все пути —
относительно корня workspace (каталога, где лежит `.claude/`), прямым слэшем.

```json
{
  "beerpowers": "2.0.0",
  "ui": true,
  "viewports": [
    { "name": "mobile", "width": 375, "height": 667, "mobile": true },
    { "name": "tablet", "width": 768, "height": 1024, "mobile": true },
    { "name": "desktop", "width": 1280, "height": 720 }
  ],
  "barriers": {
    "guard-push": true,
    "guard-kill": true,
    "guard-comments": true,
    "guard-commit-split": true
  },
  "comments": {
    "excludeDirs": ["projects/shop-frontend/app/api"]
  }
}
```

| Ключ | Смысл | Обязателен | Дефолт при отсутствии |
|---|---|---|---|
| `beerpowers` | версия плагина, которой записаны копии `bin/` и хуков под стек | да | — (`doctor`: fail) |
| `ui` | у проекта есть веб-интерфейс, который роли проверяют в браузере: от него зависят правила браузера и скриншотов | нет | `false` |
| `viewports` | ширины, на которых роли проверяют и снимают экраны: по записи на диапазон вёрстки проекта, `{name, width, height, mobile}`; имена и ширины не повторяются. Читают `tester`, `reviewer`, `front` и `cdp-screenshot.mjs` (поле сценария `viewport`, режим `--viewports`) | нет | `mobile` 375×667 с эмуляцией устройства, `desktop` 1440×900 |
| `barriers` | включённые барьеры; `guard-agent-memory` не выключается и в списке не стоит | нет | все `true` |
| `comments.excludeDirs` | каталоги сгенерированного кода, который лежит в git, — `guard-comments` не смотрит в них строки; путём от корня workspace, `projects/<репо>/<путь>`: запись действует только в своём репозитории и в его рабочих деревьях | нет | `[]` |
| `tests` | параллельный полный прогон тестов и мутационные пробы: лимит процессов машины `slots` и прогон каждого репозитория `repos.<репо>` — команда, маски файлов, режим, переменные воркера, подготовка, `mutate` — команда мутанта с фильтром и что копия дерева берёт из базы. Схема и примеры — [`parallel-tests.md`](parallel-tests.md) и [`mutants.md`](mutants.md); читают `parallel-tests.mjs` и `mutants.mjs` | нет | раздела нет — полный прогон по форме `memory/commands/<скоуп>.md`; нет `mutate` — пробы руками |

**«Обязателен» значит: `workspace-check` падает, если ключа нет.** Скрипты при этом идут
на дефолте из таблицы — отсутствующий ключ не ломает работу, но и не проходит проверку.

**Каталоги — константы движка, а не ключи.** Репозитории кода — `projects/<имя>/`, рабочие
деревья задач — `worktrees/<КОД>/<имя-репо>/`, папки задач — `memory/tasks/<КОД>/`; пути от корня
workspace. Ключ стоил бы каждому вызову хука чтения файла: на Windows это около 50 мс на ключ,
а барьеры срабатывают на каждой команде `Bash`. Проекту другая раскладка не нужна.
Имена репозиториев — `[A-Za-z0-9_.-]`; репозиторий с другим именем shell-скрипты пропускают,
`workspace-check` его называет.

**Код всегда лежит в `projects/<имя>/`, даже если репозиторий один.** Корень workspace —
отдельный репозиторий конфигурации команды и памяти; `projects/` и `worktrees/` стоят
в его `.gitignore` — `setup` дописывает строки, `workspace-check` проверяет. Так рабочие деревья
и артефакты задач не попадают в историю продукта, а конфиг команды — в репозиторий продукта.

**Список репозиториев не хранится — он получается обходом:** каждый каталог
`projects/<имя>/`, в котором есть `.git` (каталог или файл), — репозиторий с именем
`<имя>` и путём `projects/<имя>`. Список, записанный в файл, устаревает молча при первом
новом клоне; обход — нет.

**CLAUDE.md вложенных репозиториев роли не читают.** Claude Code подгружает такой файл сам,
как только роль открыла файл в этом каталоге, и он молча подменяет факты памяти. Поэтому
`CLAUDE.md` и `.claude/CLAUDE.md` каждого репозитория в `projects/` и каждого рабочего
дерева закрыты маской `claudeMdExcludes` в `settings.json` — исключений нет; сторожит
`workspace-check`.

**Viewports — из брейкпоинтов проекта, а не из привычки.** Вёрстка переключается на своих
брейкпоинтах: у одного проекта нет мобильной версии, у другого есть ещё планшет и широкий
экран. Поэтому список — одна запись на каждый диапазон между брейкпоинтами, которые проект
реально поддерживает, а не стандартная пара. Ширина записи — нижняя граница диапазона: на ней
вёрстка этого вида теснее всего, и переполнение видно первым. У самого узкого диапазона —
наименьшая поддерживаемая ширина (обычно 360 или 375), у самого широкого — ширина макета,
если она известна. `mobile: true` — диапазоны, рассчитанные на касание.

**Высота — типовая по ширине, не из проекта.** У фрейма макета фиксированной высоты нет, в коде
её тоже нет. Высота задаёт только окно прогона: что видно без прокрутки, где срабатывают `vh`,
`sticky` и модалки. Берётся самая низкая из популярных у этой ширины — на ней кнопка под
сгибом и модалка выше окна видны первыми; размеры — экран целиком в CSS-пикселях, как в эмуляции
устройств DevTools:

| Ширина | Высота | Устройства |
|---|---|---|
| 360 | 640 | телефоны Android |
| 375 | 667 | iPhone 6/7/8, SE |
| 390 | 844 | iPhone 12–14 |
| 768 | 1024 | iPad вертикально |
| 1024 | 768 | iPad горизонтально, старые ноутбуки |
| 1280 | 720 | ноутбуки HD |
| 1366 | 768 | массовые ноутбуки |
| 1440 | 900 | MacBook Air 13″, мониторы 1440×900 |
| 1536 | 864 | ноутбуки Full HD с масштабом 125 % |
| 1920 | 1080 | Full HD |

Ширины нет в таблице — высота ближайшей меньшей ширины. Высоту не спрашивают; в плане setup она
стоит с пометкой «типовая».

Список собирает `setup` (Discovery: `screens` в конфиге Tailwind, `--breakpoint-*` в CSS
Tailwind 4, брейкпоинты UI-кита, SCSS-переменные, `@media` глобальных стилей) и показывает
пользователю вместе с файлом-источником. `/beerpowers:onboard` сверяет его с кодом повторно
и называет расхождение. Ширина — часть имени скриншота (`<роль>-<экран>-<ширина>.png`), поэтому
две записи одной ширины — фатальная ошибка.

### Чтение из скриптов

Скрипты `templates/bin/` читают параметры через `node` — он нужен `workspace-check.mjs`
и `cdp-screenshot.mjs` и есть на обеих платформах команды. Shell-скрипты подключают общий помощник
рядом с собой:

```sh
self_dir=$(cd -- "$(dirname -- "$0")" && pwd)
. "$self_dir/lib/workspace.sh"
ws_root            # корень workspace: WORKSPACE_ROOT или каталог над .claude/
ws_get ui          # значение ключа с дефолтом из таблицы выше
ws_repos           # строки «<имя>\t<путь от корня>» по правилу обхода
```

Разбор один — `lib/workspace.mjs` (дефолты, типы, обход); `workspace.sh` — транспорт к нему,
второй копии дефолтов нет. Массив `ws_get` печатает по элементу на строку, вложенный ключ
адресуется точкой (`barriers.guard-push`, `comments.excludeDirs`).

### Точки расширения рабочих деревьев

Зависимости по lock-файлу `worktree-add` ставит сам. Проектная работа вокруг worktree
(тестовая база, сервисы под дерево) — не в копиях, а в двух проектных скриптах без шапки,
которые копии зовут, если файл есть и исполняем:

| Скрипт проекта | Кто зовёт и когда | Аргументы |
|---|---|---|
| `.claude/bin/worktree-setup` | `worktree-add` — после создания дерева, копирования env и установки зависимостей | `<КОД> <имя-репо> <абсолютный путь worktree>`, за ними — всё, что стоит после `--` в вызове `worktree-add` (а туда — после `--` в `/beerpowers:task-start`); `WORKSPACE_ROOT` в окружении |
| `.claude/bin/worktree-teardown` | `workspace-clean … --apply` — после всех проверок, до удаления | те же |

Ненулевой код — скрипт плагина падает; у teardown дерево тогда не удаляется. Teardown обязан
быть идемпотентным: повтор после сбоя — штатный ход. Файл есть, но не исполняем —
предупреждение и пропуск.

Сухой прогон `workspace-clean worktree <КОД>` (без `--apply`) зовёт teardown с последним
аргументом `--dry-run`, только если в его шапке есть строка `# supports: --dry-run`: такой
teardown печатает, что удалил бы (имя тестовой базы, контейнер), и ничего не меняет. Без строки
teardown только называется — человек, одобряющий `--apply`, не видит, что тот снесёт.

`WORKSPACE_ROOT` переопределяет корень — так скрипт проверяют на одноразовой фикстуре.

### Чтение из хуков

Хуки плагина `node` не требуют: флаг барьера читается `sed`'ом по строке
`"<имя барьера>": true|false`. Поэтому `barriers` пишется по ключу на строку, как в примере
выше. Нет `workspace.json` — действуют дефолты. Нет `.claude/team-charter.md` в
`$CLAUDE_PROJECT_DIR` — хук молча пропускает всё: барьеры действуют только в проектах
с командой.

## `.claude/git-settings.json` и `.claude/git-settings.local.json`

Git-настройки — отдельно от `workspace.json`, двумя файлами по тому же принципу, что
`settings.json` и `settings.local.json`. Механика, которую они настраивают, — `git-flow.md`.

```json
// .claude/git-settings.json — под версией, общий для команды
{
  "standArchive": false,
  "removeSourceBranch": true,
  "repos": {
    "shop-backend": "main-default",
    "shop-frontend": "dev-default"
  }
}
```

```json
// .claude/git-settings.local.json — под gitignore, личный
{
  "reviewers": {
    "shop-backend": ["ivanov"],
    "shop-frontend": []
  }
}
```

| Ключ | Файл | Смысл | Дефолт при отсутствии |
|---|---|---|---|
| `repos.<репо>` | общий | профиль репозитория: `main-default` · `dev-default` · `custom` | `main-default`; `workspace-check` называет репозиторий без профиля |
| `standArchive` | общий | архивировать прежний стенд при пересборке | `false` |
| `removeSourceBranch` | общий | удалять ветку задачи после мержа MR | `true` |
| `reviewers.<репо>` | личный | логины ревьюеров MR, без `@`; `[]` — не назначать никого | репозитория нет — team-lead спрашивает, а не подставляет |

**Хранится только то, чего git сказать не может.** Ветка по умолчанию берётся с сервера
(`git ls-remote --symref origin HEAD`), цель выпуска `dev-default` — та из `master`/`main`, что
есть на `origin`, хостинг — по адресу `origin`, assignee MR — владелец токена API. Записанная
копия любого из этих значений расходилась бы с хостингом молча. Базу задачи, если она
не по профилю, держит `memory/tasks/<КОД>/git-flow.md`.

Разбор — `lib/git.mjs`: его импортируют `.mjs`-скрипты, а shell-скрипты зовут
`node .claude/bin/lib/git.mjs resolve|merged|protected <корень> <репо> …`. Профиль при setup
предлагает `detect` того же модуля — его setup зовёт из каталога плагина, до копирования
скриптов: ветка по умолчанию и ветки `master`/`main`/`dev` у сервера, последние 10 коммитов
первой линии ветки выпуска, предложение профиля с основанием.

## Engine-блоки в сгенерированном тексте

Charter, `team-lead.md` и агенты состоят из двух видов текста: **engine** — правила движка,
одинаковые для любого проекта, и **проектный** — всё остальное. Граница стоит маркерами:

```markdown
<!-- beerpowers:engine <имя-блока> -->
…текст шаблона дословно…
<!-- /beerpowers:engine -->
```

- Имя блока — латиница, цифры и дефис, уникально внутри файла.
- Внутри engine-блока **нет плейсхолдеров `{{…}}`** и нет проектных литералов: путей,
  имён репозиториев, команд сборки. Каталоги движка — константы (`memory/tasks/<КОД>/`),
  проектным литералом они не считаются; проектная форма команды — указателем на файл памяти
  (`memory/commands/<скоуп>.md`). Поэтому блок в проекте байт в байт равен блоку шаблона,
  и `update` сливает его заменой, а не суждением.
- Плейсхолдеры живут только вне блоков: `setup` подставляет их один раз, дальше это текст
  проекта, `update` его не трогает.
- Вложенных блоков нет. Проектный текст внутри engine-блока — нарушение: его перезапишет
  первый же `update`.
- **Условный блок** несёт в маркере условие: `<!-- beerpowers:engine self-check if=ui:true -->`.
  Условие — `<ключ>:<значение>` по `.claude/workspace.json`, для булевых ключей — `ui:true`.
  `setup` вписывает блок, только если условие выполнено; `update` считает отсутствие
  такого блока нормой при невыполненном условии и добавляет его, когда условие стало
  выполняться. Блок без `if=` обязателен.

**Слияние в `update`:**

| В проекте | В шаблоне текущей версии | Действие |
|---|---|---|
| блок есть, текст равен шаблону прошлой версии | блок есть | заменить на текущий |
| блок есть, текст отличается от шаблона прошлой версии | блок есть | конфликт: показать оба текста, спросить; молча не перезаписывать |
| блок есть | блока нет | удалить блок вместе с маркерами — по записи в `migrations.md`, иначе спросить |
| блока нет | блок есть | добавить по месту, которое называет запись в `migrations.md`; записи нет — спросить, куда |

Шаблон прошлой версии берётся из кеша плагина той версии, если он есть, иначе — из описания
в `migrations.md`; версия проекта равна версии плагина — шаблоном прошлой служит текущий
(расхождение тогда — правка руками, конфликт); нет ни кеша, ни описания — любое расхождение
считается конфликтом.

## Копии файлов плагина в проекте

Скрипты `templates/bin/*` и хуки под стек `templates/hooks/*` копируются `setup`'ом
в `.claude/bin/` и `.claude/hooks/`. Вызываются они литеральным относительным путём
(`.claude/bin/worktree-add`), и правило `allow` в `settings.json` одно на все машины: путь
к кешу плагина содержит версию и различается между машинами.

**Шапка копии** — вторая строка файла: после shebang у скриптов и хуков, после строки-названия
у вспомогательных файлов без shebang (`lib/make-shim.mk`); у копий reference — первая. В шаблоне
так и записана:

```
# generated by beerpowers v{{BEERPOWERS_VERSION}} — не править: обновляет /beerpowers:update
```

Для `.mjs` — то же с `//`. `setup` и `update` подставляют версию плагина; больше
в копии ничего не меняется.

**Сверка в `doctor`:** шаблон с подставленной версией из `workspace.json` побайтно равен
копии. Не равен — либо копию правили руками (покажи дифф, предложи `update`), либо копия
из другой версии (назови обе). Проектный скрипт без шапки — не копия, `doctor` его
не сверяет.

**Проектное для копии живёт рядом, а не в ней.** Хуку `quality-reminder` нужны гейты
проекта по типу файла — они лежат в `.claude/quality-gates.txt` (строка `<маска case> <текст
гейта>`, первая подошедшая маска выигрывает, `#` — комментарий; формат — шапка самого хука).
Файл пишет `setup`, правит проект, `update` его не трогает.

**Правка копии руками запрещена:** `update` перезапишет её без вопроса и назовёт файл
в отчёте. Нужна другая логика — проектный скрипт рядом под своим именем, без шапки.

### Копии reference

Charter, `team-lead.md` и агенты ссылаются на механику, которую должна уметь открыть роль:
`hooks.md`, `tasks-layout.md`, `worktrees.md`, `git-flow.md`. Роль не знает, где лежит кеш
плагина, поэтому эти четыре файла `setup` копирует в `.claude/reference/` проекта. Шаблоном
служит сам файл `reference/<имя>.md` плагина: копия — это шапка первой строкой плюс файл
без изменений:

```
<!-- generated by beerpowers v<версия> — не править: обновляет /beerpowers:update -->
```

Поэтому в этих четырёх файлах ссылки — только на соседей по каталогу (`hooks.md`)
и на файлы проекта путём от корня (`memory/MEMORY.md`); команды плагина называются
вызовом `/beerpowers:<команда>`, а не путём к файлу. `doctor` сверяет копию без первой строки
с файлом плагина.

## Адаптер записи в трекер

Запись в трекер устроена в два слоя. Общий — для любого трекера: действия, подтверждение
черновиком, порядок предложения задачи (`team-lead.md`, блок `tracker-write`), шаблон задачи
и бага (скил `tracker-task`), вход человека `/beerpowers:tracker`. Свой у каждого трекера —
адаптер: копия `templates/bin/<трекер>-write.mjs` в `.claude/bin/` рядом со скриптом чтения
`.claude/bin/<трекер>`. Сейчас адаптер один — `yandex-tracker-write.mjs`. Новый трекер — новый
адаптер по этому контракту, а не правка блока, скила и команды.

| Что | Контракт |
|---|---|
| Команды | `template task\|bug`, `check <черновик>`, `create <черновик>`, `edit <КОД> <черновик>`, `comment <КОД> <файл>`, `links <КОД>`, `link <КОД> <вид> <КОД2> [--replace]`, `unlink <КОД> <КОД2>`, `transitions <КОД>`, `move <КОД> <переход> [--resolution …] [--field …] [--comment <файл>]`, `attach <КОД> <файл>…`, `detach <КОД> <id>`, `--help` |
| Вид связи | `зависит-от`, `блокирует`, `связана`, `подзадача-для`, `родитель-для` — с точки зрения первого `<КОД>` |
| Черновик | обычный markdown: `# название`, таблица `\| Поле \| Значение \|` (поля — скил `tracker-task`), строка `---`, описание; картинка `![подпись](путь к файлу)` и файл `[имя](путь к файлу)` — локальным путём от каталога черновика; последняя строка — подпись `© Клод Клодыч <отчество по модели>` |
| Разметка трекера | только внутри адаптера: он загружает локальные файлы, переводит ссылки и подпись при отправке; уже стоящую разметку своего трекера (описание, взятое из задачи для правки) пропускает как есть |
| Проверка | `create` и `edit` сначала гоняют `check` и без чистой проверки ничего не отправляют; отказ — код 1 и строки `ошибка: …` в stderr, замечание — `предупреждение: …` |
| Связь пары | `link` не меняет вид уже стоящей связи без `--replace`; `create` и `edit` ставят связи из поля «Связи» черновика и заменяют вид, уже стоящий на этой паре; связи вне поля не трогают |
| Доступ | токен и организация — по тем же источникам, что у скрипта чтения; токен не печатается; отказ в праве записи — отдельным сообщением, что сделать человеку |

Разрешения — по командам, а не на весь скрипт: команды, которые идут без подтверждения
(`template`, `check`, `comment`, `links`, `link`, `unlink`, `transitions`), — в `allow`, остальные —
в `permissions.ask` (setup 4.3).
