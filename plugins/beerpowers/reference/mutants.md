# Мутационные пробы — `mutants.mjs`

> Generic reference плагина. Читает team-lead при `/beerpowers:setup` (заготовка
> `tests.repos.<репо>.mutate` в `.claude/workspace.json`), `/beerpowers:doctor`
> и `/beerpowers:update`. Ролям хватает charter («Число в отчёте…», пункт «Мутационные пробы —
> через `mutants.mjs`») и `--help` копии `.claude/bin/mutants.mjs`. Слоты машины и переменные
> воркера — общие с параллельным прогоном: [`parallel-tests.md`](parallel-tests.md).

Мутационная проба доказывает, что тест сторожит критерий: прод-код ломается одной строкой,
и тест обязан покраснеть. Когда каждая задача пишет обвязку проб заново, они идут по одному
мутанту в общем рабочем дереве, каждый гоняет целые тестовые классы, а после правки тестов
весь набор перезапускается. Замер на проекте с PHPUnit: 39 мутантов по 143 теста двух классов,
набор прогнан дважды — 34 минуты; 54 мутанта и повтор всего набора — около 20 минут.

Инструмент снимает все три причины: мутанты идут параллельно в изолированных копиях дерева,
каждый гоняет только свой фильтр с остановкой на первом падении, а повторный прогон берёт
неизменившиеся из кеша.

## Настройки — `tests.repos.<репо>.mutate`

```json
"shop-backend": {
  "command": "…{files}…",
  "files": ["tests/**/*Test.php"],
  "env": { "DB_DATABASE": "shop_w{i}_test", "TEST_TOKEN": "{i}", "TMP": "{tmp}", "TEMP": "{tmp}" },
  "prepare": "sh \"{root}/.claude/bin/testdb-ensure\"",
  "mutate": {
    "command": "php vendor/bin/phpunit -c phpunit.xml --no-coverage --colors=never --stop-on-failure {filter}",
    "check": "php -l \"{file}\"",
    "link": ["vendor"],
    "copy": [".env.testing"],
    "timeout": 600
  }
}
```

| Ключ | Смысл | Обязателен | Дефолт |
|---|---|---|---|
| `mutate.command` | прогон мутанта; `{filter}` — аргументы фильтра из определения мутанта; остановка на первом падении — флагом раннера (`--stop-on-failure`, `--bail`) | да | — |
| `mutate.check` | проверка файла после замены, `{file}` — его абсолютный путь (синтаксис: `php -l`, `node --check`); не прошла — «ошибка применения», а не «убит» | нет | — |
| `mutate.link` | каталоги базы, которые копия получает ссылкой (на Windows — junction): `vendor`, `node_modules`; в `git status`, `add` и `clean` копии они не участвуют — шаблон `vendor/` в `.gitignore` симлинк не ловит | нет | `[]` |
| `mutate.copy` | файлы базы, которые копия получает копией: env-файлы, которых нет в git; отслеживаемый файл здесь — отказ, копия дерева получает его и так | нет | `[]` |
| `mutate.timeout` | предел одного прогона, секунды; дольше — дерево процесса гасится, мутант «убит (таймаут)» | нет | `600` |

`env` и `prepare` записи — те же, что у параллельного прогона: `{i}` — слот копии, `{dir}` —
её путь. Мутант гоняется одним процессом на слот, поэтому `{i}` есть у переменных и в режиме
`native`; раннеру с собственной параллелью нужен флаг одного процесса (Jest `--runInBand`) —
тогда `JEST_WORKER_ID=1` переводится в слот копии тем же кодом настройки тестов, что
в `parallel-tests.md`.

## Файл мутантов

Лежит во временном каталоге роли, а не в `memory/tasks/<КОД>/`: список файлов папки задачи
закрытый, и в память идёт только таблица, которую печатает инструмент.

```json
{
  "repo": "shop-backend",
  "task": "SHOP-12",
  "filter": "--filter CoordinatesRuleTest tests/Unit/Rules/CoordinatesRuleTest.php",
  "tests": ["tests/Unit/Rules/CoordinatesRuleTest.php:31"],
  "mutants": [
    {
      "id": "M1",
      "criterion": "широта вне [-90, 90] отклоняется",
      "file": "app/Rules/Coordinates.php",
      "find": "abs((float) $value) <= $limit",
      "replace": "abs((float) $value) < $limit",
      "what": "граница диапазона включительно → строго"
    }
  ]
}
```

- `repo`, `task`, `filter`, `tests` сверху — значения по умолчанию, у мутанта — свои.
- `find` — точная строка, **ровно одно вхождение** в файле: иначе «ошибка применения» без прогона.
  Мутант, попавший не в ту строку, мерит не тот код. Многострочный фрагмент — с `\n` в JSON.
- `filter` — аргументы, которые встают на место `{filter}`: самый узкий фильтр, который
  ещё ловит мутант, — один тест или один класс, а не каталог.
- `tests` — тестовые файлы фильтра (`файл:строка` — строка идёт в таблицу): их содержимое
  входит в хеш мутанта, правка теста перезапускает только мутанты с этим файлом.
- `id` — метка пробы `M<N>` из таблицы меток charter; `criterion` — критерий приёмки или метка
  находки; `what` — одна фраза «что сломано» для колонки «Мутация».

## Как идёт прогон

- **Копия на слот.** `git worktree add --detach` в `.claude/.cache/mutants/<репо>-s<слот>`
  на коммите базы (`projects/<репо>` или `worktrees/<КОД>/<репо>`) плюс снимок её
  незакоммиченных правок одним служебным коммитом в копии — тесты задачи до коммита часто
  ещё не дошли. Копии переживают прогон и переиспользуются: следующий прогон сбрасывает копию
  на новый коммит базы. Пока слот держит процесс, копия его — номер слота уникален на машине.
- **Контроль.** На каждую пару «репозиторий, фильтр» — нулевой мутант: тот же фильтр без замены.
  Он обязан быть зелёным, иначе мутанты этого фильтра «недействительны»: красный тест
  на неиспорченном коде убивает любого мутанта, и проба мерила бы себя (charter, «Инструмент
  замера — часть утверждения»). Красный контроль не кешируется.
- **Мутант.** Замена → `mutate.check` → команда с фильтром → откат файла `git checkout` →
  `git status --porcelain` копии обязан быть пуст. Тест оставил файлы — копия восстанавливается
  (`checkout`, `clean -fd` без `-x` и без путей `link` и `copy`: ссылки и env остаются), запись в логе
  мутанта; не восстановилась — прогон останавливается.
- **Кеш** — `<мутанты>.cache.json` рядом с файлом мутантов. Ключ — хеш определения мутанта,
  команды, переменных, мутируемого файла и тестовых файлов. Правка другого прод-файла ключ
  не меняет: после фикса, задевшего путь мутанта не в его файле, — `--force`.
- **Вывод.** Строка `done` на контроль и мутант, затем таблица в форме таблицы мутаций
  `test-cases.md` — колонки «Критерий или находка · Тест · Мутация · На ветке · На мутанте ·
  Статус» (та же таблица — файлом `<мутанты>.table.md`), `TOTAL mutants=… killed=… survived=…
  errors=… invalid=… skipped=… cached=…` и последней строкой `CODE=`. Код 0 — все мутанты убиты;
  1 — есть выжившие, ошибки применения, недействительные или не прогнанные (`--only`); 2 —
  ошибка настроек или файла мутантов. Логи прогонов — `<мутанты>.runs/<id>.log`.
- **Уборка.** `--clean` убирает копии, чей слот никто не держит: сначала снимает ссылки, потом
  `git worktree remove` — удаление по ссылке снесло бы `vendor` базы.

## Ограничения

- **Браузерные сценарии.** Мутацию, которую ловит только прогон в браузере, инструмент
  не гоняет: dev-сервер обслуживает своё рабочее дерево, а не копию мутанта. Такая проба —
  руками в дереве задачи, по одной, с откатом и проверкой `git status` после каждой.
- **Хеш видит только мутируемый файл и тесты фильтра.** Остальной код дерева в ключ не входит.
- **Одна замена в одном файле на мутант.** Поломку из правок в двух файлах инструмент
  не выражает; две правки в одном файле — одним `find`, охватывающим обе.
