# Git: ветки, коммиты, push, MR, стенды

Единственное место, где описана работа с git. Читает тот, кто коммитит и заводит MR, —
team-lead: роли git не пишут (charter, «Git — роли не пишут»), а базу диффа берут из ответа
`node .claude/bin/git-base.mjs <репо> <КОД>`. Остальные файлы на этот ссылаются и правил
не повторяют.

Настройки — два файла. `.claude/git-settings.json` лежит в git и общий для команды: профиль
каждого репозитория, `standArchive`, `removeSourceBranch`. `.claude/git-settings.local.json`
под gitignore и личный: ревьюеры MR по репозиторию. Формы команд проекта и свой флоу
(`custom`) — `memory/commands/git.md`. Контракт файлов настроек — `workspace.md` плагина.

## Профиль репозитория

| Профиль | Ветка задачи — от | MR — в | Выпуск |
|---|---|---|---|
| `main-default` | ветки по умолчанию на сервере | туда же | мерж MR и есть выкатка: перемоткой, жмёт человек |
| `dev-default` | `dev` — ветки по умолчанию на сервере | `dev` | в `master`/`main`: плановый — merge-коммит `dev`, срочный и фикс — cherry-pick `-x` |
| `custom` | по `memory/commands/git.md`, раздел репозитория | там же | там же |

**Имена веток не хранятся — их узнают у сервера.** Ветка по умолчанию — ответ
`git ls-remote --symref origin HEAD`, а не локальный `origin/HEAD`: тот записан при клонировании
и сам не обновляется, когда ветку на хостинге меняют. Цель выпуска `dev-default` — та из
`master` и `main`, что есть на `origin`. Есть обе — это не повод выбирать: у репозитория свой
флоу (`custom`) или лишняя ветка, решает человек. Всё это считает `git-base.mjs`; руками
вычислять не нужно.

Репозитория нет в `git-settings.json` — он идёт как `main-default`, а `workspace-check`
называет пропуск.

## База задачи

Ветка задачи называется кодом задачи — `<КОД>`. Её база — по профилю, если задача не говорит
иного. Иное записывается в `memory/tasks/<КОД>/git-flow.md` строкой репозитория (раскладка —
`tasks-layout.md`): ветка задачи-предшественника, релизная ветка, а в `custom` база
записывается всегда — по `memory/commands/git.md`. `git-base.mjs` читает её оттуда.

**Без явной базы её выбирает team-lead — по смыслу, не по конфликтам.** Задача зависит
от невлитой фичи, если ей нужен её код или контракт: это видно по постановке, связям в трекере,
«Зависимостям» соседних задач. Зависит — база её ветка, и в `git-flow.md` задачи пишутся
и база, и зависимость. Не зависит — база по профилю. Возможные конфликты критерием не служат:
от того, что две задачи задевают один файл, вторая от первой не зависит. Выбранная база
и причина называются пользователю одной строкой до того, как заводятся ветки.

**Ветка задачи от ветки задачи** — цепочка: MR целится в родителя, иначе в дифф попадает вся
его работа, и порядок мержа обязателен — сначала родитель. Хостинг цель MR сам не переставляет:
после мержа родителя цель переставляется **руками**, а ветка переносится ребейзом.

**Базу сверяют трижды:** до первого вызова роли, перед push с MR и при каждом возврате
к задаче, пока MR ждёт ревью. Цель ушла вперёд — ветка переносится ребейзом и отправляется
`push --force-with-lease`. Ребейз переносит правку, но не вердикт: `APPROVED`, выданный
на прежней базе, силы не имеет, гейты гоняются заново.

Цель могут не только сдвинуть, но и **переписать** — после силового push'а прежняя база
исчезает из истории, и ветка показывает отставание на десятки коммитов. Признак —
`git -C <репо> merge-base --is-ancestor <прежняя база> origin/<цель>` с ненулевым кодом;
перенос тогда только формой `rebase --onto origin/<цель> <прежняя база> <ветка>`, обычный
`rebase` наберёт дубликаты. Сверка не с той целью — ошибка, а не упрощение: дифф при этом
чистый, и отставание по нему не видно.

## Коммиты

Коммитит team-lead. Коммит — `type(<КОД>): описание`: описание по-русски, в повелительном
наклонении («добавь фильтр по дате»), `type` — `feat`, `fix`, `refactor`, `style`, `docs`
или `chore`. Свой набор типов или своя форма у компании — `memory/commands/git.md`, он
перекрывает этот абзац. Гейт между вердиктом и слиянием ставит человек.

**Коммиты промежуточные, после каждого этапа** — по коммиту на каждый завершённый заход
исполнителя, включая заходы, которые `reviewer` завернул: `reviewer` читает инкремент `HEAD~1`,
рестарт сессии опирается на `git log`. Перед **каждым** коммитом — линт по charter, «Линт
в конце задачи».

**В MR уезжает один коммит на задачу и один коммит на раунд правок.** Граница режимов —
момент запроса ревью у человека:

| Этап | Коммиты | Схлопывание |
|---|---|---|
| работа команды до `APPROVED` финального прохода | много, по заходам | нет |
| закрытие задачи, до первого push | **один** `type(<КОД>): суть` | всё до `merge-base` с целью MR |
| правки по замечаниям MR, пока идёт раунд | много, по заходам | нет |
| перед обновлением MR | **один** `fix(<КОД>): …` на раунд | новые коммиты до головы `origin/<КОД>`, не до `merge-base` |

Отправленная история заморожена: `--amend` и голый `--force` после запроса ревью не делаются —
треды ревью привязаны к строкам конкретного диффа. Зачем схлопывать: в целевую ветку иначе
уезжают завёрнутые состояния — ловушки для `bisect` и `blame`; cherry-pick `-x` одного коммита
дешевле двенадцати; проверка «влита ли ветка» сравнивает патчи, и схлопывание на хостинге
дало бы ложно «невлитые» коммиты. Контекст фиксов остаётся в `review-report.md` и `bug-log.md`.

**`memory/tasks/**` коммитится отдельно от всего остального** — ни с кодом, ни с конфигурацией,
ни с долгоживущей памятью. Причина — срок жизни: историю по этому пути однажды вычистят
`git filter-repo --path memory/tasks --invert-paths`, и смешанные коммиты останутся
выпотрошенными наполовину. Барьер — `guard-commit-split`, если он включён.

**Артефакты коммитятся на границе этапа, а не после каждой правки** — после раннего ревью,
`tester`'а, финального ревью, правок по ревью MR: `memory/tasks/**` одним коммитом, долгоживущая
память и конфигурация (`memory/*.md`, `README.md`, `.claude/`) отдельным. Перед этим team-lead
сверяет `git status --short` по всему репозиторию workspace, добавляет поимённо только свои
файлы, чужие правки соседней сессии не трогает и называет в ответе.

## Push

**Push и MR делает team-lead.** Отправляется ветка задачи поимённо:
`git -C <репо> push -u origin <КОД>`.

| Куда | Можно |
|---|---|
| ветка по умолчанию, `master`/`main`, `dev` профиля `dev-default` | ничего — только через MR, вливает человек |
| ветка задачи, релизная, стенд | `push`, после ребейза — `--force-with-lease` |
| куда угодно | голый `--force`, `--all`, `--mirror`, удаление ветки — нельзя |

Барьер — `guard-push`, если он включён (`hooks.md`).

## MR

Хостинг — по адресу `origin` (`git -C <репо> remote get-url origin`). Assignee — владелец
токена API, то есть тот, кто ведёт сессию: он нигде не записывается. Ревьюеры — из
`.claude/git-settings.local.json`: репозитория там нет — спросить пользователя и предложить
записать ответ, а не подставлять наугад; `[]` — не назначать никого. Удалять ли ветку после
мержа — `removeSourceBranch` из `.claude/git-settings.json`.

**GitLab: MR заводится первым же push'ем ветки**, push-опциями: они доходят до сервера только
при реальной передаче ref, на уже отправленной ветке второго шанса нет. Барьер `guard-push`
блокирует первый push ветки задачи без `-o merge_request.create`. Входы собираются **до**
отправки: цель MR (`git-base.mjs`), assignee, ревьюеры, актуальность базы, текст описания,
работающий токен для второго шага.

```bash
git -C <репо> push -u origin <КОД> -o merge_request.create -o merge_request.target=<цель> \
  -o merge_request.title="<КОД>: <суть>" -o merge_request.description="<одна строка>"
```

Переносы строк в push-опциях git запрещает, поэтому push несёт однострочное описание, а полное
ставится вторым шагом через REST API — однострочное всё равно называет суть, чем проверено
и что не проверено.

**Токен API.** git ходит по HTTPS с personal access token, у которого есть scope `api`, — тот же
токен годится для API, его отдаёт git credential helper. Выборка токена и целевой запрос — одним
вызовом:

```bash
TOKEN=$(printf 'protocol=https\nhost=<хост>\n\n' | git credential fill | sed -n 's/^password=//p')
curl -s -X PUT -H "PRIVATE-TOKEN: $TOKEN" -H "Content-Type: application/json" \
  --data-binary "@<файл с JSON>" "https://<хост>/api/v4/projects/<группа%2Fпроект>/merge_requests/<iid>"
```

- путь проекта в URL — с `/`, закодированными как `%2F`, включая вложенные группы; значение
  токена в вывод не печатается;
- многострочное описание — JSON-файлом с `\n` и `--data-binary @файл`: `--data-urlencode` даёт `400`;
- `401` — токен без scope `api` или git ходит по SSH: тогда токен API отдельный, и где он лежит,
  записано в `memory/commands/git.md`;
- классификатор разрешений пропускает выборку токена, за которой сразу идёт целевой запрос;
  та же выборка вместе с пробами вокруг неё (`GET /api/v4/user`, `remote get-url`, `2>/dev/null`
  у helper'а) отклоняется как `[Credential Exploration]`. Отказ — не повод отдавать описание
  человеку: вызов собирается заново по форме выше;
- `glab` удобнее, если он авторизован **из оболочки агента**: токен в хранилище ОС виден
  интерактивному сеансу человека и не виден процессам агента — признак `No token found`
  при галочке в `glab auth status` у человека. Тогда — форма выше.

**GitHub: PR заводится сразу после первого push'а** командой `gh pr create` с целью
из `git-base.mjs` и полным описанием в `--body-file`. Входы — те же и тоже до отправки.

`memory/commands/git.md` держит только то, чего нет в этом файле, в `git-settings.json`
и у сервера: где токен API, если git ходит по SSH; флоу `custom`; соглашения компании сверх
этого файла.

**Описание MR обязательно, стиль caveman (full).** Первым разделом — «Для выкладки
на стенд»: переменные окружения, команды на сервере, миграции с данными, перезапуск воркеров,
ручные действия; делать нечего — так и написано одной строкой. Дальше: зачем, что сделано,
чем проверено (строка `tester`'а о тестах — charter, «Тестом называется…»), что осталось
непроверенным, отдельно — правки за пределами объёма задачи. Сохранить текст в `.md` и попросить
человека вставить руками — **провал**, а не рабочий путь. Ответ, в котором заведены MR,
заканчивается сводкой ссылок по скиллу `beerpowers:summarizing-mr-links`.

## Перед MR — git-шаги закрытия задачи

Порядок всего закрытия — `team-lead.md`, «Закрытие задачи»; git-шаги в нём — эти, сверху вниз:

1. **SHA-сверка ревью и push.** `git -C <репо> diff <коммит вердикта>..HEAD --stat` пуст;
   непуст — хвостовые коммиты перечислены и проревьюены по `HEAD~1` до push. Сверка идёт
   по деревьям, поэтому схлопывание следующего шага её не ломает — но делается до него.
2. **Схлопнуть в один коммит** `type(<КОД>): суть` до `merge-base` с целью MR. Повторный
   `diff <дерево вердикта>..HEAD` пуст. В раунде правок по MR — до головы отправленной ветки,
   один `fix(<КОД>): …` на раунд. Артефакты `memory/tasks/**` лежат в корне workspace, а не
   в репозитории кода, и в схлопывание не входят.
3. **Дифф без лишнего.** `git -C <репо> diff --name-only <база>..HEAD` против списка файлов
   design brief или постановки: файл вне объёма либо убирается, либо попадает в описание MR
   в раздел «правки за пределами объёма».
4. **База сверена с `origin`** и ветка перенесена ребейзом, если цель ушла; после переноса
   гейты заново.
5. **Описание MR** собрано по составу выше.

**Заход закончен — основной каталог репозитория возвращается на ветку по умолчанию.** MR заведён
или человек остановил работу — локальная ветка по умолчанию подтягивается до `origin`,
каталог переключается на неё:

```bash
git -C <репо> fetch origin <ветка по умолчанию>:<ветка по умолчанию>
git -C <репо> checkout <ветка по умолчанию>
```

Ветка в основном каталоге — признак занятости: на него опираются человек
и `/beerpowers:task-start`, который по чужой ветке уводит новую задачу в worktree. `fetch`
в такой форме идёт только перемоткой и откажет, если локальная ветка разошлась с сервером, —
тогда разобраться, а не перезаписывать. Незакоммиченное в каталоге — не переключать, назвать
человеку.

## Стенды

Стенд — ветка, на которую выкатывается работа **до** мержа, чтобы проверить её на тестовом
окружении. Профиль от стенда не зависит, и в настройках стенды не перечисляются: стенд называет
человек — «залей в dev».

**«Залить ветку в стенд»** — перебазировать стенд поверх ветки задачи и отправить. Мерж-коммитов
нет. Дерево пересборки — `worktrees/chore-<стенд>-rebuild/<имя-репо>`, заводится абсолютным
путём назначения: `git -C <репо> worktree add <путь>` считает относительный путь от `-C`.

```bash
git -C <дерево> checkout <стенд>
git -C <дерево> rebase <ветка задачи>
git -C <дерево> push --force-with-lease origin <стенд>
```

Если `origin/<стенд>` — предок нового стенда (стенд не нёс своих коммитов), push идёт без силы.
Стенд при этом перестаёт быть чистой суммой ветки по умолчанию и веток задач, и это нормально:
он одноразовый. Собирать стенд локально не нужно — его проверяет CI; гейты обязательны для веток
задач, а не для стенда.

**Коммиты стенда не пропадают молча.** Заливка ребейзом, выравнивание с `--skip` и пересборка
из веток переписывают стенд, и в каждом из этих путей коммит может выпасть незаметно. Перед
каждым push стенда с силой:

```bash
node .claude/bin/git-base.mjs --lost <дерево> origin/<стенд> HEAD
```

Скрипт печатает коммиты прежнего стенда, у которых в новом нет пары ни по патчу, ни по теме;
влитое в основную ветку пропажей не считается. Список не пуст — вслух человеку, с причиной
по каждому: влит в основную другой редакцией, задача снята, выпал по ошибке. Выпавший
по ошибке возвращается cherry-pick'ом в дерево пересборки, проверка повторяется. Барьер
`guard-push` делает ту же проверку на push с силой и отказывает один раз со списком: повтор
той же команды — только после ответа человека.

**В стенде только коммиты веток задач** — ни фиксов, ни «приведения к основной» поверх. Нашлась
проблема — чинится ветка, на стенд приезжает её коммит. Проверка перед push: тема каждого
коммита стенда сверх его базы есть в какой-то ветке задачи.

**Ветка уже на стенде, а в неё добавился коммит, — ребейз дорожает:** он останавливается
на каждом коммите стенда в тех же файлах и требует `--skip` на каждой копии коммитов самой ветки.
Альтернатива — cherry-pick нового коммита на вершину стенда: стенд не переписывается, push
обычный, конфликт — только у этого коммита; цена — копия с другим хешем, которая отпадёт при
следующей пересборке. Выбор между ними — за человеком. Разрешать конфликт ребейза версией
прежнего стенда можно **только для файлов, которых задача не касалась**: на своих это молча
затирает правку. Проверка результата — `git -C <дерево> diff <прежняя вершина стенда> HEAD --stat`
показывает ровно дифф заливаемого коммита, ничего сверх.

**Стенд разошёлся с основной веткой — сначала выравнивание, потом заливка.** Основная здесь —
ветка, от которой собран стенд: ветка по умолчанию, а для стенда релиза — релизная. Стенд несёт копии
коммитов, которые в основной ветке лежат в другой редакции, и `rebase <ветка задачи>` встаёт
на конфликтах не по задаче. Порядок, локально, без промежуточных push:

1. Стенд перебазируется на `origin/<основная>` — не на локальную, она может отставать.
   Коммиты, чей патч там уже есть, git выбрасывает сам.
2. На конфликтном коммите решается, копия это или своя работа: двойник ищется по теме
   (`git log origin/<основная> --grep=<КОД>`), патчи сравниваются `git patch-id --stable`,
   затем — есть ли добавленные строки в `origin/<основная>:<файл>`. Все на месте — копия
   устарела, `--skip`. Решение — по содержимому, не по заголовку.
3. Выровненный стенд равен `origin/<основная>` или несёт только свои коммиты; дальше — обычная
   заливка. Что ушло со стенда вместе с пропущенными копиями, называется пользователю —
   по выводу `git-base.mjs --lost`.

**Пересборка стенда из веток** — когда основная ушла вперёд и стенд проще собрать заново:

1. Состав — по кодам задач в `git log origin/<основная>..origin/<стенд>`; родитель ветки —
   ближайшая другая ветка-кандидат, являющаяся её предком (`merge-base --is-ancestor`). Ветки
   переносятся на свою базу (`git replay --onto` без checkout, при конфликте — обычный `rebase`),
   гейты — на вершинах, затем отдельными push'ами `--force-with-lease` без предварительного
   `fetch`: иначе lease сверит с уже обновлённой ссылкой.
2. Стенд собирается в дереве пересборки от вершины ветки-основания: по диапазону на ветку
   `git cherry-pick --empty=drop <родитель>..<ветка>` в прежнем порядке — уже применённые
   патчи отпадают сами.
3. **Сверка состава — до push, вслух пользователю.** Коды задач старого и нового стенда
   сравниваются командой; каждая задача, которой в новом нет, называется с причиной: влита
   в базу, снята решением или выпала. Сверка — по кодам в темах коммитов, а не `git cherry`:
   после пересборки хеши меняются у всех, и `cherry` показывает десятки ложных «пропаж».
   Коды не видят коммит без кода и выпавший коммит задачи, которая в стенде осталась, —
   их ловит `git-base.mjs --lost` (выше), он идёт следом.
4. **Новый стенд — одним push'ем** `--force-with-lease`: каждый push запускает пайплайн стенда.
   Старый стенд архивируется (`git push origin origin/<стенд>:refs/heads/archive/<стенд>-<дата>`),
   только если в `.claude/git-settings.json` стоит `"standArchive": true`; по умолчанию — нет.
5. **Дерево пересборки убирается сразу после push, в том же заходе:**
   `.claude/bin/workspace-clean worktree chore-<стенд>-rebuild --apply`. Скрипт снимает дерево,
   только если его вершина уже лежит в `origin/<стенд>`; push не прошёл — отказ, дерево остаётся
   для повтора.

## `main-default` — релизная ветка

Используется редко: когда задачу выпускают не одна, а пачкой. Имя релизной ветки называется
при старте задачи (`<КОД>@<релизная>` в `/beerpowers:task-start`) и применяется к тем
репозиториям, где такая ветка есть на `origin`; нет нигде — team-lead спрашивает, где её
завести. Не названо — команда не спрашивает: обычная задача. Имя пишется в `git-flow.md` задачи
строкой репозитория.

- Релизной ветки нет на `origin` — создать и отправить до ветки задачи: иначе база ветки —
  не то, во что целится MR.
- Хотфикс ушёл в основную — релизная перебазируется на неё и отправляется
  `--force-with-lease`. Этот ребейз переписывает базу всем веткам задач от релизной: их перенос —
  только `rebase --onto origin/<релизная> <прежняя голова> <ветка>`, и тот, кто переложил
  релизную, **сразу называет новую голову и прежнюю базу**. Вердикты на прежней базе аннулируются.
- Релиз собран — релизная перебазируется на основную, и человек вливает её MR перемоткой.
  Merge-коммита нет.
- Ручная проверка на стенде — работа человека; цикл `MR → ревью → правки → стенд → проверка`
  может повторяться, это штатный ход.

Цена: откат затрагивает весь релиз, а не одну задачу; ребейз релизной — ручная работа,
пропорциональная числу живых веток задач от неё.

## `dev-default` — выпуск

Ветки задач — всегда от `dev`, MR — в `dev`, вливает человек. Задача влита, когда её коммит
в `dev`. Фикс — такая же задача: ветка от `dev`, MR в `dev`, затем срочный выпуск.

**Плановый выпуск** — человек вливает `dev` в `master`/`main` MR'ом с merge-коммитом: перемотка
здесь не используется. Team-lead заводит этот MR по просьбе, но не вливает.

**Срочный выпуск и фикс** — cherry-pick коммита задачи в `master`/`main`. Путь отмечается
в `git-flow.md` задачи: «срочно» в колонке выпуска.

```bash
git -C <репо> fetch origin
git -C <репо> checkout -b <КОД>-release origin/<master|main>
git -C <репо> cherry-pick -x <коммит задачи в origin/dev>
git -C <репо> push -u origin <КОД>-release
```

MR из `<КОД>-release` — в `master`/`main`. Флаг `-x` дописывает `(cherry picked from commit …)`
и связывает два MR. Коммит задачи один — его и переносят; поэтому схлопывание до push
обязательно и здесь. Следующий плановый merge `dev` принесёт тот же патч второй раз, и git
сводит его без конфликта.

## `custom` — свой флоу проекта

Флоу репозитория описан в `memory/commands/git.md`, разделом с именем репозитория. Раздел
обязан назвать: от какой ветки задача и куда её MR; как работа уходит в прод; путь фикса;
ветки, закрытые для push. Всё, чего там нет, берётся из общих разделов этого файла.
`/beerpowers:task-start` для задачи в таком репозитории всегда пишет базу в `git-flow.md` задачи,
поэтому `git-base.mjs` и роли работают с ним так же, как с остальными.

## Где это держится механически

- `node .claude/bin/git-base.mjs <репо> [<КОД>]` — база, цель MR, цель выпуска и команда диффа.
- «Влита ли ветка» считается одной функцией `.claude/bin/lib/git.mjs` — по предкам коммита
  **или** по содержимому патча, против каждой цели: так видна и перемотка, и merge-коммит,
  и ребейз, и cherry-pick. Её зовут `tasks-status`, `workspace-clean`
  и `/beerpowers:worktrees-clear`.
- Барьер `guard-push` закрывает ветку по умолчанию и `master`/`main`, держит голый `--force`
  и первый push без MR на GitLab — `hooks.md`.
