# Параллельный прогон тестов — `parallel-tests.mjs`

> Generic reference плагина. Читает team-lead при `/beerpowers:setup` (заготовка раздела
> `tests` в `.claude/workspace.json`), `/beerpowers:doctor` и `/beerpowers:update`. Ролям
> хватает charter («Число в отчёте…», пункт «Полный прогон тестов репозитория…») и `--help`
> копии `.claude/bin/parallel-tests.mjs`.

Полный набор тестов веб-продукта упирается не в процессор, а в задержку: каждый запрос к базе
и поисковому индексу в контейнере — круг в доли миллисекунды, и процесс тестов большую часть
времени ждёт. Поэтому несколько процессов на одном наборе ускоряют прогон почти линейно,
пока процессор машины не занят весь. Замер на проекте с PHPUnit (2 329 тестов Unit и Feature,
Postgres и Elasticsearch в Docker): один процесс — 425 с, процессорное время PHP — 20% из них;
4 процесса — 106 с, 8 процессов — 60 с; три полных прогона по 8 процессов одновременно — 102 с
каждый, при 24 и больше процессах процессор системы занят в медиане на 96%.

Отсюда две вещи, которые делает инструмент:

- **делит набор на процессы с изоляцией каждого** — своя база, свой префикс индекса, свой
  временный каталог: без этого процессы портят данные друг другу;
- **держит общий лимит процессов на машину**, а не на сессию: несколько сессий команды
  запускают полные прогоны одновременно, и лимит одной сессии ничего не говорит о соседних.

## Настройки — раздел `tests` в `.claude/workspace.json`

```json
"tests": {
  "slots": 16,
  "repos": {
    "<репо>": {
      "mode": "split",
      "command": "…{files}…",
      "files": ["tests/**/*Test.php"],
      "exclude": ["tests/Integration/S3"],
      "workers": 8,
      "env": { "DB_DATABASE": "<репо>_w{i}_test" },
      "prepare": "…"
    }
  }
}
```

| Ключ | Смысл | Обязателен | Дефолт |
|---|---|---|---|
| `slots` | лимит процессов на машину для этого проекта | нет | личная переменная `BEERPOWERS_TEST_SLOTS` → число логических ядер |
| `repos.<репо>` | прогон репозитория `projects/<репо>` и его рабочих деревьев `worktrees/<КОД>/<репо>` | — | репозитория нет — инструмент его не запускает |
| `.mode` | `split` — инструмент делит файлы на процессы; `native` — параллель фреймворка (Jest `--maxWorkers`), инструмент только выдаёт число слотов | нет | `split` |
| `.command` | команда прогона; в `split` обязана нести `{files}` | да | — |
| `.files` | маски тестовых файлов от корня репозитория: `*` — в пределах каталога, `**` — любая глубина, `?` — один знак; каталоги `.git`, `node_modules`, `vendor` обход пропускает | в `split` | — |
| `.exclude` | маски или каталоги, которые из набора вычитаются (тесты с живым внешним сервисом) | нет | `[]` |
| `.workers` | сколько слотов запрашивать | нет | лимит, поделённый на число репозиториев вызова |
| `.env` | переменные воркера — шаблоны с подстановками | нет | `{}` |
| `.prepare` | подготовка воркера перед тестами: создать базу, применить миграции; идемпотентна — идёт перед каждым прогоном | нет | — |

`slots` в общем файле — договорённость команды, машинное значение — личная переменная
`BEERPOWERS_TEST_SLOTS` в `env` файла `.claude/settings.local.json`: у ноутбука и рабочей станции
разное число ядер. Переменная сильнее ключа.

**Подстановки.** Пути подставляются как есть, абсолютными: в команде их берут в двойные кавычки.

| Подстановка | Значение | Где нельзя |
|---|---|---|
| `{i}` | номер слота воркера — уникален среди одновременных прогонов машины | тест-команда `native` |
| `{n}` | число слотов прогона | — |
| `{slots}` | номера слотов через запятую | — |
| `{repo}` | имя репозитория | — |
| `{dir}` | абсолютный путь рабочего дерева репозитория (`projects/<репо>` или `worktrees/<КОД>/<репо>`) | — |
| `{root}` | корень workspace | — |
| `{tmp}` | пустой временный каталог воркера; убирается после зелёного прогона | — |
| `{junit}` | файл junit запуска — по нему считаются тесты и строится следующая раскладка | `prepare` |
| `{files}` | файлы группы путями от `{dir}` через пробел | везде, кроме `command` в `split` |
| `{env:ИМЯ}` | переменная окружения — машинное значение (путь к сертификатам, к интерпретатору) из `env` файла `.claude/settings.local.json` | — |

Неизвестная подстановка, `{files}` не на месте, `split` без `{files}` — отказ схемы: такой
прогон запустил бы не те тесты или весь набор в каждом процессе. Нет `{junit}` ни в команде,
ни в `env` — прогон идёт, но тестов в итоге не посчитать (`tests=?`), а раскладка всегда по числу
файлов; это предупреждение `workspace-check`.

**Номер слота — ключ изоляции.** Слот уникален на машине, пока прогон его держит, поэтому база
`<репо>_w{i}_test` у двух одновременных прогонов разных сессий — разная, даже если это один
репозиторий в `projects/` и в рабочем дереве задачи. Слотов не больше лимита — значит, и баз
на репозиторий не больше лимита: подготовка создаёт их один раз и дальше только догоняет
миграции. Удалять их без подтверждения пользователя нельзя, как и любую базу.

## Как идёт прогон

- **Слоты.** Захват — файл `slot-<номер>` с PID владельца в общем каталоге машины
  (`%LOCALAPPDATA%\Temp\beerpowers-test-slots` на Windows, `/tmp/beerpowers-test-slots-<uid>`
  на остальных; не `TMP` процесса: его переопределяют песочница сессии и сам инструмент
  для воркеров). Осмотр и захват — под замком-каталогом. Захват с мёртвым PID протух
  и убирается при следующем осмотре строкой `STALE`. Прогон берёт min(запрошено, свободно),
  свободных нет — ждёт, строкой `WAIT` раз в минуту; слоты отпускает в конце прогона
  репозитория, а не по воркеру: иначе ждущий прогон схватил бы первый освободившийся слот
  и пошёл одним процессом. Кто держит слоты — `--status`.
- **`split`.** Файлы по маскам минус исключения делятся на столько групп, сколько слотов
  получено, жадно по времени из сводного junit прошлого прогона этого репозитория
  (`.claude/.cache/parallel-tests/<репо>.junit.xml`, пути от корня репозитория — годится
  и для рабочих деревьев); файл, которого в junit нет, весит как средний; junit нет вовсе —
  по числу файлов. Каждая группа — свой процесс команды. Строка команды длиннее предела
  оболочки (cmd.exe — 8191 знак) режется на несколько запусков подряд в том же воркере.
- **`native`.** Один процесс команды с `{n}`. Переменные `env` с `{i}` получает только
  подготовка — по разу на каждый слот; тест-команда получает остальные и
  `BEERPOWERS_TEST_SLOTS`, а номер воркера фреймворка в номер слота переводит настройка тестов
  проекта (пример ниже).
- **Оболочка.** Команда идёт из каталога `{dir}` в оболочке системы: cmd.exe на Windows, `sh`
  на остальных. Кавычки — двойные; переменные — через `env` настройки, а не `$VAR` или `%VAR%`.
- **Вывод.** `START` на репозиторий — с коммитом прогона `head=<sha>` и `tree=clean|dirty` (есть ли
  в дереве незакоммиченное; без своего репозитория — `?`) — и `done` на воркер по ходу; в конце `REPO` на репозиторий
  (слоты, `tests`, `failed`, `skipped`, время, `status`), под ней воркеры с путём лога и до 30
  упавших тестов строками `FAIL`, затем `TOTAL repos=… tests=… failed=…` и последней строкой
  `CODE=<код>`: 0 — всё зелёное, 1 — упали тесты, подготовка или запуск, 2 — ошибка настроек
  или аргументов. Логи воркеров, junit каждого запуска и сводный junit — в
  `.claude/.cache/parallel-tests/runs/<время>-<pid>/<репо>/` (`--out` — другой каталог);
  прогоны старше семи дней оттуда убираются — и любым вызовом `.claude/bin/workspace-clean`,
  раньше срока — с `--keep-days`.
  Ненулевой код процесса без упавших тестов в junit
  (фатальная ошибка, предупреждение как отказ) — тоже отказ со ссылкой на лог.
- **Уборка.** Остановленный инструмент гасит свои процессы по своим PID (на Windows —
  `taskkill /T` по дереву) и снимает свои захваты.

## Изоляция процессов — что проверить в проекте

Параллель падает не на тестах, а на общем состоянии. Перед первой записью `repos.<репо>`
пройди по списку и каждое общее место разведи переменной воркера:

- **база** — своя на слот (`DB_DATABASE`, `DB_NAME`), с признаком тестовой в имени, если
  бутстрап тестов его требует;
- **поисковый индекс, очередь, кеш** — свой префикс на слот; тесты, которые пишут в индекс
  с именем из кода, а не из переменной, префиксом не разводятся — их каталог в `exclude`;
- **файловое хранилище** — подмена хранилища фреймворка по номеру процесса (Laravel:
  `Storage::fake` разводит каталог по `TEST_TOKEN`);
- **системный временный каталог** — `TMP`, `TEMP`, `TMPDIR` → `{tmp}`: тесты пишут туда файлы
  с одинаковыми именами;
- **порты** — тест, поднимающий сервер, берёт порт от слота или свободный;
- **живые внешние сервисы** (бакет, платёжный шлюз) — в `exclude`: параллельно их не гоняют.

`files` — весь набор раннера, а не его часть: маски берутся из конфига тестов (`<testsuites>`
в `phpunit.xml`, `testMatch` и `roots` Jest), и каждый каталог набора в них попадает. Сужает
набор только `exclude`, и исключённое инструмент не гоняет вовсе: его полный прогон — отдельная
команда одним процессом, которую `memory/commands/<скоуп>.md` называет рядом с формой через
инструмент. Без неё гейт «полный прогон зелёный» молча теряет эти тесты.

Проверка — один полный прогон через инструмент: тот же счёт тестов, что у прогона одним
процессом, минус тесты `exclude`, и ни одного нового падения. Счёт одного процесса — итоговая
строка раннера или его список тестов без прогона (`phpunit --list-tests`, у Jest — файлы
`--listTests`). Разница больше, чем даёт `exclude`, — маски теряют каталог набора.

## Пример: Laravel и PHPUnit

```json
"shop-backend": {
  "command": "php vendor/bin/phpunit -c phpunit.xml --colors=never --no-coverage --log-junit \"{junit}\" {files}",
  "files": ["tests/**/*Test.php"],
  "exclude": ["tests/Integration/S3"],
  "env": {
    "DB_DATABASE": "shop_w{i}_test",
    "SCOUT_PREFIX": "shop_w{i}_test_",
    "TEST_TOKEN": "{i}",
    "TMP": "{tmp}",
    "TEMP": "{tmp}",
    "TMPDIR": "{tmp}"
  },
  "prepare": "sh \"{root}/.claude/bin/testdb-ensure\""
}
```

- PHPUnit 10+ принимает несколько файлов аргументами — это и есть `{files}`.
- Переменная из окружения процесса сильнее `<env>` в `phpunit.xml`, пока у того нет
  `force="true"`, и сильнее `.env.testing`: загрузчик Laravel существующие переменные
  не переписывает. Стоит `force="true"` у `DB_DATABASE` — каждый воркер уйдёт в одну базу.
- `testdb-ensure` — проектный скрипт без шапки: создаёт базу `$DB_DATABASE`, если её нет,
  и применяет миграции к ней. На Windows `sh` в cmd.exe находится, только если инструмент
  запущен из Git Bash; из PowerShell — путь к `sh.exe` Git через `{env:…}`.
- Аргументы машины (`-d curl.cainfo=…` с путём к сертификатам) — подстановкой `{env:ИМЯ}`:
  в `workspace.json` абсолютных путей нет.

## Пример: NestJS и Jest

```json
"api": {
  "mode": "native",
  "command": "npx jest --ci --maxWorkers={n} --reporters=default --reporters=jest-junit",
  "env": { "JEST_JUNIT_OUTPUT_FILE": "{junit}", "DB_NAME": "api_w{i}_test" },
  "prepare": "npm run db:test:prepare"
}
```

Подготовка идёт по разу на слот с `DB_NAME=api_w<слот>_test`. Воркер Jest знает только свой
`JEST_WORKER_ID` (1…`maxWorkers`), поэтому базу в слот переводит файл из `setupFiles` конфига
Jest — он исполняется в каждом воркере до тестов:

```ts
const slots = (process.env.BEERPOWERS_TEST_SLOTS ?? '').split(',');
const slot = slots[Number(process.env.JEST_WORKER_ID ?? 1) - 1];
if (slot) process.env.DB_NAME = `api_w${slot}_test`;
```

Без `BEERPOWERS_TEST_SLOTS` (прогон не через инструмент) база остаётся той, что в конфиге.
