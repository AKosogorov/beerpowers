# Реестр миграций сгенерированного — для /beerpowers:update

> Generic reference плагина. Читает **только team-lead** при [`/beerpowers:update`](../commands/update.md).
> Каждая запись описывает, что изменилось в engine-managed частях сгенерированных файлов
> и как подтянуть существующий проект. Контракт maintainer'а: правка, меняющая сгенерированное
> (шаблоны `templates/`, структура charter в setup 4.1, settings/hooks-baseline), обязана добавить
> сюда запись `## → <версия>` (см. «Версионирование и миграции» в CLAUDE.md репозитория).
> Запись называет каждый изменённый engine-блок его именем из маркера и файл, где он стоит:
> update сверяет разницу в проекте с записью, и блок, которого запись не называет, выглядит
> правкой руками.

Порядок применения: все записи от версии charter (исключительно) до текущей версии плагина
(включительно), сверху вниз.

Charter со штампом `generated-by: qtim v1.13.0` или `v1.14.0` переводится записью `→ 2.0.0`
целиком. Charter qtim старше 1.13.0 сначала доводится до 1.14.0 командой `/qtim:team-sync`
апстрима, затем — этой записью: записи qtim до 1.14.0 сюда не перенесены.

## → 2.0.0

Источник — проект, собранный qtim 1.13.0–1.14.0, в том числе вручную доведённый до charter
2.0 (разрез по читателю, память по виду знания, барьеры-хуки в проекте). Это единственная
запись, которая требует суждения: у источника нет маркеров engine-блоков, и границу блока
update находит сравнением текста, а не по маркеру. Порядок ниже — порядок применения;
весь перевод — один коммит, откат — его revert плюс обратное включение qtim.

**Перед стартом.** `beerpowers` установлен, `qtim` в этом проекте выключен — на уровне
проекта (`enabledPlugins` в `.claude/settings.local.json`), а не глобально, если на машине есть
другие проекты на qtim. Команды у плагинов в разных пространствах имён и сами не конфликтуют,
но SessionStart-хук qtim, увидев charter без своего штампа, советует `/qtim:team-sync`, который
переписал бы charter шаблонами qtim, а скилы qtim дублируют `beerpowers:*` по коротким именам.
`/beerpowers:doctor` прогнан — его fail по п. 3 («собран qtim») ожидаем, остальные fail — в план.

**Запись в `.claude/` при автоматическом режиме разрешений.** Классификатор отказывает не только
в правке `settings.json`, но и в массовой записи в `.claude/` — `git mv` скриптов, копии `bin/`,
`git rm` команд и скилов — и роли, и team-lead'у. Отказ не обходится правкой по одному файлу.
Всё, что пишется в `.claude/` (кроме `settings.json`), собирается в scratchpad деревом
по путям проекта вместе со скриптом применения, который ничего не коммитит; team-lead показывает
человеку, что скрипт сделает, и запускает его только после явного «запусти», либо его запускает
человек. На Windows — Git Bash полным путём (`& "C:\Program Files\Git\bin\bash.exe" <скрипт>`
в PowerShell): голый `bash` там уходит в WSL.

1. **`.claude/workspace.json` и git-настройки** — завести по контракту `reference/workspace.md`.
   Git-ключей в `workspace.json` нет: профиль каждого репозитория — `.claude/git-settings.json`
   по setup, Q9 (сигналы — `lib/git.mjs detect`, Discovery п. 8: ветка по умолчанию и ветки
   `master`/`main`/`dev` у сервера, свежая история ветки выпуска), `standArchive` — по тому, архивировал ли проект стенд при пересборке.
   Ревьюеры из `.claude/mr-settings.json` — в личный `.claude/git-settings.local.json`
   (`reviewers` по имени репозитория, без пути `projects/`); `assignee` и `target` не переносятся —
   их теперь берут у токена и сервера. Сам `mr-settings.json` — файл пользователя: удаляет его
   человек после переноса, строка в `.gitignore` меняется на `git-settings.local.json`.
   Отслеживаемый `.claude/mr-settings.json.example` удаляется (`git rm`): пример личного файла
   теперь — в `reference/workspace.md`, раздел про `git-settings.local.json`.
   Таблицы `memory/tasks/*/git-flow.md` старой формы приводятся к колонкам
   «Репозиторий | База | Выпуск» (`.claude/reference/tasks-layout.md`): `lib/git.mjs` читает базу
   только из таблицы с этим заголовком, и задача со старой таблицей молча уходит на базу
   по профилю. База ветки-предшественника, записанная прозой (раздел «Зависимости»), переносится
   в таблицу. Правка — в коммите артефактов задач, отдельном от коммита перевода.
   Значения `workspace.json` — из фактов проекта, а не дефолтов. Код всегда в `projects/<имя>/`;
   проект, где код лежал в корне вместе с `.claude/`, раскладывается человеком заново до перевода
   (каталог workspace, репозиторий в `projects/`). Ключи `layout`, `projectsDir`, `worktreesDir`, `tasksDir` больше не пишутся: каталоги — константы `projects/`, `worktrees/`, `memory/tasks/`; папки задач в другом каталоге переносятся `git mv` в `memory/tasks/`. Пишутся `ui`, `comments.excludeDirs` (каталоги, которые исключал
   проектный `guard-comments.sh`, — путями `projects/<репо>/<каталог>`). Файлы задач вне закрытого списка
   шаблона (например карта переноса между репозиториями) — в `handover.md` задачи или в память,
   своих типов артефактов проект не заводит. `barriers` — по хукам, которые проект подключал в `settings.json`:
   подключён → `true`, не подключён → дефолт контракта. Сомнение в значении — один вопрос.
   При `ui: true` — `viewports` из брейкпоинтов фронта (setup, Discovery п. 5): ширины, которые
   проект уже называл в ролях и скриншотах (`tester-*-375.png`, «mobile и desktop»), — не источник,
   а только сверка. Таблица брейкпоинтов с файлом-источником — раздел «Брейкпоинты»
   в `memory/tests/frontend.md`. Ключ показать пользователю таблицей до записи.
2. **Charter → `templates/charter/team-charter.md`.** Для каждого engine-блока шаблона найди
   в charter проекта абзацы с тем же правилом (по жирной первой фразе: «Тестом называется
   только тест», «Shell-вызовы», «Записи о красных базах…»):
   - текст совпадает с блоком (с точностью до подстановки параметров: `master` ↔ «ветка по умолчанию»,
     `memory/tasks` ↔ `memory/tasks`, `/qtim:…` ↔ `/beerpowers:…`, хук `.claude/hooks/X.sh` ↔
     барьер `X` плагина) → заменить текстом блока с маркерами;
   - текст проекта **шире** блока (проектные примеры, имена репозиториев, команды, лишние
     предложения) → блок шаблона с маркерами, а проектный остаток — отдельным абзацем сразу
     после блока, вне маркеров; ничего из проектного не выбрасывается;
   - правило проекта, которого нет в шаблоне (правила по бренду, перенос между репозиториями,
     ширины экрана, `rules/` в репозиториях, исключённые `CLAUDE.md`) — остаётся на своём месте
     вне маркеров;
   - блок шаблона, которого в charter нет, — добавить по месту шаблона (условные — только
     при выполненном `if=`).
   Секции, которые в шаблоне — плейсхолдеры (Назначение, Стек, Команды, Состав, Модели,
   Intake-режим, Universal skills), переносятся из проекта как есть.
   Список доменных инвариантов из charter уходит в `memory/project/domain-invariants.md`
   (сливается с тем, что там уже есть), в charter остаётся engine-блок с указателем. «Anti-patterns» в charter больше нет: запрет уходит
   в `memory/project/safety-rules.md`, инвариант — в `memory/project/domain-invariants.md`, форма
   команды — в `memory/commands/<скоуп>.md`, пересказ правила charter удаляется. Проектный текст
   приводится к правилу «Один факт — одно место» setup (Phase 4): запрет, который охраняет доменный
   инвариант, уходит из `safety-rules.md`, «Не трогает» и чеклистов ролей в инвариант; из таблицы «Состав» уходит колонка
   «Не трогает» (она — в файле роли), строка «Модели» держит только отступления, раздел «Команды» —
   указатель на `memory/commands/`, проектная строка линта удаляется; в ролях строка «Перед
   началом прочитай» ссылается на колонку «Read on spawn», формы гейтов уходят в раздел «Гейты»
   `memory/commands/<скоуп>.md`, а в роли встаёт engine-блок `gate-forms`. В таблице «Файлы памяти» engine-строки — в блок, проектные
   (файлы слоёв, модулей, аудиты) — таблицей той же формы после блока. Ссылки на
   `.claude/skills/page-shot/` → скилл `beerpowers:page-screenshot`, на `/tasks-sweep` и
   `/qtim:team-retro` → `/beerpowers:retro`.
   Абзац «Метки находок» блока `evidence` стал таблицей меток: кроме `B`/`R`/`N` в ней буквы
   сценариев (`C`), проб (`M`), срезов брифа (`S`) и вопросов пользователю (`Q`). Проектный абзац
   о нумерации сценариев, срезов или проб рядом с блоком update называет в отчёте кандидатом
   на удаление — правило теперь в блоке. Метки в папках уже начатых задач не перенумеровываются.
3. **`team-lead.md` → `templates/charter/team-lead.md`** — тем же способом. Проектные разделы
   (перенос между репозиториями, тиражирование, заливка в стенд-ветку, тестовая база worktree)
   и проектные примеры в таблицах — после соответствующего блока вне маркеров. Таблица effort
   переносится как есть (это плейсхолдер `{{EFFORT_TABLE}}`). Git-правила проекта в `team-lead.md`
   не остаются: механика — копия `.claude/reference/git-flow.md`, проектные формы, заливка
   в стенд и свой флоу (`custom`) — в `memory/commands/git.md`, разделом на репозиторий.
   Пункт закрытия «Память» получает строку `память: перенесено | нечего` в `handover.md` —

4. **Агенты → `templates/roles/<role>-agent.md`.** Сопоставление по `name` во frontmatter.
   Engine-блоки шаблона роли — тем же способом, что в п. 2; стековые чеклисты проекта
   (`presets/<стек>/<роль>.md` описывает их обобщённую форму) и проектные пункты остаются вне
   маркеров. Frontmatter: `skills` — без `security-review` (см. `reference/skill-dependencies.md`;
   его заменяет ручной security-чеклист `reviewer` и `auditor` из шаблона), без локальных копий
   скилов плагина (`page-shot` → вызов `beerpowers:page-screenshot` по имени) и только скилы, видимые
   в сессии; те же исключения — в колонке «Skills» charter, иначе `workspace-check` падает
   на расхождении. Universal-скилы из строки «Universal skills» charter (`caveman`) во frontmatter
   остаются как были — `workspace-check` их разрешает, поведение ролей не меняется. Поля `effort:` нет; `model` и `tools` — как
   в проекте, если шаблон не требует инструмента сверх них (`Skill` у ролей со ссылками
   на скилы); `description` — из шаблона, если старое описание называет то, чего роль больше
   не делает (`security-review`, codex). Ссылки `qtim:<скил>` → `beerpowers:<скил>`; упоминания
   codex и `codex-consult` — убрать.
5. **Память.** Раскладка по виду знания (`project/`, `commands/`, `issues/`, `tech-debt/`,
   `tests/`, `adr/`, `tasks/`) у проекта уже есть — файлы не переносятся и не переписываются.
   Engine-блоки с маркерами получают только файлы, у которых есть шаблон с блоками:
   `MEMORY.md` («Раскладка», «Куда класть находку», «Владельцы правил» — проектные строки
   таблиц после блока отдельной таблицей), `project/safety-rules.md` (общие запреты и развилки —
   блоками, проектные — после), `project/glossary.md` (раздел «Ведение»),
   `issues/known-issues.md` (раздел «Ведение»). `memory/epic-state.md`, если есть, переезжает
   разделом «Пауза» в `handover.md` своей задачи.
   В блоке `confirm-generic` `safety-rules.md` — пункт «Критерий приёмки команда сама не снимает»,
   в «Владельцах правил» `MEMORY.md` — его маркер; проектное правило о снятии критериев рядом
   с блоком — кандидат на удаление в отчёте update.
6. **Хуки.** Барьеры плагина (`guard-push`, `guard-kill`, `guard-comments`, `guard-commit-split`,
   `guard-agent-memory`) заменяют проектные копии: из `.claude/settings.json` уходят их записи
   в `hooks`, файлы `.claude/hooks/guard-*.sh` удаляются (показать дифф каждого против барьера
   плагина до удаления — проектная логика сверх плагина переносится в параметры
   `workspace.json` или называется пользователю). `quality-reminder.sh` → копия
   `templates/hooks/quality-reminder.sh` с шапкой, а его проектные гейты — в
   `.claude/quality-gates.txt` по формату шапки хука; запись в `settings.json` остаётся.
   Блокирующий `screenshots-gate.sh` qtim в beerpowers не переносится: гейт скриншотов держит
   финальный `reviewer`, который видит, менял ли фикс экран. Его файл в `.claude/hooks/`
   удаляется, запись в `settings.json` снимается. Если проект хочет напоминание тестеру —
   копия `templates/hooks/screenshots-reminder.sh` и запись на два события, `SubagentStart`
   и `SubagentStop`, с matcher `^<тип тестера>$` и аргументом `--agent <тип тестера>`
   (setup 4.3); прежние позиционные аргументы не переносятся. В `permissions.deny` — маски
   разрушающих git-форм через `-C` из setup 4.3 (`Bash(git -C * reset --hard:*)`, `clean`,
   `push -f`, `push --delete`, `push origin <защищённая ветка>`): у старого проекта общий
   `allow` на `Bash(git -C:*)` без них. **`.claude/settings.json` в автоматическом режиме
   разрешений правит человек:** классификатор отказывает в правке как в самомодификации —
   update готовит итоговый файл рядом (в scratchpad) и дифф, человек копирует; до этого
   барьеры работают дважды, а записи хуков ссылаются на удалённые файлы.
   Исполняемый бит shell-скриптов `.claude/bin/` и `.claude/hooks/` — `git update-index --chmod=+x`:
   на macOS хук и скрипт без него не запускаются. `allow` форм сборки и проверки — под
   `projects/<репо>` и под `worktrees/*/<репо>`; каждый разрушающий скрипт проекта (откат
   и сброс миграций, `schema:drop`, `down -v`) — в `deny` под оба пути (setup 4.3).
7. **Скрипты `.claude/bin/`.** Новые копии без прежнего аналога — `git-base.mjs` и `lib/git.mjs`.
   Для каждого шаблона `templates/bin/*` с тем же именем —
   перезапись копией с шапкой; проектные режимы, которых нет в шаблоне, называются
   пользователю до перезаписи (их место — проектный скрипт рядом или `worktree-setup` /
   `worktree-teardown`). Скрипты без пары в шаблоне (`brand-scan`, `worktree-testdb` и подобные)
   остаются проектными, без шапки; `workspace-clean` и `worktree-add` плагина зовут их через
   точки расширения `.claude/bin/worktree-setup` / `worktree-teardown`, если проект их заведёт.
   `.claude/skills/page-shot/scripts/cdp-shot.mjs` → `.claude/bin/cdp-screenshot.mjs`, переменная
   `SHOT_TASK` в проектных вызовах → `SCREENSHOT_TASK`; `.claude/bin/tracker-issue` →
   `.claude/bin/yandex-tracker`, его переменные `TRACKER_*` → `YANDEX_TRACKER_*`, настройки
   `.claude/tracker-settings.json` и `.example` → `.claude/yandex-tracker-settings.json` и `.example`
   (строка `.gitignore` тоже), `memory/commands/tracker.md` → `memory/commands/yandex-tracker.md`;
   глобальный `~/.claude/tracker-settings.json` переименовывает человек — назвать в отчёте;
   `.claude/make-shim.mk` → `.claude/bin/lib/make-shim.mk`. Зависимости по lock-файлу
   (`pnpm-lock.yaml`, `package-lock.json`, `composer.lock`) `worktree-add` ставит сам, без флага:
   проектный флаг вроде `worktree-add --deps` и установка зависимостей в проектном скрипте
   удаляются, формы с ним в памяти — тоже. Остальные проектные флаги прежних скриптов
   (тестовая база и подобное) переезжают в `worktree-setup` и передаются ему после `--`:
   `worktree-add <репо> <КОД> -- <флаг>`, `/beerpowers:task-start <КОД> -- <флаг>`; без `--`
   `worktree-add` чужой флаг отвергает. Индекс долга в workspace с несколькими репозиториями
   требует у каждого пункта поле `repo` — репозитории `projects/` через запятую или `workspace`;
   без него `tech-debt-index.mjs` не соберёт индекс. Проектное поле той же роли (например
   `brand` — бренд из двух репозиториев) переводится в `repo` по смыслу каждого пункта, а не
   заменой: пункт касается бэкенда, фронта или обоих. Список предлагаемых значений — таблицей
   пользователю до записи; прежнее поле после перевода удаляется. `allow` в `settings.json` — литеральные пути копий и проектных
   скриптов (`worktree-setup`, `worktree-teardown`); правила на удалённые пути — убрать.
   **Смоук-прогоны скриптов после перевода — только сухим прогоном или на копии:**
   проектный `worktree-teardown` работает с живыми сервисами (базой, контейнером).
