# Барьеры-хуки

Механика барьеров: что именно блокирует каждый, почему это не делается масками разрешений,
какими флагами и параметрами `.claude/workspace.json` он управляется и как проверить хук
до того, как на него положиться. Правила, которые барьеры держат, — в charter; флоу веток —
[`git-flow.md`](git-flow.md).

Барьеры приходят с плагином и зарегистрированы им самим, в `settings.json` проекта их нет.
Действуют только в проекте, где есть `.claude/team-charter.md`: без charter каждый хук молча
пропускает всё. Исключение — `guard-user-files`: он стережёт и сам setup, который charter
только создаёт. `.claude/workspace.json` пишет `/beerpowers:setup`; выключить барьер —
поставить его флаг в `false`, хук перечитывает файл на каждом вызове.

| Барьер | Событие | Флаг `barriers.<имя>` | Без флага | Что ещё читает |
|---|---|---|---|---|
| `guard-push` | PreToolUse `Bash` | есть | включён | ветки и хостинг — из git репозитория |
| `guard-kill` | PreToolUse `Bash` | есть | включён | — |
| `guard-comments` | PreToolUse `Bash` | есть | включён | `comments.excludeDirs` |
| `guard-commit-split` | PreToolUse `Bash` | есть | включён | — |
| `guard-agent-memory` | PreToolUse `Edit\|Write` | нет — не выключается | включён | — |
| `guard-user-files` | `UserPromptSubmit`, PreToolUse `Skill`, `Write`, `Bash` | нет — действует только пока идёт setup или onboard | включён | — |
| `quality-reminder` | PostToolUse `Edit\|Write` | нет — копия в проекте по выбору setup | — | `.claude/quality-gates.txt` |

## Как хук читает `workspace.json`

**Сначала — ранний отсев.** Барьер на `Bash` ищет в сыром событии своё слово (`push`,
`commit`, `kill` или `Stop-Process`) и без него выходит, не читая флаг и не разбирая JSON:
барьеры идут на каждой команде, а запуск `sed` на Windows стоит десятки миллисекунд.
`guard-user-files` так же выходит, если окно не открыто.

Без `node` и без `jq`: хук обязан работать на любой машине команды, поэтому файл читается
`sed`'ом. Отсюда требования к записи:

- флаг — `"<имя барьера>": true` или `false`, значение без кавычек;
- строка — `"<ключ>": "<значение>"`, значение без кавычек внутри;
- массив — только из строк: `"excludeDirs": ["projects/app/gen/api", "projects/api/src/generated"]`. Элемент не содержит
  кавычку, запятую, `]` и пробел; в строку массив записан или разнесён по строкам — всё равно;
- ключ `excludeDirs` и имена барьеров встречаются в файле по одному разу.

Нет файла, нет ключа или пустая строка — дефолт: `comments.excludeDirs` — пусто. Каталоги
`projects/` и `memory/tasks/` — константы, из файла не читаются. Git-настроек хуки из файлов не читают: ветку по умолчанию
и хостинг `guard-push` берёт у самого репозитория.

## Почему хуками, а не масками и не текстом

**Маски разрешений матчат префикс команды**, а опасная форма часто отличается порядком
аргументов, а не префиксом: `git -C <путь> push origin master` не попадает под
`Bash(git push:*)`, `taskkill //F //IM chrome.exe` — под маску с другим порядком флагов.

**Текст правила не держится под давлением бюджета и длины контекста.** Правило, которое
промахнулось при уже записанной формулировке, переводится в исполняемую форму: греп,
скрипт с pass/fail, хук. Хук печатает причину отказа и, где возможно, готовую форму
исправления — роль узнаёт правило в момент нарушения, а не читает его заранее.

**Данные — не команды.** Все барьеры на `Bash` отрезают тело heredoc и содержимое кавычек
до разбора: сообщение коммита или тело MR может упоминать любые опасные формы, описывая их,
а не выполняя. Составная команда (`;`, `&&`, `|`) разбирается по сегментам, иначе безопасный
первый сегмент прикрыл бы опасный второй.

## `guard-push` — защищённые ветки

Хук разбирает команду и блокирует:

- push в ветку по умолчанию, `master` или `main` — в том числе парой `HEAD:<ветка>`
  и `refs/heads/<ветка>`. Ветка по умолчанию — локальный `refs/remotes/<remote>/HEAD`, без
  запроса к серверу: хук ограничен по времени, а недоступный хостинг держал бы каждый push
  до таймаута. Поэтому `master` и `main` закрыты по имени всегда, даже если `origin/HEAD`
  устарел; точную ветку по умолчанию с сервера считает `.claude/bin/git-base.mjs`;
- push без refspec — цель возьмётся из upstream и может оказаться защищённой. Ветка,
  заведённая формой `git checkout -B dev origin/<ветка по умолчанию>`, получает в upstream
  её, а не `origin/dev`, и push без цели из `dev` уходит в защищённую.
  Форма заведения ветки от чужой базы обязана завершаться явным
  `git branch --set-upstream-to=origin/<своя ветка>`;
- голый `--force`, `-f` и refspec с `+`;
- push из дерева пересборки стенда `worktrees/chore-<стенд>-rebuild/<репо>` в любую ветку, кроме
  `<стенд>`. Push с силой из таких деревьев разрешён в `.claude/settings.json` маской на путь,
  без имени ветки — имён стендов в настройках нет, и ветку держит барьер;
- push с `--force-with-lease` или `--force-if-includes`, после которого из
  `refs/remotes/<remote>/<ветка>` пропадут коммиты: у коммита прежней вершины в новой истории
  нет пары ни по патчу (`git patch-id --stable`), ни по теме. Влитое в основную ветку, на которую
  ветка переложена, пропажей не считается. Отказ — один раз на пару «прежняя вершина → новая»,
  со списком пропавших: пропажа бывает намеренной (задача снята со стенда, ветка схлопнута),
  решает человек, повтор той же команды проходит. Ту же проверку до push даёт
  `node .claude/bin/git-base.mjs --lost <дерево> origin/<ветка> HEAD`;
- удаление ветки на сервере: `--delete`, `-d`, refspec `:<ветка>`;
- `--all` и `--mirror`;
- на GitLab (адрес remote содержит «gitlab») — первый push ветки задачи без
  `-o merge_request.create`. Ветка задачи — с кодом трекера в имени (`PROJ-123`) или с папкой
  `memory/tasks/<имя>/`; релизная, стенд и архив заводятся без MR и проверку не проходят. Опции доходят до сервера только при реальной передаче ref;
  на уже отправленной ветке push вернёт `Everything up-to-date`, опции потеряются молча,
  и второго шанса завести MR push-опциями нет. «Уже отправлялась» хук проверяет по
  `refs/remotes/<remote>/<ветка>` в репозитории из `-C`: ветка на сервере есть, а ссылки
  нет — `git fetch origin --prune`, и проверка пропустит. На другом хостинге проверки нет.

Проходят: push-опции (`-o merge_request.target=<ветка>` задаёт цель MR, а не ветку отправки),
`git stash push`, упоминания push в кавычках и heredoc. `--force-with-lease` и
`--force-if-includes` в ветку задачи и в релизную ветку разрешены — ветки обновляются
rebase'ом, и после него обычный push отклоняется; эта форма отказывается перезаписывать
ветку, изменившуюся с последнего `fetch`, поэтому чужая работа не теряется; свою, пропавшую
при ребейзе, ловит проверка пропаж выше. В закрытую ветку не проходит и она.

Релизные ветки барьер не запрещает: их перекладывает team-lead, и без `--force-with-lease`
это невозможно. Барьер тут заменён обязанностью — переложивший релизную сразу называет
исполнителям новую голову и прежнюю базу для `rebase --onto` (см. [`git-flow.md`](git-flow.md)).

По умолчанию барьер включён: защита веток на хостинге стоит не везде, а маска `deny`
в `settings.json` ловит только текст команды — другой remote, `HEAD:<ветка>` и push без refspec
проходят мимо неё.

## `guard-kill` — убийство процессов

Блокирует убийство по имени образа и по шаблону: `taskkill //IM` и `//FI`, `taskkill`
без `//PID` вовсе, `pkill`, `killall`, `Stop-Process -Name` (и внутри `powershell -c "…"`),
а также `kill -1` и `kill 0`, бьющие по группе процессов. Проходит только цель по PID:
`taskkill //F //PID <pid> //T`, `kill -9 <pid>`, `Stop-Process -Id <pid>`. Цена ошибки —
снесённый браузер пользователя вместе с его окнами: роль, прибирая свой headless-браузер,
убивает все процессы с тем же именем образа.

## `guard-comments` — комментарии в коде

На `git commit` печатает добавленные в индексе строки комментариев в коде (при `commit -a`
и `--all` — и неиндексированные правки отслеживаемых файлов) и блокирует коммит **один раз**; повторный коммит того же набора строк проходит — набор запоминается хешем
в `.claude/.cache/comment-guard` (каталог `.claude/.cache/` — под gitignore). Содержание
не оценивается: отличить причину от пересказа машинно нельзя, решение остаётся за автором.

Смотрятся комментарии `//`, `/* */`, `<!-- -->` и Blade `{{-- --}}` — TypeScript/JavaScript,
Vue, Svelte, PHP, CSS/SCSS/LESS, Go, Java, Kotlin, Swift, Rust, C/C++, C#, Scala, Dart, HTML —
и `#` — Python, shell, Ruby, Perl, YAML, TOML, PHP, Elixir, Dockerfile. И в начале строки,
и в её конце после кода; перед хвостовым `//` и `#` нужен пробел, поэтому `https://`
и `${#var}` комментарием не считаются, как и shebang `#!` и атрибут PHP `#[`. Каталоги `comments.excludeDirs` исключены — туда кладут генерируемый код: регенерация
приносит комментарии десятками, руками их не правят, и показ только топит настоящие. Запись —
путь от корня workspace `projects/<репо>/<каталог>` и действует только в своём репозитории
и его рабочих деревьях `worktrees/<КОД>/<репо>/`: репозиторий хук узнаёт по имени каталога.
Копии плагина в `.claude/` — файлы с шапкой `generated by beerpowers` — исключены всегда: их
целиком перезаписывает `/beerpowers:update`. Проектные скрипты рядом с ними шапки не несут
и показываются.

## `guard-commit-split` — артефакты задач отдельно

На `git commit` смотрит индекс репозитория из `-C` (нет `-C` или путь не раскрыт — корень
проекта): если в нём и `memory/tasks/**`, и что-то ещё — отказ с перечнем «остального» и формой
разнесения на два коммита. Историю по пути `memory/tasks` однажды вычистят целиком, и отдельные
коммиты выпадут чисто, а смешанные останутся выпотрошенными. В репозиториях кода каталога
`memory/tasks` нет — проверка молча проходит. Форма `git commit -- <пути>` не разбирается: набор
файлов тогда не из индекса, а ложный отказ дороже пропуска.

## `guard-agent-memory` — память роли

В `.claude/agent-memory/<роль>/` и `.claude/agent-memory-local/<роль>/` пропускает только
`feedback_*.md` и `MEMORY.md`. Всё остальное — знание о проекте или инструменте —
возвращается указателем на таблицу «Куда класть находку» в `memory/MEMORY.md`. Путь
нормализуется по разделителям, так что форма Windows (`C:\…\.claude\agent-memory\…`)
и POSIX ловится одинаково. Флага нет: память роли, растущая мимо `memory/`, расходится
с памятью проекта в любом проекте.

## `guard-user-files` — файлы проекта на время setup и onboard

Действует только пока идёт `/beerpowers:setup`, `/beerpowers:onboard` или
`/beerpowers:product-onboard` — команды, которые пишут в проект, где уже лежит чужое:
`CLAUDE.md` пользователя, его настройки, накопленная память. В это время:

- `Write` поверх существующего файла — отказ: дописывать через `Edit`, дифф — человеку;
- `rm`, `mv`, `git rm`, `git mv`, `git clean`, `git restore`, `git checkout -- <путь>`,
  `git reset --hard`, `cp` и `>` поверх существующего файла — отказ.

Новые файлы, папки задач `memory/tasks/`, `.claude/.cache/` и копии с шапкой
`generated by beerpowers` проходят. Charter для барьера не нужен: setup идёт до него.

Окно команды открывает промпт, который начинается с одной из трёх команд (`UserPromptSubmit`),
или вызов её моделью через `Skill`; закрывает другая слеш-команда, последний шаг самой
команды (`--close`) или шесть часов. Обычные сообщения окно не закрывают: диалог setup
идёт и ими. Флага нет — вне трёх команд барьер молчит.

## `quality-reminder` — напоминание о гейтах

Не барьер и не плагинный хук: `setup` копирует его в `.claude/hooks/` проекта и подключает
в `.claude/settings.json` на PostToolUse `Edit|Write`. Не блокирует: после правки файла
возвращает в контекст гейт для его типа. Вывод идёт через `additionalContext` — stdout
PostToolUse в контекст модели сам по себе не попадает.

Копия совпадает с шаблоном плагина байт в байт (кроме версии в шапке), поэтому гейты
проекта лежат рядом — в `.claude/quality-gates.txt`, который `update` не трогает:

```text
# комментарий; пустые строки пропускаются
*/database/migrations/*  Миграция: идемпотентность, индекс на FK, развилку пользователю до применения.
*.php                    PHP: статанализ, затем полный check.
*.vue                    Клиент: сборка и линт по изменённым файлам.
```

Маска — первое слово строки, шаблон shell `case` по пути с прямыми слэшами (`*` захватывает
и `/`, альтернативы через `|` не поддерживаются — по строке на маску); текст — остаток строки.
Срабатывает первая подходящая строка, поэтому частные маски ставятся выше общих. Нет файла
или маска не подошла — хук молчит.

## Правка хука вступает в силу со следующей сессии

Подключение хуков читается при старте сессии: новый хук или изменённая регистрация в текущей
сессии не действуют. Барьеры плагина обновляются вместе с плагином, копия `quality-reminder` —
через `/beerpowers:update`; проверяй новое поведение крафтовым JSON, не дожидаясь сессии.
Флаги и параметры `workspace.json`, наоборот, хук перечитывает на каждом вызове.

## Как проверить хук

Хук — обычный скрипт: JSON события на stdin, решение на stdout. Крафтовый JSON проверяет его
без сессии и без риска выполнить саму команду. Пустой вывод — пропуск, JSON
с `"permissionDecision":"deny"` — отказ, для `quality-reminder` — JSON с `additionalContext`.

Барьеры плагина лежат в каталоге установленного плагина (`hooks/`), а не в проекте; проект
задаётся переменной `CLAUDE_PROJECT_DIR`, команда запускается из корня проекта:

```bash
printf '%s' '{"tool_input":{"command":"git push origin main"}}' \
  | CLAUDE_PROJECT_DIR="$PWD" sh <каталог плагина>/hooks/guard-push.sh

printf '%s' '{"tool_input":{"file_path":"C:\\proj\\.claude\\agent-memory\\architect-agent\\notes.md"}}' \
  | CLAUDE_PROJECT_DIR="$PWD" sh <каталог плагина>/hooks/guard-agent-memory.sh

printf '%s' '{"tool_input":{"file_path":"/proj/app/models/user.php"}}' \
  | sh .claude/hooks/quality-reminder.sh
```

Что проверять у барьера: каждый вид отказа, каждый разрешённый вид рядом с ним
(`--force-with-lease` в ветку задачи, push-опции, kill по PID), выключенный флаг и отсутствие
charter — оба дают пустой вывод. Барьерам на `git commit` нужен репозиторий с подготовленным
индексом: собери его во временном каталоге (`git init`, файлы, `git add`) и передай путь
через `-C`. В репозитории плагина те же случаи собраны фикстурами — `tests/hooks/run.sh`
печатает pass/fail по каждому и завершается ненулевым кодом при падении.
