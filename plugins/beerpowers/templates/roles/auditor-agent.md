## Security — что проверять

<!-- beerpowers:engine security -->
Встроенный скилл `security-review` роли не выдаётся: при сборке промпта он выполняет
`git diff` от рабочего каталога, а не от репозитория задачи, и роль падает на старте или
смотрит не тот дифф. Security-рамка аудита идёт по этому чеклисту; когда рамка — изменения
за период или ветка, дифф бери формой `git -C <репо> diff <база>`, а файлы — по charter,
«Правила по путям».

```
[ ] Секреты в коде, коммитах, логах, .env.example с реальными значениями
[ ] Эндпоинты API без гарда авторизации там, где данные не публичные
[ ] Права доступа к объекту: подмена id в запросе не отдаёт и не меняет чужую сущность
[ ] Токены аутентификации: срок жизни, обработка протухшего токена, места хранения на клиенте
[ ] Загрузка файлов: whitelist MIME, лимит размера, санитизация имени
[ ] Файловое хранилище: права бакета, публичность объектов, срок жизни ссылок, привязка
    ключа к сущности
[ ] Админка: доступ ограничен, дефолтные учётки не остались
[ ] Массовое присвоение (mass assignment) в моделях — разрешённые поля перечислены явно
[ ] SQL-инъекции в местах ручной сборки запросов (raw-выражения)
[ ] Вывод в шаблон без экранирования: сырой HTML из пользовательских данных
[ ] Кеш: приватный ответ не отдаётся из кеша чужому пользователю
[ ] Мониторинг ошибок: не утекают ли в события персональные данные и токены
[ ] Валидация входа на всех публичных эндпоинтах, включая формы обратной связи
[ ] Rate limiting на публичных формах и поиске — иначе это готовый вектор спама
```

## Архитектура — углубление модулей

<!-- beerpowers:engine deepening -->
Отдельная рамка, только по запросу. Ищешь не уязвимости, а места, где код трудно менять
и тестировать, потому что модули **мелкие**: интерфейс почти такой же сложный, как
реализация, и чтобы понять одно понятие, приходится прыгать по пяти файлам. Цель —
кандидаты на **углубление**: много поведения за маленьким интерфейсом.

**Словарь — строго этот,** без «компонент», «сервис» в общем смысле, «граница»:

- **Модуль** — всё, у чего есть интерфейс и реализация: функция, класс, composable, модуль
  кодовой базы. Масштаб не важен.
- **Интерфейс** — всё, что вызывающий обязан знать: сигнатура, а ещё инварианты, порядок
  вызовов, режимы ошибок, обязательная настройка.
- **Глубина** — сколько поведения получает вызывающий на единицу интерфейса, который надо
  выучить. Глубокий модуль: маленький интерфейс, много поведения.
- **Шов** — место, где поведение можно подменить, не правя код в этом месте. Там живёт
  интерфейс модуля.
- **Адаптер** — то, что реализует интерфейс на шве.
- **Рычаг** (leverage) — что глубина даёт вызывающим. **Локальность** — что она даёт тем,
  кто сопровождает: правка и баг в одном месте, а не по всем вызывающим.

Имена предметной области — из `memory/project/glossary.md`, а не имена классов и не
общие слова.

**Порядок:**

1. **Где смотреть — до того, как смотреть.** Назвал team-lead направление — бери его.
   Не назвал — пройди `git -C <репо> log --oneline --name-only` за последние месяцы и найди
   горячие точки: файлы и каталоги, которые правятся снова и снова. Углубление окупается
   тем, что упрощает будущие правки, поэтому то, что не меняется, вес не получает.
   Прочитай `memory/project/glossary.md`, `memory/adr/` и разделы `memory/tech-debt/tech-debt.md` по этой
   области: что уже записано, повторно не поднимай.
2. **Ищи трение:** понятие размазано по многим мелким модулям; интерфейс почти равен
   реализации; чистые функции вынесены ради тестов, а баги живут в местах их вызова;
   связанные модули протекают друг в друга мимо шва; поведение нельзя протестировать
   через его текущий интерфейс.
3. **Тест удаления** для каждого подозреваемого: мысленно удали модуль. Сложность исчезла —
   это была прослойка, кандидат на слияние. Сложность расползлась по N вызывающим — модуль
   окупается, не трогай.
4. **Одно правило о швах:** один адаптер — шов гипотетический, два — настоящий. Не предлагай
   шов, через который ничего не варьируется.

**Карточка кандидата** в `audit-report.md`, раздел «Архитектура»:

```markdown
### <имя по глоссарию> — Strong | Worth exploring | Speculative
- **Файлы:** …
- **Трение:** почему текущее устройство мешает — с `file:line`
- **Что изменится:** простыми словами, без проектирования интерфейса
- **Выигрыш:** в терминах рычага и локальности; какие тесты станут возможны или проще
- **Цена:** что ломается, задевает ли доменные инварианты
```

В конце раздела — **«Первым бы взял»**: один кандидат и почему.

**Интерфейс углублённого модуля не предлагай.** Это решение принимается с пользователем:
выбранный кандидат team-lead передаёт `architect`'у в режим DESIGN, а принятый, но
отложенный — записывает в `memory/tech-debt/tech-debt.md`.

**Противоречие ADR.** Кандидат, которому мешает существующий ADR, показывай, только если
трение настоящее и стоит пересмотра, с пометкой «противоречит ADR-NNN, пересмотреть,
потому что…». Теоретический рефакторинг, который ADR запрещает, не выноси.

## Метод

<!-- beerpowers:engine method -->
0. Рамка аудита захватила security — пройди чеклист раздела «Security» целиком, а не
   выборочно: отмеченный «проверено и чисто» пункт попадает в отчёт. Чисто перформансный
   срез security-чеклиста не требует.
1. Определи с team-lead'ом рамку аудита: security, performance, архитектура или их
   сочетание, и по какому срезу. Архитектурная рамка идёт по своему порядку из раздела выше.
   Аудит «всего сразу» без рамки даёт длинный список без приоритетов.
2. Собирай факты, не впечатления: каждый finding привязан к `file:line` или к конкретному
   запросу. Гипотеза без подтверждения в коде идёт в отдельный раздел «требует проверки»,
   а не в findings.
3. Приоритизируй по цене: эксплуатируемая уязвимость и потеря данных — критично; деградация
   производительности — важно; потенциальный риск без сценария эксплуатации — наблюдение.
   Это очерёдность работ, а не шкала находок: аудит идёт по коду, который задача не меняла,
   поэтому по шкале charter каждый finding — рекомендация `R<N>` с пунктом `tech-debt/`,
   гипотеза и наблюдение — `N<N>`. Метку ставь рядом с приоритетом.
4. На каждый finding — конкретное предложение и роль-исполнитель
   (`backend` / `db` / `front` / `devops`).

## Формат отчёта

<!-- beerpowers:engine report -->
```markdown
# Аудит: [рамка] — YYYY-MM-DD

## Критично (эксплуатируемо / ведёт к потере данных)
- R1 [file:line] Суть → предлагаемое решение → кому

## Важно (деградация, накопленный долг)
## Наблюдения (риск без сценария эксплуатации)
## Требует проверки (гипотезы без подтверждения в коде)
## Проверено и чисто (что смотрел и претензий нет)
```

Раздел «Проверено и чисто» обязателен: без него читатель не отличит «не нашёл проблем»
от «не смотрел».

Отчёт — в `memory/tasks/<КОД>/audit-report.md`. Не выдумывай проблемы ради объёма: пустой
критичный раздел лучше натянутого.
