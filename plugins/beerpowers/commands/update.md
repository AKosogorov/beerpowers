# /beerpowers:update — перенос новой версии плагина в проект

> Читает только team-lead. Запускается в проекте с уже собранной командой, когда плагин
> обновился (SessionStart-hook подсказывает это при дрейфе версий), или когда `/beerpowers:doctor`
> нашёл устаревшую или правленую копию. Сначала обновляется сам плагин (менеджер плагинов Claude Code),
> потом эта команда переносит его версию в файлы проекта. Не путать с [`setup.md`](setup.md) —
> тот собирает команду с нуля или дозаполняет состав и задаёт вопросы; update состав
> не меняет, только подтягивает движок в уже сгенерированное. И с [`doctor.md`](doctor.md) —
> тот проверяет и не пишет. Нет charter — сначала `/beerpowers:setup`.
>
> Контракт engine-блоков, условий `if=` и копий — [`../reference/workspace.md`](../reference/workspace.md);
> что менялось от версии к версии — [`../reference/migrations.md`](../reference/migrations.md).

## Контракт: что менять, что сохранять

- **Механически, без суждения:**
  - engine-блоки (`<!-- beerpowers:engine <имя> -->` … `<!-- /beerpowers:engine -->`)
    в `.claude/team-charter.md`, `.claude/team-lead.md`, `.claude/agents/*.md` и файлах
    памяти с маркерами (`memory/MEMORY.md`, `memory/project/safety-rules.md`,
    `memory/project/glossary.md`, `memory/issues/known-issues.md`) — по таблице слияния
    контракта;
  - копии `.claude/bin/*`, `.claude/hooks/*` со шапкой `generated by beerpowers` и
    `.claude/reference/{hooks,tasks-layout,worktrees,git-flow}.md` — перезапись из плагина
    с текущей версией в шапке;
  - штамп `generated-by: beerpowers v<версия>` в charter и ключ `beerpowers` в
    `.claude/workspace.json`.
- **По записи реестра миграций:** новые ключи `workspace.json`, settings-baseline, перенос
  блока на новое место, удаление блока, которого больше нет в шаблоне.
- **Не трогается никогда:** текст вне engine-блоков (проектные блоки, подставленные
  плейсхолдеры, доменные инварианты, состав и имена ролей, skills, `model`), знания в `memory/`
  и `.claude/agent-memory/`, `.claude/quality-gates.txt`, проектные скрипты без шапки.
- **`CLAUDE.md`, `.gitignore`, `.claude/rules/` — файлы пользователя:** update только дописывает
  недостающее по записи миграции, показав дифф.
- Ничего не удалять молча. Конфликт в engine-блоке — показать и спросить, не перезаписывать.

## Шаги

1. **Версии.** Прочитай `version` из `${CLAUDE_PLUGIN_ROOT}/.claude-plugin/plugin.json` и штамп
   из `.claude/team-charter.md`.
   - `generated-by: qtim v1.13.0` или `v1.14.0` → **перевод с qtim**: шаг 2 читает одну запись
     `→ 2.0.0`, дальше — по её пунктам (там же — что делается суждением, а не заменой блока).
     qtim старше 1.13.0 → остановись: сначала `/qtim:team-sync` апстрима до 1.14.0.
   - `generated-by: beerpowers v<X>`: `X` = версии плагина → сразу шаг 3 (копии и блоки всё равно
     сверяются — так ловится правка руками); `X` новее плагина (откат) → только штамп, сообщи
     об откате.
   - штампа нет → спроси, из какой версии собран проект; не угадывай.
2. **Реестр миграций.** Возьми записи от версии charter (исключительно) до версии плагина
   (включительно), сверху вниз.
3. **Diff-анализ по маркерам.** Для каждого файла с engine-блоками — шаблон текущей версии
   (`${CLAUDE_PLUGIN_ROOT}/templates/charter/`, `templates/roles/`, `templates/memory/`) и шаблон
   версии charter (кеш плагина той версии `…/plugins/cache/<marketplace>/beerpowers/<X>/`, если
   он есть; нет — описание в записи миграции; версия charter равна версии плагина — шаблон
   текущей версии и есть шаблон прошлой). Агент сопоставляй с шаблоном по `name` во
   frontmatter (`<role>-agent`); роль без шаблона engine-блоков не имеет — пропусти её строкой
   в отчёте. По каждому блоку — строка таблицы слияния из контракта: заменить / конфликт /
   удалить / добавить. Условный блок (`if=`) оценивается по `workspace.json`: условие не
   выполнено и блока нет — норма. Копии: сверка как в `/beerpowers:doctor`, п. 6.
4. **План + подтверждение.** Компактно: файл → блок или копия → действие → основание (таблица
   слияния или запись миграции). Конфликты — отдельным разделом с обоими текстами.
   **Ничего не пиши до подтверждения пользователя.**
5. **Применение.** Замена блока — текст между маркерами целиком, маркеры остаются; соседний
   проектный текст не трогается ни на символ. Копии — перезапись с подставленной версией;
   каждая перезаписанная копия, отличавшаяся от шаблона своей версии, называется в отчёте
   («`.claude/bin/worktree-add` — была правлена руками, восстановлена»).
6. **Штамп.** `generated-by: beerpowers v<версия> · mode: plugin-linked` в шапке charter,
   `"beerpowers": "<версия>"` в `workspace.json`.
7. **Проверка.** `node .claude/bin/workspace-check.mjs` — все строки pass; fail — в отчёт,
   не объявлять синхронизацию законченной. Строки WARN синхронизацию не останавливают: находки
   списком в отчёт, проектные файлы по ним update не правит.
8. **Отчёт.** Что заменено (по файлам и блокам), какие копии восстановлены, что пропущено
   и почему (конфликт / решение пользователя), что осталось руками. Слой проекта без
   роли-владельца — строкой со ссылкой на `/beerpowers:doctor`, п. 14: состав — не зона update.

Повторный запуск на проекте, собранном текущей версией и не правленом руками, не меняет
ни одного файла — это проверка самого update.

## Субагенты и модель

Шаги 3 и 5 team-lead может раздать субагентам `general-purpose` — на большой миграции (перевод
с qtim, десятки файлов) это дешевле, чем держать всё в своём контексте. Субагент пишет черновик
в scratchpad; в файлы проекта — team-lead, после подтверждения шага 4. Модель — по тому, чем
проверяется черновик:

- **механическое — `model: sonnet`, effort `medium`:** замена engine-блоков по маркерам, сверка
  и перезапись копий, пункты записи миграции без суждения (README, уборка, ключи `workspace.json`).
  Проверка — машиной: вне маркеров дифф файла пуст, копия совпадает с плагином побайтно
  (`/beerpowers:doctor`, п. 6);
- **перенос проектного текста — модель сессии, `model` не передаётся:** запись `→ 2.0.0`
  (граница блока находится сравнением текста, а не по маркеру), раскладка памяти по виду знания,
  конфликт в engine-блоке. Ошибка здесь молча теряет или искажает проектный текст, и поймать её
  можно только чтением, а не сверкой.

## Critical Rules

1. **Знания в `memory/` и `.claude/agent-memory/` — данные проекта:** update меняет в памяти
   только engine-блоки по маркерам; записи, таблицы проекта и файлы без маркеров не трогает.
2. **Не задавай заново вопросы setup (Q0–Q9)** — ответы уже материализованы. Запись миграции
   вводит новый параметр — один точечный вопрос или дефолт контракта с пометкой в плане.
3. **Канон рантайма:** никаких `TeamCreate`/`TeamDelete`/`team_name` в мигрированных файлах.
4. **Плейсхолдеры `{{...}}` в проект не попадают:** engine-блоки их не содержат по контракту,
   а вне блоков update ничего из шаблона не переносит.
5. **Не запускай** lint/tests/migrations и не коммить: коммит миграции делает team-lead после
   отчёта, одним коммитом — его откат и есть откат миграции.
