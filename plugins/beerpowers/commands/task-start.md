# /beerpowers:task-start — задачи в работу

Перед разбором прочитай `.claude/team-lead.md`, если в этой сессии ещё не читал: класс задачи,
стопоры, effort ролей, порядок гейтов и закрытие описаны там, а не в charter.

Каталоги `projects/`, `worktrees/`, `memory/tasks/` — константы движка, контракт —
[`workspace.md`](../reference/workspace.md).
Ветки, база и профили репозиториев — [`git-flow.md`](../reference/git-flow.md).

```
/beerpowers:task-start <задача> [<задача> …] [--preview] [--worktree] [-- <флаги проекта>]
```

Всё после `--` — флаги проектной подготовки рабочего дерева (что умеет проектный
`.claude/bin/worktree-setup`, смотри его `--help`). Зависимости ставит сам `worktree-add`,
по lock-файлу, без флагов.
Команда их не разбирает, а передаёт как есть в каждый вызов `worktree-add` этого запуска,
тот — в `worktree-setup`. Worktree не заводится — флаги не нужны и молча не теряются:
скажи пользователю, что они не применились.

`<задача>` — `<КОД>` или `<КОД>@<релизная-ветка>`. Релизная ветка привязана к задаче, не к вызову,
и действует в тех репозиториях задачи, где она есть на `origin`: `<КОД>@<релизная>` у фуллстек-задачи
даёт бэкенд от релизной, если она есть только там, и фронт по профилю. Нет её нигде — спросить,
в каком репозитории завести. Без `@` база выбирается в шаге 4.

**Задач в вызове может быть несколько** — каждая проходит шаги сама по себе, а разбор
дополнительно называет связи между ними. Новые и уже начатые задачи в одном вызове
смешиваются свободно: путь каждой выбирается по её папке (раздел «Возобновление»). Перед
сборкой релиза так проверяют все входящие задачи разом — с `--preview`, чтобы ничего
не писать.

## Режимы

| Вызов | Что делает |
|---|---|
| без флагов | весь путь: постановка, разбор, класс, артефакты `memory/tasks/<КОД>/`, ветки от нужных баз, dry-run постановки, передача команде по классу — lean и фича через [`/beerpowers:team-lazy`](team-lazy.md), тривиальная — team-lead сам |
| `--preview` | только разведка: постановка, разбор, класс, развилки — ничего не пишет и никого не поднимает |
| `--worktree` | отдельный рабочий каталог, даже если репозиторий свободен |
| папка `memory/tasks/<КОД>/` уже есть | возобновление: постановка перевыгружается, разница показывается и сверяется со сделанным; ветки и артефакты не заводятся заново |

Дефолт — работа: это самый частый вызов. На незнакомой задаче — `--preview`: разбор
и развилки видны до того, как роли начали работать и тратить бюджет. Других режимов нет
намеренно: класс задачи решает и состав артефактов, и состав ролей, а полный прогрев
[`/beerpowers:team-up`](team-up.md) не нужен — в `team-lazy` недостающие роли доспавниваются по ходу.

## Источник постановки — по форме аргумента

| Форма | Источник |
|---|---|
| `PROJECT-NNN` | трекер задач — скриптом трекера в `.claude/bin/` (Яндекс Трекер — `yandex-tracker`); скрипта в проекте нет — постановку даёт человек |
| описательное имя (`fix/header-scroll`) | постановка от пользователя в этой сессии либо пункт `memory/tech-debt/tech-debt.md` целиком |

Меняется только шаг 1. Разбор, `git-flow.md`, стоп-условия, база ветки, отдельный коммит
артефактов обязательны всегда: **задача без трекера не значит задача без правил.**

## Возобновление — папка задачи уже есть

Выгрузка постановки — снимок: задачу в трекере правят и комментируют, а `tracker/task.md`
остаётся прежним, и команда молча делает то, что просили неделю назад. Поэтому папка
`memory/tasks/<КОД>/` есть — задача не заводится заново, а возвращается в работу. Шаги 1, 3 и 4
для неё заменяются этим разделом; разбор (шаг 2), отчёт и передача (шаги 5–6) — как обычно.

1. **Ветки и артефакты не трогаются.** `preflight.md`, `git-flow.md` и прочее не переписываются;
   ветки из `git-flow.md` проверяются фактом — недостающую завести по шагу 4.
2. **Перевыгрузить постановку** — если задача из трекера и скрипт есть. Вложения под
   gitignore, и разницу по ним git не покажет — её печатает сам скрипт: строки «вложение
   добавлено / заменено / удалено».

   ```bash
   .claude/bin/yandex-tracker <КОД> --comments --save memory/tasks/<КОД>/tracker
   git diff -- memory/tasks/<КОД>/tracker/task.md
   ```

   С `--preview` выгрузка не перезаписывается — свежая версия идёт в кеш, разница та же:

   ```bash
   .claude/bin/yandex-tracker <КОД> --comments --out .claude/.cache/task-start/<КОД>.md
   git diff --no-index -- memory/tasks/<КОД>/tracker/task.md .claude/.cache/task-start/<КОД>.md
   ```

   Выгрузки `tracker/task.md` нет — задачу начали без трекера или без скрипта — сравнивать
   не с чем: так и сказать и пересказать постановку целиком. Задача не из трекера — её
   постановка в `preflight.md` и меняется человеком: спросить, что изменилось.
3. **Пересказать разницу по смыслу, а не построчно:** изменилось ли требование и какая
   сделанная работа от этого стала лишней или неверной; новые пункты объёма; статус
   и исполнитель; что нового в комментариях — ответ на открытую развилку, отмена решения,
   просьба подождать; новые и удалённые вложения. Ничего не изменилось — одной строкой,
   это нормальный исход.
4. **Сверить со сделанным.** Противоречие с уже сделанным назвать явно. Изменение постановки —
   в `preflight.md` цитатой из трекера с датой и автором, следствие для объёма рядом своими
   словами. Ломает утверждённый дизайн — задача для `architect`: отступления от плана ведёт он,
   в `plan-delta.md`. Комментарий закрыл развилку из `preflight.md` — отметить её закрытой,
   с датой и автором ответа.
5. **Коммит выгрузки** — отдельным коммитом артефактов, как в шаге 5; сообщение говорит, что
   изменилось в постановке, а не «обновил файл»:
   `docs(<КОД>): постановка обновлена — добавлен пункт про подкатегории`.

Dry-run постановки (шаг 6) повторяется, только если постановка изменилась по существу.

## 1. Прочитать постановку

Формы ниже — для Яндекс Трекера (`.claude/bin/yandex-tracker`); скрипт другого трекера
пишет в тот же каталог `tracker/`.

```bash
.claude/bin/yandex-tracker <КОД> --comments
```

Комментарии читаются всегда — в ленте живёт то, чего нет в описании; длинная лента сужается
`--comments-limit N`, не выключается (`memory/commands/yandex-tracker.md`). Задачи нет или доступ
не прошёл — стоп, сказать пользователю; постановку из имени ветки не выдумывать.

Скрипта трекера в проекте нет — постановку даёт человек: попросить текст
задачи и комментарии, дальше как с постановкой от пользователя.

Из техдолга: пункт берётся целиком и остаётся на месте до изменения кода. От пользователя:
суть, критерий приёмки и границы объёма идут в `preflight.md` до начала работы — сказанное
в чате исчезает вместе с сессией.

## 2. Разобрать

По каждой задаче:

- **что требуется** — абзацем, своими словами;
- **класс** по charter — тривиальная, lean или фича — с признаком, по которому выбран:
  «lean: одна зона `Catalog`, миграций и денег нет». Класс задаёт состав гейтов и режим
  передачи; стопоры рекласса — `.claude/team-lead.md`, «Класс задачи»;
- **открытые развилки** — чего постановка не решает и что ждёт людей вне команды;
- **стоп-условия** — что обязано быть верным до старта;
- **что задача НЕ закрывает**, если сказано;
- **связь между задачами**, если их несколько: кто от кого зависит, общий контракт API,
  порядок мержа — у парных бэк-фронт он обратен порядку разработки.

Дописанное пользователем после флагов — часть постановки, а не реплика: учесть в разборе
и пересказать в отчёте. Противоречит постановке — назвать расхождение, решает человек.

С `--preview` — на этом всё.

## 3. Завести артефакты

Класс **тривиальная** — артефакты не заводятся, кроме одного случая: база не по профилю
(`@<релизная-ветка>`, ветка предшественника) — тогда `git-flow.md` с одной таблицей. Базу
задачи скрипты влитости (`workspace-clean`, `tasks-status`, `/beerpowers:retro`) берут только
из него: без файла ветка от релизной висит невлитой, пока релиз не уйдёт в ветку по умолчанию.
В остальном team-lead читает постановку из трекера на лету, делает правку и коммит; уточнения
из чата живут в той же сессии. Сработал стопор рекласса в lean — артефакты заводятся в этот
момент, уточнения переписываются в `preflight.md` из чата дословно.

Для lean и фичи:

```bash
.claude/bin/yandex-tracker <КОД> --comments --save memory/tasks/<КОД>/tracker
```

Не из трекера или скрипта нет — `tracker/` не создаётся. Дальше, **только если есть что
сказать**, пустые файлы не заводятся:

- `git-flow.md` — база не по профилю хотя бы в одном репозитории (релизная, ветка
  задачи-предшественника), срочный выпуск в `dev-default`, зависимость от другой задачи — или
  репозиторий со своим флоу (`custom`): для него база пишется всегда, по `memory/commands/git.md`.
  Формат и «Зависимости» — [`tasks-layout.md`](../reference/tasks-layout.md);
- `preflight.md` — стоп-условия, класс задачи и всё, что пользователь дописал после флагов:
  **дословной цитатой с датой**, следствие для объёма рядом своими словами (форма — `team-lead.md`,
  «Сказанное в чате живёт до конца сессии»).

## 4. Завести ветки

Для всех классов, включая тривиальную: MR без ветки не бывает, push в ветку по умолчанию
закрыт хуком.

База — для каждой задачи и каждого репозитория отдельно, по [`git-flow.md`](../reference/git-flow.md),
«База задачи»: названа `@<релизная-ветка>` — она (нет на `origin` — создать и отправить); иначе
team-lead решает **по смыслу**: зависит ли задача от невлитой фичи — нужен ли ей её код или
контракт. Зависит — база её ветка; нет — по профилю репозитория. Конфликты критерием не служат.
Выбранная база и причина называются пользователю одной строкой до того, как заводятся ветки,
и пишутся в `git-flow.md` задачи, если они не по профилю. Проверка — `node .claude/bin/git-base.mjs
<репо> <КОД>` печатает то, от чего будет расти ветка. Задача в нескольких репозиториях — ветка
в каждом.

| Условие | Что делать |
|---|---|
| репозиторий свободен, флага нет | ветка в рабочем каталоге |
| репозиторий занят другой задачей | worktree обязателен |
| передан `--worktree` | worktree |

Занятость проверяется фактом: `git -C <репо> status --short` непусто или
`git -C <репо> branch --show-current` не ветка по умолчанию и не база задачи.

Worktree заводится скриптом, не голым `git worktree add`:

```bash
.claude/bin/worktree-add <репо> <КОД-ЗАДАЧИ> [<база>] [-- <флаги проекта из вызова команды>]
```

Файлы окружения — только по `--copy-env`, и разрешает копию человек, а не скрипт: спросить,
не подставлять флаг самому. Зависимости `worktree-add` ставит сам по lock-файлу (`pnpm-lock.yaml`, `package-lock.json`, `composer.lock`), копированием — никогда; `--no-deps` — когда дерево нужно только читать. Проектная подготовка (тестовая база и подобное) — проектный `.claude/bin/worktree-setup`, `worktree-add` зовёт его сам; его флаги — после `--` в вызове этой команды. Раскладка
`worktrees/<КОД>/<имя-репо>/` и почему имя каталога критично —
[`worktrees.md`](../reference/worktrees.md); цена worktree и грабли этого workspace —
`memory/commands/worktrees.md`. Убирается потом [`/beerpowers:worktrees-clear`](worktrees-clear.md).

## 5. Отчитаться

Таблица по задачам: код, репозитории, флоу и база, класс, где артефакты, заведены ли ветки.
Ниже — развилки и чего не хватает для старта. Артефакты — **отдельным коммитом**, правило
`memory/tasks/**` (`.claude/reference/git-flow.md`, «Коммиты»).

## 6. Передать команде

Класс **тривиальная** — передавать некому: team-lead делает правку сам, без dry-run и ролей,
и называет пользователю, что проверено и что нет (`.claude/team-lead.md`, «Класс задачи»).

**Dry-run постановки** — для классов lean и фича, перед первым исполнителем. Агент
со свежим контекстом (`general-purpose`, sonnet, `medium`, промпт по `.claude/team-lead.md`,
«Бриф роли») получает **только** файлы `memory/tasks/<КОД>/` и доступ
к репозиторию — ни пересказа, ни истории чата — и отвечает на три вопроса: какой шаг сделал
бы первым; какие вопросы задал бы автору постановки, таблицей с критичностью блокер / попутно /
косметика; какие места читаются двояко — чтение А, чтение Б, что взял бы по умолчанию.
Архитектурные советы и догадки за автора запрещены.

| Ответ на вопрос | Что делать |
|---|---|
| есть в файлах задачи, но не там, где искал | перенести или продублировать указателем |
| есть только в чате или в голове team-lead'а | записать в `preflight.md` дословно с датой |
| нет нигде | решить и записать либо вынести пользователю развилкой |

Критерий прохода — ни одного вопроса класса «блокер до старта». Неверный «первый шаг» —
признак плохо описанного порядка работы или зависимостей. Пустой отчёт на крупной задаче
подозрителен сам по себе.

**Передача — [`/beerpowers:team-lazy`](team-lazy.md):** роли поднимаются по требованию,
недостающие доспавниваются по ходу, когда появляется петля ревью или теста. Полный прогрев
`/beerpowers:team-up` отсюда не вызывается. Правила режима не пересказывать, читать его файл.

Промпт роли получает **пути к артефактам, а не пересказ задачи**:

> Задача `<КОД>`, класс lean. Постановка — `memory/tasks/<КОД>/tracker/task.md`,
> вложения — `tracker/task-attachment/`. База и дифф — `node .claude/bin/git-base.mjs <репо> <КОД>`.
> Стоп-условия и уточнения — `preflight.md`.

Несколько задач — порядок спавна по «Зависимостям»: сначала та, чей контракт нужен остальным.
Парные бэк-фронт не параллельно, если фронт ждёт ответа бэкенда, — иначе код под выдуманный
контракт.

## Чего команда не делает

С `--preview` — не правит код и не поднимает роли: показывает разбор и останавливается.
Без флага разделение обязанностей прежнее: код пишут роли (в тривиальной — team-lead),
git — team-lead.
