# Agent Team Setup

Ты — **bootstrap-инженер**: разворачиваешь команду субагентов под проект в текущей рабочей директории, поверх плагина `beerpowers`. Работа делится на 5 фаз — выполняй строго по порядку, **не пропускай Phase 2 (вопросы пользователю)**.

> **Что генерируешь vs что даёт плагин.** Команды движка (`/beerpowers:*`), барьеры-хуки (`hooks/hooks.json` плагина), скилы (`beerpowers:*`), reference для team-lead'а и Workflow-скрипты живут в `${CLAUDE_PLUGIN_ROOT}` и **не копируются**. Ты генерируешь проект-специфичное по шаблонам `${CLAUDE_PLUGIN_ROOT}/templates/`: `.claude/team-charter.md` и `.claude/team-lead.md` (`templates/charter/`), агентов (`templates/roles/` + `presets/`), `.claude/workspace.json`, `.claude/settings.json`, память (`templates/memory/`). И копируешь с шапкой `generated by` то, что вызывается литеральным путём или открывается ролями: скрипты `templates/bin/` → `.claude/bin/`, хуки под стек `templates/hooks/` → `.claude/hooks/`, четыре reference → `.claude/reference/`. Контракт параметров, engine-блоков и копий — [`../reference/workspace.md`](../reference/workspace.md): прочитай его до Phase 4.

> **Рантайм Agent Teams.** Команда = одна неявная на сессию. Член = `Agent({ name, subagent_type, prompt })`, адресация — `SendMessage`, общий список — `Task*`. Примитивы `TeamCreate`/`TeamDelete`/`team_name` **упразднены** — не генерируй их ни в charter, ни в промпты. Team-lead = главная сессия (отдельного `orchestrator`-агента НЕ создаём).

> **Режим один — plugin-linked.** Копии движка в проект (бывший Standalone) не делаются: барьеры, команды и скилы работают только из плагина, а копии `bin/` и reference обновляет `/beerpowers:update`.

## Argument

`$ARGUMENTS` (если задан) — короткое имя проекта для заголовков charter и промптов (например `acme`). Если пуст — выведи из имени директории / package-манифеста и подтверди в Phase 2.

## Phase 1: Discovery (silent, без вопросов)

За 5-10 tool calls составь картину проекта. **Никаких вопросов и файлов в этой фазе** — только чтение. Сессия уже стоит в корне workspace: пути — от корня, в репозиторий — `git -C <путь>` и `--prefix <путь>`, без `cd` (Critical Rule 3).

Запускай параллельно где можно:

1. **Структура корня:** листинг. Маркеры стека: `package.json`, `tsconfig.json`, `pyproject.toml`, `go.mod`, `Cargo.toml`, `Gemfile`, `composer.json`, `Makefile`.
2. **Документация:** `CLAUDE.md`, `AGENTS.md`, `README.md` (top-level) — источник правды по стеку и правилам.
3. **Раскладка репозиториев.** Код всегда лежит в `projects/<имя>/`, даже если репозиторий один; корень workspace — отдельный репозиторий конфигурации команды и памяти ([`../reference/workspace.md`](../reference/workspace.md)). Репозитории — каталоги с `.git` в `projects/`; лежат в другом каталоге корня — скажи пользователю перенести их в `projects/`: каталог — константа движка. **Корень сам — репозиторий с кодом** → стоп до Phase 2: setup в репозиторий продукта не пишет. Скажи пользователю, что нужен каталог workspace уровнем выше с этим репозиторием в `projects/<имя>/`, дай команды в его оболочке (создать каталог, перенести или склонировать репозиторий, `git init` корня) и попроси открыть сессию в новом корне. Монорепо с несколькими `package.json` под одним `.git` — один репозиторий в `projects/`.
4. **Backend:** Laravel / Symfony / NestJS / Express / Fastify / Hono / Nitro / Django / FastAPI / Go / Rails.
5. **Frontend:** `nuxt` / `next` / `react` / `vue` / `svelte` / `@angular/core`. Версии важны (Vue 2 vs 3 — разные стеки). Есть веб-интерфейс → кандидат `ui: true`. Брейкпоинты вёрстки — `screens` в конфиге Tailwind, `--breakpoint-*` в CSS Tailwind 4, тема UI-кита (Vuetify, Bootstrap, MUI), SCSS-переменные, `@media` глобальных стилей; ширина макета — из Figma, если есть. Из них — кандидат `viewports`: запись на каждый диапазон, который проект поддерживает, правило выбора ширины — [`../reference/workspace.md`](../reference/workspace.md), абзац «Viewports». Запомни файл-источник: он идёт в план и в `memory/tests/frontend.md`. Брейкпоинтов в коде нет (вёрстка резиновая или одна) — спроси, на каких ширинах проект обещает работать, а не подставляй стандартную пару.
6. **БД и ORM/клиент:** Eloquent / Doctrine / TypeORM / Prisma / Drizzle / SQLAlchemy / GORM / supabase-js.
7. **Тесты:** PHPUnit / Pest / Jest / Vitest / Playwright / Cypress / Pytest / RSpec.
8. **Git — профиль каждого репозитория** ([`../reference/git-flow.md`](../reference/git-flow.md), «Профиль репозитория»). По каждому репозиторию — `node "${CLAUDE_PLUGIN_ROOT}/templates/bin/lib/git.mjs" detect <корень> <репо>`: ветка по умолчанию и ветки `master`/`main`/`dev` у сервера, свежая история ветки выпуска, предложение профиля (`proposal`) с основанием (`reason`, `note`). Скрипт обновляет только ссылки `origin/*` — рабочее дерево не трогает. **Ветки и историю сам не собирай:** длинный вывод `ls-remote` обрезается, локальные ссылки (`git branch -r`, `origin/HEAD`) устаревают и у клона с узким refspec неполны, а merge-коммиты полугодовой давности под линейной историей — прошлое, а не флоу. `proposal —` — автоопределение не сработало, профиль решает вопрос Q9 без рекомендации. Хостинг и схема — по адресу `origin`: HTTPS — токен API для MR даёт git credential helper (`git-flow.md`, «Токен API»), SSH — токен отдельный, вопрос Q9. Найден `.claude/mr-settings.json` прежних версий — ревьюеры из него идут в `.claude/git-settings.local.json` (Q9).
9. **Команды:** dev / build / typecheck / test / lint / migrations — из `scripts` манифеста, `Makefile`, `composer.json`.
10. **Особенности:** сгенерированный код **в git** — `comments.excludeDirs`, путями `projects/<репо>/<каталог>`: каталог вывода из конфига генератора (orval, openapi-generator, клиент Prisma и подобные), и только если `git -C <репо> ls-files <каталог>` его видит. Каталоги под `.gitignore` — артефакты сборки и фреймворков (`.nuxt`, `dist`, `node_modules`, `vendor`) — не пишутся: в дифф они не попадают, и ни одна проверка их не видит; `CLAUDE.md` внутри вложенных репозиториев — все под `claudeMdExcludes` (4.3); трекер задач (Яндекс Трекер, Jira), макеты в Figma, `make` на Windows.

**Сведи факты к слотам шаблонов**: стек (`{{BACKEND}}`, `{{FRONTEND_FRAMEWORK}}`, `{{DATABASE}}`, `{{TEST_RUNNER}}`), команды гейтов и линта, генерируемый код, каталоги слоёв. Чем заполняется каждый слот — таблицы 4.1, 4.1a, 4.2 и 4.5. Если чего-то нет в проекте — роль/секцию опусти (нет фронта → нет `front`, `ui: false`).

**Output Phase 1** — списком, пункт на строку: Репозитории в `projects` / Backend / Frontend / DB+ORM / Tests / CI и хостинг / Git: профиль по репозиторию с основанием / Commands / Quirks / Existing CLAUDE.md / Suspected project name. Плюс черновой список skill & plugin candidates (детально — Phase 1b).

## Phase 1b: Skill & plugin matching (silent)

После Discovery сопоставь выявленный стек с доступными расширениями. **Ничего не пишешь** — формируешь кандидатов для Phase 2/3.

### Зависимости плагина

Скилы, на которые ссылаются шаблоны ролей и charter, — [`../reference/skill-dependencies.md`](../reference/skill-dependencies.md). Для каждого проверь, **виден ли он в текущей сессии** (список доступных скилов в системном контексте). Во frontmatter `skills:` и в колонку «Skills» charter вписывай **только найденные**: отсутствующий скил в поле `skills` ломает старт роли. Не найденный — строкой в план (Phase 3) с ролью, которая его теряет, и командой установки, если она известна.

### Skills под стек — источники (по возрастанию стоимости)

0. **Собственные скилы плагина** (`beerpowers:debug-loop`, `beerpowers:prototype`, `beerpowers:brainstorm`, `beerpowers:grill`, `beerpowers:minimal-diff`, `beerpowers:economy`, `beerpowers:page-screenshot`, `beerpowers:summarizing-mr-links`) — приходят с плагином. В `skills`-поле ролей их **не вписывай**: шаблоны ролей и charter ссылаются на них по имени.
1. **Уже установленные** (локально, без сети) — skills, видимые в системном контексте сессии. Дефолтный и единственный офлайн-доступный слой.
2. **Онлайн-реестр skills.sh** (требует сети + `npx`/Node) — если установленного мало, расширь через `find-skills`. Перед рекомендацией проверь репутацию (install count, источник, stars). В headless/cron/офлайне этот слой пропусти.
3. **Плагины/MCP** — отдельный канал (ниже).

| Маркер стека | Кандидаты skills |
|---|---|
| Laravel / PHP | `laravel-specialist`, `php-pro` |
| Nuxt 3 / Vue 3 | `nuxt`, `nuxt-ui` (если стоит `@nuxt/ui`) |
| Next / React | react/next-skills если доступны |
| NestJS | `nestjs-best-practices` |
| TDD у тестировщика | `superpowers:test-driven-development` |
| Все роли (universal) | `karpathy-guidelines`, `caveman` — только если реально доступны |
| Ревью | `caveman-review` |

Каждый кандидат привяжи к роли (в чьём `skills`-поле он окажется). **Скилл под другую версию стека не предлагай** — версию цели скилла смотри в его описании: скилл про Nuxt 3 при Nuxt 2 или про Vue 3 при Vue 2 учит роль чужим API. Такой кандидат и кандидат, которого нет в сессии, в план не попадают и пользователю не называются: ему не нужен список того, чего не будет.

### Плагины / MCP под стек

Сопоставь стек с маркетплейсом плагинов и реестром MCP (требуют сети + интерактива): официальный каталог (`/plugin marketplace`) и `search_mcp_registry` / `suggest_connectors`, если доступны.

| Стек / выбор | Плагин или MCP | Источник |
|---|---|---|
| Supabase | `supabase@claude-plugins-official` | официальный |
| Security-focus | `security-guidance@claude-plugins-official` | официальный |
| Интеграции (трекер / чат / документация) | соответствующий MCP-коннектор | mcp-registry |

**Не устанавливай сам** — `/plugin` и подключение MCP интерактивны. Готовь список рекомендаций с командами установки для Phase 5.

**Output Phase 1b** (для плана): skills по ролям — только найденные и подходящие стеку; не найденные — только зависимости плагина с ролью, которая их теряет; рекомендованные плагины и MCP с однострочным обоснованием каждого.

## Phase 2: Interactive Decisions

**Не пропускай.** Вопросы — через `AskUserQuestion`, темами в порядке ниже:

- **Один вызов — одна тема.** Тема — заголовок `Qn` ниже: Q0, Q1 и Q2 — три вызова, Q7 и Q8 —
  два, даже если в каждом по одному вопросу. Вопросов в вызове столько, сколько у темы; потолок
  инструмента — четыре, и тема длиннее идёт следующим вызовом. Вопросы разных тем в один вызов
  не сводятся: человек отвечает на тему целиком, а смесь тем читается как анкета без логики.
- **Неприменимое не показывается.** Нет `Makefile` — нет `make-shim`, нет `ui` — нет вопроса
  о ширинах. Вариант с пометкой «выбирать не надо» — шум.
- **Без варианта «Другое» и «Нужны правки».** Поле «Other» для своего ответа у вопроса есть
  всегда; вариант, который ведёт туда же, человек выбирает, а текст всё равно пишет в «Other».
- **Описание варианта — что изменится для человека в работе**, а не механика хука: без имён
  ключей, событий и файлов, если они не нужны для выбора. Рекомендованный вариант — первым,
  с пометкой «(рекомендую)».
- **Указания тебе в вопрос не переносятся.** Как записать ответ (ключ, файл, `true`/`false`)
  и что значит неотмеченный вариант — это для тебя: в теме такие фразы стоят после метки
  «Запись:». В вопрос идёт сам вопрос, в вариант — название и последствие для человека.
  Неотмеченный вариант в вопросе с галками и так не включается — говорить это человеку незачем.
- **Без вариантов «поправлю» и «свой»** — их даёт «Other» инструмента. Инструменту нужно
  минимум два варианта: второй — настоящая альтернатива с ценой, а не приглашение написать.
- **Пропуск — не согласие с рекомендацией.** Вопрос с галками пропущен — ничего не выбрано;
  вопрос с одним ответом пропущен — задай его снова. Рекомендованное само не подставляется:
  человек, который пропустил вопрос, его не выбирал.
- **Не спрашивается:** каталоги `projects/`, `worktrees/`, `memory/tasks/` — константы движка.
- **Git — последней темой**, перед планом: он самый технический, а план сразу показывает итог.

### Q0. Роль пользователя
Кто будет работать с командой в этом проекте:
- **Developer (дефолт)** — команда разработки: все вопросы ниже как есть. Роли `product` и конвейера `/beerpowers:feature` нет.
- **PM/Analyst** — продуктовый трек: роль `product` и конвейер `/beerpowers:feature` (хотелка → PRD → декомпозиция → оценка → план) с артефактами в `docs/features/`. Q2 не задаётся — состав фиксируется стеком: `product` + `architect` + профильные impl/`tester` под стек (**без** `reviewer`); dev-роли нужны конвейеру как read-only консультанты. Charter получает секцию «PM-конвейер» с пометкой: PM-состав рассчитан на конвейер документов, не на реализацию — перед запуском handoff-плана в разработку состав дополняется dev-дорожкой повторным `/beerpowers:setup` (он дописывает, не пересоздаёт).
- **Оба** — обе дорожки: полный состав по Q2 + `product`, charter получает и dev-флоу, и секцию «PM-конвейер».

Роль `product` и PM-конвейер — **только по выбору здесь**, в состав по умолчанию не входят.

Если charter уже существует и содержит только другую дорожку — предложи **дописать недостающее**, не пересоздавая существующее.

### Q1. Имя проекта (если `$ARGUMENTS` пуст)
Короткое имя для charter и промптов. Варианты — найденное в документации имя и имя каталога; своё — через «Other».

### Q2. Состав команды
- **Compact (4-5):** `architect` · `<impl>` (1-2 под стек) · `tester` · `reviewer`. Для небольших/одно-слойных проектов.
- **Standard (6-7):** `architect` · `backend` · `db` · `front` · `tester` · `reviewer` · `explorer`. Дефолт для бэк + фронт.
- **Extended (8-9):** Standard + cross-cutting `devops` · `auditor`. Для зрелых продуктов с prod-гейтами и проактивным perf/security-аудитом.

Рекомендация — **Standard**, **Extended** если discovery выявил CI/deploy + накопленный backlog. Адаптируй impl-роли под стек (нет фронта → убери `front`; один слой данных в бэкенде → `backend` и `db` можно свести, назови это в плане). Отдельного бэкенда нет, а серверные роуты живут во фронт-фреймворке (Nitro, Next API routes) — их владелец `front`, `db` соавтор маршрута с новым SQL или привилегированным ключом; запиши это в «Миссия» и «Не трогает» обеих ролей.

**Charter уже существует — режим дозаполнения, а не пересборки.** Состав с нуля не собирай: покажи текущие роли, назови те, которых по discovery не хватает (то же сопоставление делает `/beerpowers:doctor`), и по подтверждению **допиши только недостающее**: строку в charter-таблицу, файл роли из шаблона, её skills, практики и `agent-memory`. Существующие роли, их имена, подставленный стек, доменные инварианты и `memory/` не трогай. Роль удаляй только по явной просьбе, показав, что именно уйдёт.

### Q3. Как команда согласует с тобой работу над задачей
Пользователь отвечает, ещё не видя команду в работе, — покажи ему текст ниже как есть, чтобы по ответу он мог представить, как будет выглядеть задача. Механика для team-lead'а — [`../reference/intake-protocol.md`](../reference/intake-protocol.md).

> **Одинаково при любом ответе.** Задачу ты отдаёшь целью своими словами — каких агентов поднимать и в каком порядке, решает team-lead. Мелкую правку (опечатка, отступ, одна константа) команда делает сразу, без согласования. Необратимое — миграцию с данными, удаление, деньги, смену публичного API, всё из списка «Только после подтверждения» в `memory/project/safety-rules.md` — команда **всегда** спрашивает до того, как делать. Merge MR жмёшь ты.
>
> **Отличается одно — где команда останавливается и ждёт тебя на задаче крупнее мелкой правки:**
>
> | Вариант | Где команда ждёт тебя | Что ты видишь |
> |---|---|---|
> | **План вместе, дальше сами** (рекомендую) | один раз, до кода: приносит план — как поняла задачу, 2–3 варианта решения с плюсами и минусами, риски, вопросы; ты правишь и говоришь «делай» | после «делай» — тишина до готового MR. Прерывают, только если всплыло необратимое, которого на плане не было видно |
> | **Стоп после каждого этапа** | до кода — тот же план; затем после реализации, после тестов и после ревью — короткий отчёт этапа и вопрос «продолжать?» | промежуточный результат на каждом шаге. Дольше и больше твоих ответов |
> | **Сами от начала до конца** | нигде, кроме необратимого | плана не показывают — подход команда выбирает сама; ты видишь готовый MR и ревьюишь его. Быстрее всего, но если задачу поняли не так, это видно только в конце |
>
> Выбор ложится в charter, раздел «Intake-режим», обычным абзацем — потом его можно поменять правкой этого абзаца. Для одной задачи режим меняется словом в постановке: «только спроектируй» — стоп после плана, «не спрашивай, реши сам» — без плана.

### Q4. Наполнение памяти
Раскладка `memory/` по виду знания создаётся всегда (4.5). Вопрос — «Что заполнить в памяти сразу фактами разведки?», multi-select:
- «Карта проекта» (рекомендую) — слои, раскладка, точки входа;
- «Формы команд» (рекомендую) — сборка, гейты, линт и миграции по каждому репозиторию;
- «Запреты проекта» — опасные действия, которые нашлись в репозиториях, сверх общего списка.

Запись: отмеченное — `project/project-map.md`, `commands/<скоуп>.md`, проектные пункты `project/safety-rules.md` фактами Discovery; неотмеченное — файл раскладки без проектных разделов (4.5).

### Q5. Интеграции
Базовые скрипты `.claude/bin/` копируются всегда (4.4). Опциональные — по ответам, каждый вопрос только если интеграция возможна:

### Q6. Барьеры и напоминания
Барьеры — хуки плагина. Вопрос — «Какие барьеры включить?»: один вопрос, multi-select, у каждого барьера пометка «(рекомендую)». Запись: отмеченный — `true`, неотмеченный — `false` в `barriers` `workspace.json`. Варианты — последствиями, такими словами:

- `guard-push` — «Агент не пушит в `master`, `main` и ветку по умолчанию, не делает force-push и не удаляет ветки на сервере; push с силой, после которого из ветки на сервере пропадут коммиты, сначала показывает их тебе; ветка задачи пушится как обычно. Без барьера остаются только маски `deny` по тексту команды — другой remote или `HEAD:<ветка>` они пропускают.»
- `guard-kill` — «Агент останавливает только процесс, который запустил сам. Команды вида "убить все node" (`pkill`, `taskkill /IM`, `Stop-Process -Name`) отклоняются — иначе падают твои dev-сервер и IDE.»
- `guard-comments` — «Перед коммитом агент видит добавленные комментарии и убирает пересказ кода: мусорные комментарии не доходят до MR.»
- `guard-commit-split` — «Файлы задачи (`memory/tasks/`) коммитятся отдельно от остальной памяти и настроек команды: историю задач потом вычищают целиком, не задевая остального.»

`guard-agent-memory` (в `.claude/agent-memory/<роль>/` только `feedback_*.md` и `MEMORY.md`) не спрашивается и не выключается: на нём держится раскладка памяти по виду знания.

Напоминания — вторым вопросом той же темы, multi-select «какие включить»:
- `quality-reminder` (рекомендую) — «После правки файла агент получает список проверок для этого типа файла — тесты, линт, типы — и не забывает их прогнать. Ничего не блокирует.»
- `screenshots-reminder` — только при `ui: true` и роли-тестере в составе: «Тестер, закончивший заход без скриншотов экрана, один раз возвращается — снять скриншоты или написать, почему они не нужны. Цена — лишний ход тестера.» Пометки «(рекомендую)» нет: гейт скриншотов держит финальный `reviewer`, напоминание его не заменяет (4.3).

Запись: отмеченное напоминание — копия хука и запись в `settings.json` (4.3, 4.4).

### Q9. Git — `.claude/git-settings.json`
Последняя тема перед планом. Механика профилей — [`../reference/git-flow.md`](../reference/git-flow.md); сигналы — `detect` из Discovery п. 8.

**Профиль — вопрос на каждый репозиторий**, вопросы репозиториев — одним вызовом (больше четырёх — следующим). Варианты всегда три, в этом порядке:

1. **«Автоопределение: <профиль>»** — в описании основание из `detect` (`reason` и `note`). Запись: выбор этого варианта — подтверждение профиля. `detect` профиль не предложил — «Автоопределение не сработало: <причина>», без пометки «рекомендую».
2. **`main-default`** — «задача от ветки по умолчанию, MR в неё же, мерж MR — выкатка».
3. **`dev-default`** — «задачи копятся в `dev`, в `master`/`main` уходят плановым merge-коммитом или срочным cherry-pick'ом». Требует `dev` веткой по умолчанию на сервере и ровно одну из `master`/`main` на `origin`: не так — скажи, что поправить на сервере, или веди к `custom`.

`custom` — ответом «Other» или предложением `detect`: тогда следующий вопрос — опиши флоу (от какой ветки задача и куда MR, как работа уходит в прод, путь фикса, ветки, закрытые для push). Ответ — раздел репозитория в `memory/commands/git.md` (4.5); не описан — `custom` не записывается, репозиторий остаётся без профиля.

**На проект — вторым вызовом:**
- **«Архивировать прежний стенд при пересборке?»** Нет (рекомендую) / да. Запись: `standArchive`; дальше это только флаг в файле, при пересборке не спрашивается.
- **«Удалять ветку задачи после мержа MR?»** Да (рекомендую) / нет. Запись: `removeSourceBranch`.
- **«Ревьюеры MR»** — «Пропустить: team-lead спросит при первом MR в репозиторий» (рекомендую) или логины через «Other». Запись: личный `.claude/git-settings.local.json` под gitignore.
- **Где токен API для описания MR?** Только если `origin` какого-то репозитория — SSH: git credential helper токена тогда не отдаёт. Варианты — «`glab`, авторизованный у тебя» и «переменная окружения `GITLAB_TOKEN`»; другое место — «Other». Запись: строка в `memory/commands/git.md`. При HTTPS вопроса нет: токен даёт git credential helper, строка пишется сама.

План — **списками**: перечисление в строку через запятую не читается. Каждый пункт — что будет и одной фразой зачем. Разделы по порядку:

## Phase 4: Generation

Создавай файлы параллельно где можно. **`.claude/settings.json` — последним файлом фазы** (4.3): его `deny` и `allow` действуют сразу после записи, в этой же сессии, и запрет вроде `Bash(cd:*)` отклонил бы следующие шаги setup. **Правило шаблонов:** engine-блоки (`<!-- beerpowers:engine … -->` … `<!-- /beerpowers:engine -->`) переносятся в проект **байт в байт** вместе с маркерами — по ним `/beerpowers:update` сливает следующие версии механически. Подставляются только плейсхолдеры вне блоков. Условный блок (`if=<ключ>:<значение>`) вписывается, только если условие выполняется по `workspace.json`; не выполняется — блок вырезается вместе с маркерами.

**Один факт — одно место.** Проектный слот не повторяет того, что уже сказал другой слот или engine-блок, — роль, которая видит одно правило в трёх файлах, не знает, какое из них свежее, и копии расходятся с первой правкой. Владельцы:

| Что | Где живёт | Остальные |
|---|---|---|
| доменные инварианты — вместе с запретом, который инвариант охраняет («сгенерированный клиент руками не правится») | `memory/project/domain-invariants.md` | не пересказывают: ни `safety-rules`, ни charter, ни роли — ни в «Не трогает», ни в чеклистах. Страховка механизмом (`.claude/rules/`, `quality-gates.txt`) — не пересказ: она доставляет правило в момент правки |
| опасные действия команды — команды, данные, секреты, процессы, прод — и развилки с подтверждением | `memory/project/safety-rules.md` | ссылаются |
| формы сборки, гейтов, линта, миграций, порты, локальная инфраструктура, быстрые гейты | `memory/commands/<скоуп>.md` | роли и charter — указатель на раздел |
| стек и факты вида «у фронта нет тестов», «CI проверяет только build» | таблица «Стек» charter | не повторяют |
| git: соглашения, токен, свой флоу | `memory/commands/git.md` | charter и роли git не описывают |
| конвенции тестов | `memory/tests/<скоуп>.md` | роли ссылаются |
| грабли кода | `memory/issues/<область>.md` | не в `commands/` |
| «Не трогает» и модель роли | файл роли (слот `DOES_NOT_TOUCH`, frontmatter) | charter держит маршрут: роль, `subagent_type`, миссия, триггеры, «Read on spawn»; skills — и во frontmatter, и в колонке «Skills»: тиммейту рантайм поле `skills` не отдаёт |

Слот, которому нечего добавить сверх владельца, опускается вместе со своей строкой.

**Проект уже собран (режим дозаполнения из Q2) — правь точечно, не перегенерируй.** Добавляй только недостающее: строки новых ролей в таблицу состава, недостающие engine-блоки по месту из шаблона, новые файлы. Проектный текст, доменные инварианты и `memory/` не переписывай. Проект собран qtim (штамп `generated-by: qtim v…`) — setup не запускается: перевод делает `/beerpowers:update` записью `→ 2.0.0` реестра миграций; скажи это пользователю и остановись.

Форма — под каждый путь из `allow`, с `projects/<репо>` и с `worktrees/*/<репо>`: `Bash(npm --prefix projects/<репо> run migration:revert:*)`, `Bash(npm --prefix worktrees/*/<репо> run migration:revert:*)`;

Правило под абсолютный путь или под маску интерпретатора (`Bash(node:*)`) — нельзя: первое различается между машинами, второе открывает любой скрипт;
- `permissions.ask` — при скопированном `yandex-tracker-write.mjs`: команды, которые идут только после «да» человека, — `Bash(node .claude/bin/yandex-tracker-write.mjs create:*)`, `… edit:*`, `… move:*`, `… attach:*`, `… detach:*`. Запись в трекер видна заказчику, и правило `ask` держит вопрос, даже если кто-то добавит широкое `allow` на скрипт;
- `claudeMdExcludes` — `CLAUDE.md` **каждого** вложенного репозитория и рабочего дерева, без исключений: маски `**/projects/*/CLAUDE.md`, `**/projects/*/.claude/CLAUDE.md`, `**/worktrees/*/*/CLAUDE.md`, `**/worktrees/*/*/.claude/CLAUDE.md`. - `hooks` — **только хуки под стек** (Q6): барьеры, SessionStart и SubagentStop-напоминание даёт `hooks.json` плагина, в проекте их не дублируй.

`quality-reminder` (если выбран): PostToolUse на `Edit|Write`, `sh "$CLAUDE_PROJECT_DIR/.claude/hooks/quality-reminder.sh"`, `timeout: 10`. Вывод хука идёт через `additionalContext`: stdout PostToolUse в контекст модели сам по себе не попадает.

**Напоминание `screenshots-reminder` (только если выбрано)** — один скрипт на два события: на старте роли-тестера пишет метку времени, на остановке ищет скриншоты `<роль>-*` в `memory/tasks/*/screenshots/` новее метки. Matcher — `subagent_type` тестера из charter, с якорями; аргумент `--agent` — он же (префикс скриншотов скрипт возьмёт из таблицы «Состав»; явный — `--prefix`, явный каталог — `--dir`, запасное окно без метки — `--window`):

```json
{ "hooks": {
  "SubagentStart": [ { "matcher": "^testing-agent$", "hooks": [ { "type": "command",
    "command": "sh \"${CLAUDE_PROJECT_DIR}/.claude/hooks/screenshots-reminder.sh\" --agent testing-agent",
    "timeout": 10 } ] } ],
  "SubagentStop": [ { "matcher": "^testing-agent$", "hooks": [ { "type": "command",
    "command": "sh \"${CLAUDE_PROJECT_DIR}/.claude/hooks/screenshots-reminder.sh\" --agent testing-agent",
    "timeout": 10 } ] } ] } }
```

Свежесть — «моложе старта этого захода роли», а не окно от момента проверки. Без записи на `SubagentStart` хук работает в запасном режиме — окно в минутах — и сам говорит об этом в напоминании. Срабатывает **один раз на роль за сессию**: `exit 2` возвращает роль в работу, подменяя ей задачу текстом из stderr (замер — `reference/runtime-compat.md`), поэтому текст прямо говорит, что прежняя задача остаётся, и даёт выход без скриншотов — строку «Скриншоты: не снимались — <причина>». Хук не знает, зачем тестера подняли повторно: заход мог быть про тесты или API, а скриншоты прошлого захода остаются в силе, если фикс экран не менял. Это решает финальный `reviewer` по маршруту фикса и сверяет с ним строку тестера. Скажи пользователю прямо: цена — лишний ход тестера на каждом заходе без скриншотов; выключается удалением обеих записей из `.claude/settings.json`.

**Что личное — в `.claude/settings.local.json`** (под gitignore): разрешения, накопленные по ходу работы, и машинозависимые пути.

Оба файла создавай/мёржи через Read, не затирая существующее. `settings.json` коммитится — **покажи дифф перед записью**.

Раскладка по виду знания из `${CLAUDE_PLUGIN_ROOT}/templates/memory/`: `MEMORY.md`, `retro-log.md`, `project/` (`project-map.md`, `glossary.md`, `domain-invariants.md`, `safety-rules.md`, каталог `modules/`), `commands/README.md`, `issues/known-issues.md` + `accepted-risks.md`, `tests/backend.md`, `frontend.md`, `probes.md`, `unverified.md`, каталоги `tech-debt/` и `adr/`. `memory/tasks/` заранее не создаётся — его заводит первая задача (пустой каталог git не хранит, а `.gitkeep` в нём — файл вне папки задачи). Engine-блоки — байт в байт, плейсхолдеры — по Q4. **Раздел без фактов не пишется вовсе:** ни заготовки, ни строк «не зафиксировано», «заполнить позже», «пока не выявлено» — их никто не заполнит, а читающий тратит на них внимание; файл появляется в раскладке и без них. **«Грабли» при setup не пишутся:** грабли — случай из работы с датой и командой, их записывают роли и `/beerpowers:retro`; общая истина вида «локальная ветка может отставать» граблями не является. Плейсхолдеры: `{{PROJECT_MAP}}` — карта и точки входа, `{{INVARIANTS_DETAILED}}` — доменные инварианты из Discovery (деньги, изоляция модулей, тенант, генерируемый код, производные индексы), каждый заголовком с номером и местом в коде — **всегда, не по Q4**: это единственный их список, его читает каждая роль; не выявлены — строка «При setup не выявлены», `{{NEVER_CODE}}` и `{{CONFIRM_EXTRA}}` — проектные опасные действия и развилки сверх engine-блоков (запрет, который охраняет инвариант, — не сюда, а в инвариант), `{{COMMANDS_INDEX}}` — строки таблицы `commands/README.md`, `{{OWNERS_EXTRA}}` — проектные маркеры владельцев (нет — удалить), `{{BREAKPOINTS}}` — брейкпоинты из Discovery таблицей «брейкпоинт · файл:строка · запись `viewports`» (брейкпоинтов в коде нет — строка «в коде не заданы, ширины подтвердил пользователь при setup»).

**`commands/git.md` и `commands/worktrees.md` создаются всегда**, даже если Q4 не выбрал формы команд: на них ссылаются engine-блоки charter и `team-lead.md` и копия `worktrees.md`. В `git.md` — только то, чего нет в `git-flow.md`, `git-settings.json` и у сервера: откуда токен API для MR по каждому хосту (HTTPS — git credential helper, SSH — ответ Q9), раздел «Флоу <репо>» на каждый `custom`-репозиторий из Q9, соглашения компании, которые **расходятся** с `git-flow.md` или дополняют его (свой набор типов коммитов, ссылка на регламент), если их называют `CLAUDE.md` или `README` продукта. Совпадающее с `git-flow.md` не пишется: формат коммита, язык, наклонение и типы по умолчанию уже там. Правило из `CLAUDE.md` одного репозитория пишется с именем этого репозитория («`shop-frontend`: ветка задачи обновляется `rebase`, не `merge`»), а не как правило проекта: у соседнего репозитория его может не быть. Таблицы профилей и веток, формы ветки, push и схлопывания там нет: профили — в `git-settings.json`, ветки — у сервера, формы — в `git-flow.md`. В `worktrees.md` — порт, зависимости и тестовая база фактами Discovery. `commands/<скоуп>.md` скриптов из Q5 (`figma.md`, `yandex-tracker.md`) — вместе со скриптом: факты проекта (очередь задач, организация, команда, которой выгружать) и строка «Доступ — шаблон `.claude/<скрипт>-settings.json.example`»; механику токенов файл не пересказывает — она в шаблоне и в шапке скрипта. Индекс долга `tech-debt/tech-debt.md` не пишется руками — его создаёт `node .claude/bin/tech-debt-index.mjs` после копирования скриптов. Файлы тестов без скоупа в проекте (нет фронта — нет `tests/frontend.md`) не создавай и убери строку из индекса.

**В режиме дозаполнения память не трогай:** существующие файлы — знания проекта; создай только недостающие из раскладки, и то по подтверждению.

### 4.6 CLAUDE.md — импорт charter и указатель на team-lead

Секция «Команда агентов» в конце `CLAUDE.md`: строка импорта charter **обычным текстом абзаца** — `@.claude/team-charter.md` (здесь в код-спане намеренно, чтобы не импортироваться; в файле — без обратных кавычек и fenced-блока: [парсер импортов пропускает и то, и другое](https://code.claude.com/docs/en/memory#import-additional-files)); строка «Team-lead перед первым вызовом `Agent` читает `.claude/team-lead.md`; роли его не читают» — указателем, **не импортом**: `team-lead.md` ролям не нужен, а импорт отдал бы его каждой; короткий указатель на `/beerpowers:task-start`, `/beerpowers:team-lazy`, `/beerpowers:team-up`. Файла нет — предложи создать.

Иерархию `CLAUDE.md` рантайм отдаёт каждой роли в стартовом контексте, импорт разворачивается в неё дословно — charter приезжает роли сам (замер — `reference/runtime-compat.md`). Инструкцию «прочитай charter на спавне» это не отменяет: импорт живёт в файле пользователя, а `explorer` (`Explore`) `CLAUDE.md` не получает вовсе. Цена — charter в контексте каждой сессии и каждой роли целиком: держи проектные блоки компактными, детали — в `memory/` и правила (4.7).

`CLAUDE.md` принадлежит пользователю: **покажи дифф перед записью**, добавляй секцию в конец, ничего не переписывая.

### 4.7 Правила по путям — `.claude/rules/`

Доменные требования, привязанные к файлам, генерируй как правила: [рантайм подмешивает их любому, кто открыл совпавший файл через `Read`](https://code.claude.com/docs/en/memory#path-specific-rules). Каждый файл — YAML-frontmatter с `paths` и короткий список требований. Глобы — под **реальную раскладку** и с рабочими деревьями: `projects/<репо>/…` и `worktrees/*/<репо>/…`. Иначе роль в worktree правило не получит.

Что выносить — только то, что уже есть в чеклистах ролей: миграции (идемпотентность, индекс на FK, каскад к владельцу), клиентский код (типы из единого источника, zero-any, no-hardcode, loading/empty/error), серверный слой (валидация входа, доступ за гардом). Правила без `paths` не создавай.

**Чеклист `reviewer` эти правила не заменяют**: `paths`-правило поднимается только на `Read`, а дифф через `Bash` его не поднимает.

### 4.8 `.gitignore`

Файл — в корне workspace: файла нет — создай с этими строками, есть — допиши, чего нет (дифф — перед записью). `.gitignore` репозиториев в `projects/` не трогается: это файлы продукта. Строки: `projects/`, `worktrees/`, `memory/tasks/*/figma/`, `memory/tasks/*/screenshots/`, `memory/tasks/*/tracker/task-attachment/`, `.claude/settings.local.json`, `.claude/.cache/`, `.claude/git-settings.local.json`, `.idea/`, `.vscode/`, `.claude/yandex-tracker-settings.json` и `.claude/figma-settings.json` (если скопированы соответствующие скрипты). Каталоги IDE — личные настройки редактора: в репозитории конфигурации команды им не место, а коллега с другим редактором получил бы их чужими.

## Critical Rules

1. **Ничего не пишем до Phase 3 (Plan Confirmation).** Discovery — только текстовый вывод.
2. **Не делегируй фазы другим агентам** — setup делаешь ты сам как team-lead.
3. **Команды setup — без `cd`:** `git -C <путь>`, пути от корня workspace. Записанный `settings.json` запрещает `cd` в этой же сессии.
4. **Не запускай** lint/tests/migrations и не коммить. Исключение — два скрипта из копий: `tech-debt-index.mjs` (пишет индекс долга) и `workspace-check.mjs` (только читает).
5. **Если CLAUDE.md/AGENTS.md есть** — они источник правды для project-specific правил.
6. **Существующие файлы не заменяются целиком и не удаляются** — `CLAUDE.md`, `settings.json`, агенты, память: только `Edit` с диффом пользователю; при коллизии имён агентов спроси (дополнить / пропустить / переименовать). Пока идёт setup, это держит барьер `guard-user-files` плагина (`reference/hooks.md`): `Write` поверх существующего файла и удаление он отклоняет. Отказ барьера — не повод искать обход: назови пользователю файл, решение за ним.
7. **Adapt to stack** — не тащи чужую специфику; подставляй плейсхолдеры под реальный стек, лишние роли и пресеты опускай.
8. **Engine-блоки не правятся под проект.** Нужна проектная оговорка — она идёт вне блока, следующей строкой.
9. **Не пиши декоративные emoji** в файлах. Статус-маркеры в чеклистах/таблицах — допустимы.
10. **Канон рантайма** — никаких `TeamCreate`/`TeamDelete`/`team_name`; team-lead = сессия, не агент.
