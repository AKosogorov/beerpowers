# /beerpowers:worktrees-clear — уборка рабочих каталогов

```
/beerpowers:worktrees-clear [<КОД> …] [--force]
```

Каталоги `worktrees/` и `projects/` — константы движка; контракт и правило обхода репозиториев —
[`workspace.md`](../reference/workspace.md).

Источник правды — **ветка по умолчанию на `origin` и база задачи** из её `git-flow.md`
(релизная, ветка предшественника) после свежего `fetch`. Ветка влита туда, значит MR принят
и worktree больше не нужен. Локального варианта нет намеренно: локальная ветка отставала молча
и называла влитые задачи активными. Ветки и влитость — [`git-flow.md`](../reference/git-flow.md).

Раскладка и правила worktree'ев — [`worktrees.md`](../reference/worktrees.md), проектные
подробности — `memory/commands/worktrees.md`.

Вызывается и сама по себе, и автоматически последним шагом [`/beerpowers:retro`](retro.md) —
с теми же кодами и тем же флагом: обе команды убирают следы одного события — влитой задачи, —
только эта по рабочим каталогам, а та по артефактам памяти.

## Аргументы

**Без аргументов** — все worktree'и всех репозиториев workspace плюс осиротевшие каталоги
(шаг 2б); проверка влитости по шагу 2, удаление только влитых.

**Коды задач** сужают уборку до каталогов `worktrees/<КОД>/<имя-репо>/` названных задач,
включая осиротевшие с тем же кодом. Проверка влитости для них та же: невлитый каталог из списка
**не удаляется**, в отчёте стоит «активен: своих коммитов N».

**`--force`** снимает проверку влитости (шаг 2 целиком) — для ветки, которую решено
не доводить до MR. Без кодов чистит **все** рабочие каталоги, включая живые: это осознанный
режим «снести всё», и отчёт перед подтверждением обязан это показать. Два ограничения:

- незакоммиченное (`status --porcelain`) и коммиты, которых нет на `origin`
  (`git -C <путь> log --oneline @{upstream}..HEAD`; нет upstream — все коммиты ветки против
  ближайшей цели), проверяются всё равно и перечисляются в отчёте построчно,
  по каждому каталогу: это то, что исчезнет без следа;
- подтверждение человека обязательно, и в вопросе названо, что именно теряется — число
  каталогов, список веток с неотправленными коммитами, незакоммиченное. `--force` снимает
  проверку, а не разговор.

Удаление под `--force` идёт через `workspace-clean worktree <КОД> --merged-anyway --apply` —
флаг скрипта ровно для этого случая, он печатает число теряемых коммитов.

## 1. Собрать состояние

Для каждого репозитория, у которого есть worktree'и:

```bash
git -C <репо> worktree list
git -C <репо> fetch origin --prune
```

`fetch` обязателен: без него `origin/*` показывает состояние прошлого раза,
и вывод команды будет ложным. Сети нет — остановись и скажи об этом; без `--force` дальше идти
нечем, а `--force` — решение человека, не способ обойти отсутствие сети. Под `--force`
`fetch` всё равно делается, если сеть есть: список неотправленных коммитов в отчёте считается
против свежего `origin`.

## 2. Проверить каждую ветку (пропускается под `--force`)

Влитость считается одной функцией — `.claude/bin/lib/git.mjs`, по предкам коммита **или**
по содержимому патча, против ветки по умолчанию на `origin` и базы задачи. Сухой прогон
уборки зовёт её сам и печатает вердикт по каждому дереву задачи — это и есть проверка:

```bash
.claude/bin/workspace-clean worktree <КОД>
```

Отдельную ветку — напрямую; обе цели называет `node .claude/bin/git-base.mjs <имя-репо> <КОД>`:

```bash
node .claude/bin/lib/git.mjs merged . <имя-репо> <ветка> origin/<ветка по умолчанию> origin/<база задачи>
```

Одной проверки по предкам мало: ветку, которую влили ребейзом или cherry-pick'ом, она всегда
называет невлитой — коммиты лежат в цели под другими хешами. Замер на рабочем workspace:
предок-проверка объявила активными 47 worktree'ев из 69, а проверка по патчу нашла среди них
**21** каталог, у которого ни одного коммита без эквивалента в цели. Поэтому функция смотрит
и то, и другое.

⚠️ **«Не влита» ещё не делает задачу активной.** Ребейз с разрешением конфликтов меняет
содержимое коммита, и проверка по патчу считает его своим, хотя та же правка уже лежит в цели
другим патчем. Прежде чем объявить каталог активным, проверь состояние MR ветки — `merged`
закрывает вопрос независимо от вердикта; форма запроса — в [`/beerpowers:retro`](retro.md),
шаг 2.2. Такой каталог снимается под `--merged-anyway` с этим основанием в отчёте.

Ветка влита — worktree кандидат на удаление. Проверить **дополнительно**, что в нём нет
незакоммиченного:

```bash
git -C <путь-worktree> status --porcelain
```

Непусто — **не удалять**, показать пользователю, что именно осталось. Работа могла
не попасть в MR. Под `--force` эта проверка остаётся: незакоммиченное перечисляется
в вопросе на подтверждение.

## 2б. Найти осиротевшие каталоги — их `worktree list` не показывает

`git worktree remove` на Windows регулярно снимает регистрацию, но **не удаляет файлы**:
`failed to delete … : Invalid argument` на занятых `node_modules`. Каталог остаётся без
`.git`, git о нём больше не знает, и предыдущий шаг его не видит вовсе. Прецедент: каталог
задачи пережил уборку и весил 943 МБ.

Список фактических каталогов сравнивается со списком зарегистрированных — по каждому
репозиторию workspace — каждому `projects/<имя>/` с `.git`:

```bash
ls -d worktrees/*/*/ 2>/dev/null
for r in projects/*/; do
  git -C "$r" worktree list | tail -n +2
done
```


Каталог есть в первом выводе и отсутствует во втором — он осиротел. Признак подтверждается
одной проверкой: `ls -d <каталог>/.git` ничего не находит. Переданы коды — из первого вывода
берутся только каталоги с этими кодами.

**Осиротевший каталог опаснее живого worktree.** Незакоммиченное в нём проверить нечем —
`git status` там не работает, а ветка могла быть уже удалена. Поэтому в отчёт он идёт
отдельной строкой, и решение по нему принимает человек, даже когда по всем признакам
это мусор.

## 3. Отчитаться таблицей

По каждому worktree: путь, ветка, куда влита и чем это видно (предок или патч; под
`--force` — «не проверялось, своих коммитов N»), есть ли незакоммиченное, вердикт. Ничего
не удалять до подтверждения человека — удаление рабочего дерева необратимо, а незакоммиченные
правки восстановить неоткуда.

Осиротевшие каталоги из шага 2б — отдельной строкой: путь и отметка «git не знает,
незакоммиченное проверить нечем».

**Вес каталогов не считать** — ни `du -sh` по worktree'ям, ни общий вес к удалению.
`node_modules` и `vendor` на Windows обходятся минутами, отчёт ждёт этого без пользы для
решения: удалять или нет, решают влитость и незакоммиченное, а не размер.

## 4. Удалить подтверждённые

```bash
git -C <репо> worktree remove <путь-worktree>
git -C <репо> branch -d <КОД-ЗАДАЧИ>
```

`<путь-worktree>` — `worktrees/<КОД-ЗАДАЧИ>/<имя-репо>`; относительный путь `git -C`
считает от каталога репозитория, поэтому надёжнее абсолютный.

`branch -d` вместо `-D` намеренно: он откажется удалять невлитую ветку, то есть служит
второй проверкой. Отказался — разбираться, а не переходить на `-D`. Два исключения, оба
осознанные и названные в отчёте: ветка, чьё содержимое уехало в цель другими хешами
(вердикт проверки — «патч»),
и уборка под `--force`, где человек подтвердил потерю перечисленных коммитов.

⚠️ **`worktree remove` часто не удаляет файлы, хотя регистрацию снимает.** На Windows
он падает с `failed to delete … : Invalid argument` на занятых `node_modules`, и каталог
остаётся сиротой — именно так появляются находки шага 2б. Проверяй результат, а не код
возврата: `git -C <репо> worktree list` больше не показывает путь, а `ls -d <путь>` всё
ещё находит.

**Файлы убирает `workspace-clean`, а не `rm -rf`** — последний остаётся в `deny`,
и обходить его другой формой (`rm -r`, `find -delete`) нельзя:

```bash
.claude/bin/workspace-clean worktree <КОД-ЗАДАЧИ>                       # сухой прогон
.claude/bin/workspace-clean worktree <КОД-ЗАДАЧИ> --apply               # удалить
.claude/bin/workspace-clean worktree <КОД-ЗАДАЧИ> --merged-anyway --apply   # под --force
.claude/bin/workspace-clean orphans --orphan --apply                    # осиротевшие из шага 2б
```

Скрипт сам снимает регистрацию worktree, сам проверяет незакоммиченное и влитость ветки
и отказывается трогать что-либо, кроме формы `worktrees/<КОД>/<имя-репо>`. Отказал — читай
причину, а не обходи: он отказывает по делу. `--merged-anyway` снимает только проверку влитости;
на незакоммиченном скрипт откажет и под ним — это и есть последняя защита `--force`.

Пустой каталог `<КОД-ЗАДАЧИ>/` после удаления последнего worktree внутри тоже убрать.

## 5. Проверить артефакты задачи

Влитая задача — повод разобрать `memory/tasks/<КОД-ЗАДАЧИ>/`. Это делает
[`/beerpowers:retro`](retro.md), здесь только напомнить о нём в отчёте, папку не трогать.
Пришли сюда из `/beerpowers:retro` — напоминание не нужно, артефакты уже разобраны.
