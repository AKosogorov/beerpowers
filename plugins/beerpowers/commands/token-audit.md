# /beerpowers:token-audit — куда уходит бюджет токенов

Считает всё локально по логам `~/.claude/projects`, сети не требует. Метод и три ловушки
формата логов, без которых цифры врут правдоподобно, описаны в шапке самого скрипта —
`.claude/bin/token-audit.mjs --help`.

Аргумент: `project` — только по проекту, `window` — только по текущему окну лимита,
пусто — оба разреза.

## 1. Состояние лимитов подписки

Прочитать лимиты аккаунта инструментом сессии (`get_usage`, `session_id: "self"`). Нужны
две вещи: процент пятичасового окна и его `resetsAt`. Статус `not_applicable` означает
работу не по подписке — тогда шаг 3 пропустить и сказать об этом.

Начало окна = `resetsAt` минус 5 часов. Считать его арифметикой, а не на глаз: окно
сбрасывается не в круглый час.

## 2. Разрез по проекту

```bash
node .claude/bin/token-audit.mjs --top 8
```

Запускать литеральным путём от корня — так его пропускает правило `allow` из setup; скрипт определяет
каталог логов по рабочему каталогу, который у инструмента уже равен корню workspace.

Человеку команду давать в его оболочке: в PowerShell — `node .claude\bin\token-audit.mjs`,
прямой вызов там молча не выводит ничего (шебанг Windows не исполняет).

## 3. Разрез по окну лимита

```bash
node .claude/bin/token-audit.mjs --all-projects --since <начало-окна> --top 5
```

`--all-projects` обязателен: лимит аккаунтный, работа в других проектах тратит то же окно.

Посчитать масштаб: процент окна разделить на измеренные billed-токены — получится, сколько
токенов приходится на один процент. Отсюда ёмкость окна и остаток в запросах при текущем
среднем контексте.

## 4. Отчёт

Коротко, числами, без пересказа всего вывода скрипта:

- итоги корпуса: запросы, billed, эквивалент, доля чтения кеша, параллельность, цепочки.
  Если пользователь сохранял прошлый прогон через `--json` и назвал файл — сравнить
  с ним и показать разницу; файла нет — не выдумывать динамику, дать срез как есть;
- окно лимита: сколько процентов, сколько токенов в проценте, сколько работы осталось
  до сброса и когда он;
- три самых крупных рычага по текущим данным, каждый — с числом запросов или процентом,
  а не словами;
- где именно рычаг применим: роли и сессии с худшими показателями, а не средние по корпусу.

Обязательные оговорки, без них отчёт неполон:

- долларовый эквивалент считается по прайсу API и к сумме подписки отношения не имеет —
  это линейка для сравнения рычагов между собой;
- масштаб «токенов на процент» снят по одной точке и на том миксе моделей, который был
  в окне; формулу взвешивания Anthropic не публикует, линейность не проверена;
- цепочки одиночных чтений — верхняя граница экономии: там, где путь второго чтения берётся
  из результата первого, слияние невозможно, и скрипт такие случаи не отличает;
- логи не покрывают веб-клиент и мобильное приложение, а окна они тратят.

Отчёта в `memory/` эта команда не заводит: цифры устаревают с каждой сессией, а метод
живёт в скрипте. Результат идёт пользователю в чат; файл — только если он попросил
(`--json` для машинного сравнения со следующим прогоном).
