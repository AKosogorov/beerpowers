# Задача и баг в трекере

Описание задачи в первую очередь читают люди разных специальностей — менеджер, дизайнер,
разработчик, QA, — и только во вторую ИИ. Поэтому в описании нет технических подробностей:
они уходят отдельным файлом-вложением. Шаблон один: общие поля и два набора секций — для задачи
и для бага. Какой тип — решает человек.

Черновик пишется обычным markdown, без разметки конкретного трекера: в неё его переводит
адаптер записи — скрипт `.claude/bin/<трекер>-write.mjs` (Яндекс Трекер — `yandex-tracker-write.mjs`).
Механическую часть правил проверяет `check <черновик.md>` адаптера, пустой черновик печатает
`template task` или `template bug`. Проверка ловит форму, а не смысл: правила ниже, которые
она не видит, соблюдаются по тексту.

## Черновик

Черновик — markdown-файл: название, таблица полей, строка `---` и описание.

```markdown
# Название задачи (front)

| Поле | Значение |
|---|---|
| Очередь | SHOP |
| Тип | Задача |
| Доска | 96 |
| Теги | Frontend |
| Исполнитель | — |
| QA | — |
| Ревьюер | — |
| Связи | зависит от SHOP-43; связана с SHOP-47 |

---

<описание: шапка, секции, подпись>
```

Под названием может стоять служебная заметка строками `> …` — в трекер она не уходит.

## Поля

- **Обязательные:** тип (`Задача` или `Ошибка`), очередь, доска (числовой id), тег `Frontend`
  или `Backend` у задачи по разработке.
- **Необязательные:** исполнитель, QA, ревьюер — логином; не назначен — `—`.
- **Название.** У задачи — результат глазами пользователя, а не «Сделать…»: «Новый гость,
  которого кассир посадил вместо прежнего, привязывается к заказу». У бага — «<где>: <что
  не так>», симптом, а не причина. В конце — сторона: `(front)` при теге `Frontend`, `(back)`
  при `Backend`.
- **Фронт и бэк — две задачи**, по одной на сторону, со связью «зависит от». Одна задача
  с обоими тегами не заводится.
- **Связи** — через `;`, вид и ключ: `зависит от`, `блокирует`, `связана с`, `подзадача для`,
  `родитель для`. Каждый ключ задачи, упомянутый в тексте, получает связь: зависимость — своим
  видом, остальное — «связана с». Если трекер сам связывает ключи из
  описания, вид из черновика заменяет автоматическую связь при создании и правке.

## Шапка

Стоит до первой секции, без заголовка; каждый блок — только если есть что написать.

- **`**Зависит от:**`** и **`**Блокирует:**`** — список. Пункт — задача трекера (ключ и одной
  строкой, чего ждём; в поле «Связи» — тот же ключ своим видом) или внешняя зависимость (что
  именно и от кого — «Ключ API reAPI от заказчика»; без связи). Что можно делать до снятия
  зависимости, здесь не пишется: это видно из секций.
- **`**⚠️ При выкладке:**`** — список действий, без которых задача не заработает на стенде,
  и разрушительных последствий выкладки: «Демо-товары удаляются», «Прежняя загрузка товаров
  из файла выгрузки перестаёт работать», «Менеджер загружает книгу товаров с экрана
  админки». Не сюда: что появится на сайте и какие задачи ждут эту.

## Секции задачи

Заголовки — ровно такие и в таком порядке; необязательная секция без содержания не пишется.

| Секция | Обяз. | Что в ней |
|---|---|---|
| `## Цель` | да | 2–4 предложения: что увидит или сможет пользователь либо заказчик, когда задача сделана. Без «как» |
| `## Контекст` | нет | Что сейчас видит пользователь, почему меняем, основание: ТЗ, пункт сметы, решение заказчика с датой. Не повторяет цель |
| `## Где` | если задача про страницы или экраны | Полные ссылки на страницы с окружением (рабочий сайт, тестовый стенд), адрес — читаемый, не punycode. Макет — ссылка на фрейм Figma с `node-id`, не на файл целиком. Страницы в тексте называются так же |
| `## Что делаем` | да | Пункт на изменение поведения, языком продукта: экраны, кнопки, тексты, правила. Числа и тексты интерфейса — точно |
| `## Критерии приёмки` | да | Проверяемые наблюдением, без чтения кода, в форме «кто — что делает — что видит»: «Студент отправляет домашнее без файла — отклонено». По ним QA пишет чеклист, а исполнитель — тесты. Есть риск регрессии — пункт «остальное работает как раньше» |
| `## Вне объёма` | нет | Только функционал, который в задаче упомянут, но в объём не входит; у пункта — где он делается (ключ) или почему не делается |

## Секции бага

| Секция | Обяз. | Что в ней |
|---|---|---|
| `## Где` | да | Ссылка на страницу, окружение, устройство, браузер и ширина экрана, роль пользователя. Баг API без интерфейса — метод и адрес |
| `## Шаги воспроизведения` | да | Нумерованные, от открытия страницы, по одному действию на шаг; воспроизводится всегда или иногда. Найдено не через интерфейс (журнал, код, ревью) — вместо неё `## Как обнаружено` |
| `## Фактический результат` | да | Что видно, словами, без догадок о причине |
| `## Ожидаемый результат` | да | Что должно быть и откуда это ожидание: ТЗ, макет, как работало раньше, как на соседней странице |
| `## Доказательства` | да | Скриншот в тексте с выделенным местом; для последовательности действий — скринкаст. Доказательство лежит в этой задаче, а не в соседней |
| `## Влияние` | да | Кого задевает, есть ли обход, блокирует ли релиз, с какого момента проявляется (если известно) |
| `## Вне объёма` | нет | Как в задаче |

Причина и место в коде — не в описании, а во вложении `<КОД>-tech.md`.

## Общие правила текста

- **Без техники.** Нет путей к файлам, имён классов и полей, эндпоинтов, SQL, команд, SHA,
  номеров MR. Исключение — баг API: метод, адрес, код ответа.
- **Техника — вложением `<КОД>-tech.md`:** ограничения и ловушки, контракты, отвергнутые варианты,
  риски, что не проверено. Место в коде — по имени модуля, функции, компонента, **без номеров
  строк и SHA**: к исполнению они устаревают, и место всё равно ищут заново. Построчного «что
  менять» нет.
- **Вложение — обычной ссылкой из пункта, которому нужны детали:** «…, детали — в
  `[SHOP-44-tech.md](путь к файлу)`». Отдельного списка вложений и итоговой строки «подробности —
  в …» нет: вложения трекер показывает сам.
- **Картинка — в тексте рядом с тем, что показывает:** `![подпись](путь к файлу)`. Текст сам
  говорит, что не так; картинка подтверждает, а не заменяет.
- **Путь к файлу — локальный, от каталога черновика:** адаптер загрузит файл в трекер
  и подставит его адрес. Ссылка на адрес в сети остаётся ссылкой.
- **Без оценок, бюджета и ставок** — ни в описании, ни во вложениях. Оценка пишется комментарием.
- **Без паролей и персональных данных.** Учётка — ролью или тестовым логином.
- **Даты абсолютные**, решения — с автором и датой.
- **Задача открывается без вопросов.** Вопросы и принятые решения — комментариями, не секциями.
  Решение, которое меняет объём, — правка описания плюс комментарий с решением.

## Подпись

Последняя строка описания и каждого комментария, который пишет сессия, — подпись по модели
сессии, простой строкой:

```
© Клод Клодыч Опусович
```

Sonnet — `Сонетович`, Haiku — `Хайкувич`, Fable — `Фейблович`. Выделяет её адаптер: в Яндекс
Трекере — оранжевым курсивом.

## Комментарий

Комментарий — тот же markdown без полей и секций, с подписью последней строкой; картинки
и файлы — так же локальными путями. Отправляет `comment <КОД> <файл.md>` адаптера.
