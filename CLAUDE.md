# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это за репозиторий

Маркетплейс плагинов Claude Code с единственным плагином `beerpowers` — движком команды специализированных субагентов, который `/beerpowers:setup` разворачивает в workspace веб-продукта: бэкенд и фронтенд одним или несколькими репозиториями в `projects/`. Форк [qtim](https://github.com/toiiia/qtim-agent-team) 1.14.0; апстрим подключён remote'ом `upstream` для точечных cherry-pick. Основа — markdown-промпты и JSON-манифесты; исполняемое — хуки плагина (`hooks/*.sh`), шаблоны скриптов проекта (`templates/bin/*`), Workflow-скрипты и CI. «Код» — это и промпты: правки к ним предъявляют те же требования консистентности, что и к коду.

Весь контент — на русском языке. Коммиты — conventional commits с русским описанием: `feat(setup): …`, `docs(readme): …`, `fix: …`, `chore: …`. При содержательных изменениях плагина бампай `version` в `plugins/beerpowers/.claude-plugin/plugin.json`.

## Структура

- `.claude-plugin/marketplace.json` — манифест маркетплейса, регистрирует плагин из `./plugins/beerpowers`.
- `plugins/beerpowers/commands/` — slash-команды `/beerpowers:*`: `setup` (генератор команды под проект), `team-up` / `team-lazy` / `team-down` (движок), `update` (миграция собранной команды по маркерам engine-блоков), `doctor` (диагностика + сверка копий), `task-start` (старт и возобновление задачи), `retro` (уроки, уборка влитых задач и рабочих деревьев одним заходом), `worktrees-clear`, `decision-brief`, `token-audit`, `onboard`, `product-onboard`, `feature` (PM-конвейер).
- `plugins/beerpowers/templates/charter/` — шаблоны `team-charter.md` (ролям) и `team-lead.md` (только team-lead).
- `plugins/beerpowers/templates/roles/` — шаблоны ролей и `presets/<стек>/` — стековые чеклисты, которые setup вставляет в проектную часть роли. **Каталог намеренно не называется `agents/`:** рантайм регистрирует `plugins/<name>/agents/*` как готовых субагентов плагина, и шаблоны с неподставленными `{{...}}` оказались бы вызываемыми в любом проекте.
- `plugins/beerpowers/templates/memory/` — скелет памяти по виду знания.
- `plugins/beerpowers/templates/bin/` — скрипты, которые setup копирует в `.claude/bin/` проекта с шапкой `generated by`; параметры читают из `.claude/workspace.json` через `lib/workspace.mjs`, git-настройки — из `.claude/git-settings.json` через `lib/git.mjs` (профиль репозитория, база задачи, влитость; ими пользуется `git-base.mjs`).
- `plugins/beerpowers/templates/hooks/` — хуки под стек, которые setup копирует в проект (`quality-reminder.sh`, напоминание о скриншотах `screenshots-reminder.sh`).
- `plugins/beerpowers/rules/` — правила ответа человеку (`<опция>.md`): `session-start.sh` выводит их в контекст главной сессии во **всех** проектах, где включён плагин, с charter или без; каждое выключается своей опцией `userConfig` в `plugin.json` (`/config`). Опция приходит в хук переменной `CLAUDE_PLUGIN_OPTION_<КЛЮЧ>` только после того, как пользователь её задал, поэтому нет переменной — правило включено.
- `plugins/beerpowers/hooks/` — hooks плагина: `hooks.json`, `session-start.sh`, шесть барьеров `guard-*.sh` с общим `lib/guard.sh`. Пять действуют во **всех** проектах с charter; кроме `guard-agent-memory`, они выключаются флагом `barriers` в `workspace.json` проекта. `guard-user-files` флага не имеет и действует только пока идёт `/beerpowers:setup`, `onboard` или `product-onboard`: `Write` поверх существующего файла и удаление — отказ.
- `plugins/beerpowers/reference/` — механика для team-lead'а: `workspace.md` (контракт параметров, engine-блоков и копий — читать первым), `migrations.md`, `intake-protocol.md`, `orchestration-patterns.md`, `feature-pipeline.md`, `skill-dependencies.md`, `runtime-compat.md`; плюс четыре файла, которые setup **копирует** в `.claude/reference/` проекта: `hooks.md`, `tasks-layout.md`, `worktrees.md`, `git-flow.md` — в них ссылки только на соседей и на файлы проекта.
- `plugins/beerpowers/skills/` — скилы плагина (`debug-loop`, `prototype`, `brainstorm`, `grill`, `minimal-diff`, `economy`, `page-screenshot`, `summarizing-mr-links`): доступны и team-lead'у, и ролям через `Skill` как `beerpowers:<skill>`. Движковой orchestration-логики в скилах быть не должно — их читают субагенты.
- `plugins/beerpowers/workflows/` — Workflow-скрипты (`ensemble-review.mjs`, `access-audit.mjs`, `flaky-hunt.mjs`); запуск по `scriptPath` из каталога плагина, opt-in пользователя обязателен; ESM, без `Date.now()`/`Math.random()` (ломают resume).
- `plugins/beerpowers/tests/hooks/` — фикстуры барьеров: `cases.txt` (вход JSON → ожидаемое решение) и раннер `run.sh`, отдельные сценарии окна `guard-user-files` (`guard-user-files.test.sh`) и старта и остановки роли для `screenshots-reminder` (`screenshots-reminder.test.sh`); `tests/bin/git.test.sh` — git-логика скриптов на фикстуре с локальными «серверами»; `tests/bin/help.test.sh` — каждый скрипт `templates/bin/` отвечает на `--help`; `tests/bin/yandex-tracker.test.sh` — источники доступа и тип организации трекера на заглушке `curl`.
- `examples/` — golden-референс сгенерированного: при правке шаблонов или структуры charter обнови эталон и сверь дифф.
- `ROADMAP.md` — практики, отложенные до триггера.

## Архитектура: движок vs генерируемое

- **Движок живёт в плагине** и в проекты не копируется: команды, барьеры, скилы, reference для team-lead'а, Workflow-скрипты. Режима Standalone нет.
- **Копируется то, что вызывается литеральным путём или открывается ролями:** `templates/bin/*` → `.claude/bin/`, хуки под стек → `.claude/hooks/`, четыре reference → `.claude/reference/`. Путь к кешу плагина содержит версию и различается между машинами, а `allow` матчит префикс текста команды. Копии правятся только в плагине; `update` перезаписывает их, `doctor` сверяет побайтно.
- **`/beerpowers:setup` генерирует проект-специфичное:** `team-charter.md`, `team-lead.md`, агентов, `workspace.json`, `settings.json` (общий `allow` под формы команд проекта), память.
- **Engine-блоки** (`<!-- beerpowers:engine <имя> [if=<ключ>:<значение>] -->` … `<!-- /beerpowers:engine -->`) в шаблонах charter, team-lead, ролей и памяти переносятся в проект байт в байт: внутри — ни плейсхолдеров, ни проектных литералов (каталоги движка — константы `projects/`, `worktrees/`, `memory/tasks/`). Плейсхолдеры — только вне блоков. На этом держится механическое слияние `update`.
- Брендирование и прочая специфика проекта, из которого плагин вырос, в движок не идёт: типовой проект — бэк и фронт одним или несколькими репозиториями; код всегда лежит в `projects/<имя>/`, корень workspace — отдельный репозиторий конфигурации команды и памяти.

При правке шаблонов ролей сохраняй frontmatter (`name`, `description`, `model`, `color`, `memory`, `tools`, `skills`); `description` — один абзац «что делает роль и когда её звать», без `<example>`-блоков; `effort:` во frontmatter не ставится — уровень выставляет team-lead в вызове.

## Канон рантайма Agent Teams — единый по всем файлам

Канонический источник — «Модель оркестрации» в `plugins/beerpowers/commands/team-up.md`; остальные файлы ссылаются на него, не дублируя. При любой правке соблюдай:

- Сессия = одна неявная команда. Примитивы `TeamCreate`/`TeamDelete`/`team_name` **упразднены** и не должны появляться ни в одном файле — только как упоминание об упразднённости.
- Член команды = `Agent({ name, subagent_type, prompt })`; продолжение поднятого агента — `SendMessage` (повторный `Agent` с тем же `name` = старт с нуля); общий список задач — `Task*`.
- Team-lead = главная сессия; отдельный orchestrator-агент не создаётся.
- Liveness привязан к текущей сессии CLI, не к файлам на диске.

## Три ортогональные оси — каждая описана ровно в одном файле

- «**Сколько** оркестрации» — Decision Matrix A/B/C/D — `commands/team-up.md`; класс задачи (тривиальная / lean / фича) — `templates/charter/team-lead.md`; порядок гейтов, маршрут `NOT APPROVED` и финальная точка — блок «Порядок гейтов» `templates/charter/team-charter.md`.
- «**Риск/обратимость** → дизайн-фаза + approval-гейт» — `reference/intake-protocol.md`.
- «**Какая форма**» — 6 паттернов на движке Workflow (opt-in пользователя обязателен) — `reference/orchestration-patterns.md`.

Не дублируй логику одной оси в файле другой — файлы ссылаются друг на друга относительными ссылками, они должны оставаться валидными.

## Версионирование и миграции сгенерированного

Сгенерированное в проектах не обновляется вместе с плагином — за стык версий отвечают:

- **Штамп** `generated-by: beerpowers v<версия> · mode: plugin-linked` в шапке charter и ключ `beerpowers` в `workspace.json`: пишет setup, читают `hooks/session-start.sh` (детектор дрейфа, в том числе charter со штампом `qtim v…`), `/beerpowers:update` и `/beerpowers:doctor`. Формат менять только синхронно во всех точках.
- **Контракт** — `plugins/beerpowers/reference/workspace.md`: схема `workspace.json`, engine-блоки и таблица слияния, правило копий. Новый ключ, новая форма маркера, новая копия — сначала там.
- **Backward-tolerant движок:** новое ожидание движка от проекта — всегда с fallback на дефолт контракта.
- **Правка, меняющая сгенерированное** (`templates/**`, структура charter в setup 4.1, settings-baseline), обязана: добавить запись `## → <версия>` в `reference/migrations.md`, строку «update: требуется/рекомендуется» в CHANGELOG и минорный бамп. Первое проверяет CI (`check_migrations.py`).

## Прочие инварианты контента

- `commands/*.md` и `reference/*` (кроме четырёх копируемых) читает **только team-lead**: orchestration-логика не должна попадать в промпты субагентов. Шаблоны `templates/roles/` — промпты субагентов: движковой логики там нет. Роли получают переносимую механику через **скилы** и через копии в `.claude/reference/`.
- Независимый оппонент — только claude-adversary, которого поднимает team-lead: `Agent` ролям не выдан. Codex из плагина убран.
- **Механизм платформы предпочитаем самодельному, но только после замера.** `paths`-правило поднимается на `Read` и **не** поднимается на `Bash`, `CLAUDE.md` не доходит до `Explore`/`Plan`, `exit 2` возвращает роль в работу, подменяя ей задачу текстом из stderr. Поэтому инструкции ролям механизмами не заменяются, а страхуются ими. Замеры — [`reference/runtime-compat.md`](plugins/beerpowers/reference/runtime-compat.md).
- **Git — в одном месте.** Ветки, коммиты, push, MR и стенды описаны только в `reference/git-flow.md`; charter, `team-lead.md`, роли и память на него ссылаются. Имена веток не хранятся нигде: ветку по умолчанию и цель выпуска скрипты берут у сервера, в `git-settings.json` — только профиль репозитория.
- **Барьер — объективная проверка, а не доверие отчёту:** хук плагина без флага в `workspace.json` и без charter в проекте молчит; deny — JSON `permissionDecision` с выполнимой формой исправления; новый случай — строка в `tests/hooks/cases.txt`.
- Скил, адаптированный из стороннего, требует строки атрибуции в шапке `SKILL.md` **и** записи в [`THIRD_PARTY_NOTICES.md`](THIRD_PARTY_NOTICES.md) с полным copyright и permission notice апстрима.
- Декоративные emoji — только в документах для людей: `README.md`, `CHANGELOG.md`, `TOUR.md`, `ROADMAP.md` (значок у заголовка раздела). В промптах, шаблонах, командах, reference и скилах их нет: их читает модель, и значок там — шум. Статус-маркеры (❌ anti-pattern, галки чеклистов) допустимы. 🍺 в заголовке «Нужно от тебя» (`rules/reply_blocking_asks.md`) — фирменный маркер блока просьбы к человеку, не украшение.

## Проверка изменений

CI (`.github/workflows/validate.yml`) на каждый push/PR: валидность JSON; запрет call-синтаксиса упразднённых примитивов в `plugins/` и `examples/`; `sh -n` по всем `*.sh` плагина (на Linux `sh` = dash); синтаксис скриптов `templates/bin/` по shebang (`node --check`, `bash -n`, `sh -n`); плейсхолдеры по белому списку (`check_placeholders.py`); **шаблоны без литералов проекта, engine-блоки парные и без плейсхолдеров внутри** (`check_templates.py`); **фикстуры барьеров** (`tests/hooks/run.sh`), окно `guard-user-files` и `screenshots-reminder` (`tests/hooks/*.test.sh`); git-логика скриптов (`tests/bin/git.test.sh`); `--help` каждого скрипта `templates/bin/` вне workspace (`tests/bin/help.test.sh`); `yandex-tracker` на заглушке `curl` (`tests/bin/yandex-tracker.test.sh`); относительные ссылки (`check_links.py`); резолвимость ссылок на скилы (`check_skill_refs.py`); семантика golden-эталона (`check_golden.py`); запись в реестр миграций при правке сгенерированного (`check_migrations.py`, нужен `fetch-depth: 0`); Workflow-скрипты (`check_workflows.mjs`). Локально — те же скрипты; Python нужен 3.x.

- Ручная проверка установки: `/plugin marketplace add AKosogorov/beerpowers` → `/plugin install beerpowers@akosogorov`; рантайму нужен флаг `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` в `settings.json`.

## Чеклист при обновлении Claude Code

Плагин привязан к экспериментальному рантайму Agent Teams — при апгрейде CLI перепроверь:

- имена инструментов в `tools:` frontmatter шаблонов `templates/roles/` — инструменты появляются и упраздняются (прецедент: `MultiEdit` слит в `Edit`). Набор, который роль реально получает, зависит от того, кем она поднята: [фоновый субагент](https://code.claude.com/docs/en/sub-agents#available-tools) теряет всё сверх фиксированного набора **включая заявленное в `tools:`**, тиммейт вдобавок сохраняет `Task*`/`Cron*`. `Skill` роль получает только если он в её `tools:`; проверяем **только фактическим вызовом**. Процедура замера и журнал — [`reference/runtime-compat.md`](plugins/beerpowers/reference/runtime-compat.md);
- поведение hooks: какие события инжектят stdout в контекст модели (SessionStart — да), а какие видны только в transcript (SubagentStop); доходит ли `CLAUDE_PROJECT_DIR` до хуков плагина;
- поле `memory` frontmatter агентов и путь agent-memory (`user` → `~/.claude/agent-memory/<agentType>/`, `project` → `.claude/agent-memory/<agentType>/`, `local` → `.claude/agent-memory-local/<agentType>/`). **Рантайм сам инжектит в промпт роли блок агентской памяти** — шаблоны его не дублируют; барьер `guard-agent-memory` знает все три пути;
- канон «Модели оркестрации» в `commands/team-up.md` — не изменились ли примитивы рантайма;
- при смене поколения моделей — перечитай шаблоны ролей с вопросом «какие инструкции компенсируют слабости прошлых моделей»: компенсирующий скаффолдинг выпиливай, инварианты оставляй; `model:` — **явный тир алиасом** (`opus` / `sonnet` / `haiku`), не `inherit` и не ID поколения.
